## 3. 已量化的问题点

### 3.1 【最大浪费】TRANSPOSE-G 分组在编码期完整算了 4 遍

`encodePlanTranspose()`（`codec.ts:1161`）为每个 `TRANSPOSE_GROUP` 分组做：

```ts
const candidate = encodeTerrainGroup(parts, {id: ID.TRANSPOSE_2D, s: spec.s, r: 1})  // ① 内部又编码 legacy + geometric 两遍
const enhanced  = encodeGroupedTranspose(parts, spec.s, undefined, undefined, true)   // ② v13 分组
// 与 ③ encodeGroupedTranspose(parts, spec.s, costs) 完全等价于 ① 的内部 legacy 那一遍
```

实测（`mozilla` 前 8 MiB，步长 24，单分组）：

| 计算 | 耗时 | 产物 |
| --- | ---: | ---: |
| `TRANSPOSE_2D`（内部：legacy + geometric） | 76,890 ms | 4,369,795 B |
| `TRANSPOSE_GROUP_V3`（v13 分组） | 52,854 ms | 4,445,504 B |
| `TRANSPOSE_GROUP`（legacy 分组） | 35,893 ms | 4,369,794 B |
| **合计** | **165,637 ms** | 最终只用其中一个 |
| 其中重复计算 | **88,747 ms（53.6%）** | 与 ① 内部的 legacy 完全等价 |

也就是说：**只要把 `TRANSPOSE_GROUP_V3` 和 legacy 的产物缓存下来复用，就能在这个样本上省掉 53.6% 的转置编码时间**，且字节完全不变（`4,369,794` vs `4,369,795` 是 `TRANSPOSE_2D` 多一个模式字节）。`mozilla` 有 5.8% 的原始数据走 `TRANSPOSE-G3`，26 个区域；`samba` 有 9.1% 走 `TRANSPOSE-2D`。

### 3.2 规则无法跨区域合并 → 同族模型重复冷启动

分组键就是规则字典项 `(id, s, r)`；`CM-TEXT` / `CM-TEXT2` / `CM-TEXT3` 是三个不同 ID，**即使数据相同也会拆成三个模型、三份冷启动**（每份 `Model` 构造时都 `fill(32768)` 分配 `nctx × 2^bits × 2 B` 的表）。

`probe-unify` 用**真实字节**验证（把自适应选出的规则统一后重算，格式与分组机制不变）：

| 样本 | 自适应原样 | 文本族→`TEXT_V3` | 二进制族→`BIN_V3` | 全部 CM→`BIN_V3` |
| --- | ---: | ---: | ---: | ---: |
| samba 4 MiB（382 区域） | 633,586 B | **609,117 B（−3.86%）** | 631,753 B（−0.29%） | 627,084 B（−1.03%） |
| samba 全文件（2,188 区域） | 3,848,465 B | **3,772,523 B（−1.97%）** | 3,831,787 B（−0.43%） | **3,734,398 B（−2.96%）** |
| mozilla 全文件（5,580 区域） | 14,308,932 B | +8.07% | +4.63% | — |

- 对 `samba` 这种"同族 CM 被拆成 21 种 ID"的文件，**只做规则归一就省 2–4%**，且分组数从 23 降到 18，编码耗时反而降低。
- 对 `mozilla` 归一反而更差（+4.6%）：那里的碎片化是有意义的（不同区域确实需要不同变换），**不能一刀切**。这正好说明需要"先测量后统一"的局部决策。

### 3.3 采样选不中更强规则（>1 MiB 区域）

`chooseSpec()` 的所有全区复核分支都带 `seg.length <= 1024*1024`（PEEL 是 512 KiB）。超过 1 MiB 的区域**只凭 40 KB 采样定胜负**。实测：

| 文件 | 自适应选中 | 同族更强规则 | 差距 | 结论 |
| --- | --- | --- | --- | --- |
| sao (7.2 MB) | `TRANSPOSE-G3(28)` 51.72% | `BIN_V2(19)` 64.27% | 选中项好 24% | 选择正确 |
| x-ray (8.5 MB) | `WIDE-16(31)` 43.89% | `CM-BIN(5)` 44.47% | 选中项好 1.3% | 选择正确 |
| nci (33.5 MB) | `CM-BIN3(24)` 5.15% | `CM-TEXT3(23)` **4.96%** | **选错 3.8%** | 应改 |
| osdb (10.1 MB) | `CM-BIN(5)` 24.61% | `BIN_V3(24)` **24.27%** | **选错 1.4%** | 应改 |

`sao`/`x-ray` 说明宽行、转置这些**规则本身很强**；`nci`/`osdb` 说明**大区域的采样判断会出错**，而 `nci` 那一次恰好就是"输给 zstd"的那一次。

### 3.4 STORE 区域：不是问题

`mozilla` 有 28 个 `STORE` 区域，占原始 3.62%（1.85 MB）、占容器 13.0%。用 xz 单独压这 1.85 MB 只能到 **97.7%**——这些字节确实近乎随机，**理论收益仅 0.3% 容器体积**。`samba`/`ooffice` 在 4–6 MiB 切片上根本没有 STORE。**不要在这个方向投入。**

### 3.5 头部开销：也不是问题

`dickens` 2 MiB 切成 1 / 2 / 8 / 16 / 64 个同规则区域，容器分别为 512,795 / 512,797 / 512,815 / 512,839 / 512,983 B——64 个区域只多 188 B（+0.04%）。`mozilla` 的 15,839 B 头部相对 14.3 MB 仅 0.11%。**"区域多所以头部大"是伪问题**，真正代价是 §3.2 的冷启动。

## 4. 性能诊断（当前最严重的产品级问题）

### 4.1 阶段拆分（`probe-timeline`，只依据 `onStage` 回调）

| 文件 | 总计 | 分析 | 候选试探 | 锚点统一 | 最终编码 |
| --- | ---: | ---: | ---: | ---: | ---: |
| xml | 75.5 s | 1.0 s (1%) | **36.7 s (49%)** | **22.9 s (30%)** | 14.9 s (20%) |
| dickens | 44.5 s | 2.1 s | 0.4 s | 0 | **42.0 s (94%)** |
| reymont | 117.8 s | 1.3 s | 7.0 s | 0 | **109.5 s (93%)** |
| ooffice | 198.4 s | 1.4 s | **170.2 s (86%)** | 0 | 26.8 s |
| samba | 299.5 s | 3.9 s | **202.1 s (67%)** | 3.1 s | 90.4 s |

三类耗时结构完全不同，**必须分开优化**：

1. **单一规则的文件**（dickens / reymont / webster / nci / sao / x-ray）：93–94% 时间在**最终编码一遍**，无从优化，只能改模型或并行。
2. **多候选多区域的文件**（ooffice / samba）：**86% / 67% 在候选试探**（`ooffice` 213 区域 × 15 候选 × 1–3 窗口 × 40 KB）。
3. **xml 型**：试探 49% + **锚点统一 30%**。这一阶段对每组 `ANCHOR_FOLD/SUB_ANCHOR/SUB_ANCHOR_V3` 做 **6 次完整 `encodeTerrainGroup`**（3 种 id × 2 种 mode），对 55% 的文本区域全量编码 6 遍。

### 4.2 CM 内核本身：9 上下文就是 546 ns/bit

`probe-bitrate`（`dickens` 前 1 MiB）：

| 配置 | 字节 | 速率 | ns/bit |
| --- | ---: | ---: | ---: |
| `o1`（2 上下文） | 448,357 (42.76%) | 1437 KB/s | 85 |
| `text` legacy（7 上下文） | 255,703 (24.39%) | 252 KB/s | 484 |
| `text` v13（9 上下文） | 249,325 (23.78%) | 224 KB/s | 546 |
| `bin` v13（9 上下文） | 261,114 (24.90%) | 237 KB/s | 515 |

即 **v13 的九上下文比 legacy 七上下文慢 13%，只换来 2.5% 的压缩率**。这是 v13 的既成事实，但意味着**任何"多试几个候选"的优化都会直接乘上 546 ns/bit 的成本**——试探阶段必须靠预筛选而不是多编码。

### 4.3 吞吐与 64 MiB 预算

- 全语料 202 MiB / 2491 s ≈ **81 KB/s**（编码）、**269 KB/s**（解码）。
- 最差单文件：`mozilla` 51 MiB → **1246 s（21 分钟）**；`samba` 21.6 MiB → 338 s；`ooffice` 6.2 MiB → 210 s（34 KB/s，区域多候选多）。
- 按 34–81 KB/s 外推，**64 MiB 单文件需要 13–32 分钟**，而 UI 只写"大文件可能耗时较久"。
- 峰值内存 8.7 KiB/输入 KiB（`mozilla` 470 MiB / 51 MiB）；64 MiB 约 600–900 MiB，叠加 `decompress` 验证副本与主线程拷贝后可能 2–3 倍。
- **进度与取消**：Worker 无取消通道，长任务只能靠关标签页。

### 4.4 解码

- `webster` 41.5 MiB 解码 **199.8 s**，几乎等于编码（186.6 s），因为退化成单一大 CM 流。
- 解码是顺序算术解码，**单流无法并行**；但 `buildPlanGroups` 天然分组，多分组可以并行解码，`STORE`/`FILL`/`RLE` 也可直通。
- UI 为了"逐字节校验"在 Worker 内**再完整解码一遍**，等于把解码耗时翻倍计入用户等待。

## 6. 安全 / 健壮性

- **容器变异**（`probe-fuzz` 900 轮）：532 次抛出明确错误（"不是有效的 UCZ 容器"/"无效的区域长度"/"无效的规则字典"…），368 次仍解出自洽结果，最慢 7.5 ms，**无挂死、无越界写**。
- **解压炸弹**：`decompress()` 读到头部立刻 `new Uint8Array(n)`，**无上限**。10 字节伪造容器声明 64 MiB / 512 MiB / 1 GiB 时会先完成分配再因截断报错（2–4 ms）；1 TiB 直接 `Array buffer allocation failed`。本地演示可接受；**一旦开放"上传 .ucz 还原"，必须加与 `MAX_INPUT_BYTES` 同量级的检查**。
- **小输入膨胀**：`1 B → 13 B`、`64 B → 65 B`（头部 12–14 B 固定）。语义无损，但 UI 显示"1300%"会误导；建议 <4 KiB 输入直接给"不压缩更小"的提示。

## 7. 改进优先级

### P0 — 只改控制流，不动格式、不改字节（1 周内）

1. **缓存 `encodePlanTranspose` 的中间产物**：`legacy = encodeGroupedTranspose(parts, s)` 与 `v3 = encodeGroupedTranspose(parts, s, undefined, undefined, true)` 各算一次，`TRANSPOSE_2D` 复用 legacy，禁止重复编码。**实测可省该路径 53.6% 时间，字节不变。**
2. **锚点统一阶段先做低成本筛选**：先比较 `ANCHOR_FOLD` 与 `SUB_ANCHOR` 的采样结果，只对前 2 名做完整编码（当前是无条件 6 遍）。`xml` 可省约 20 s / 75 s。
3. **提高全区复核覆盖面**：对 >1 MiB 区域，把采样前 3 名做一次全区复核（或对 `CM-*` 同族候选只保留采样最优 + 次优）。直接收益：`nci` −3.8%、`osdb` −1.4%。
4. **规则归一的局部决策**：仅对"同 cls、同族 CM、相邻或同分组"的区域尝试统一，**用真实编码比较后再替换**（§3.2 已证明 `samba` 可 −2~−4%，而 `mozilla` 一刀切会 +4.6%，所以必须测）。

### P1 — 需要动结构（1 个月）

5. **拆分 `codec.ts`**：容器格式 / 候选生成 / 选择器 / 编码分发 / 解码分发 五个模块，`codec.ts` 只留公共 API。这是后续所有改动的前置条件。
6. **加 CI**：`tsc --noEmit` + `npm run test:codec` + `npm run build` 三 job，PR 必过。
7. **基准门槛**：§2.1 已固化为 `scripts/diag/baseline.json`；用 `node scripts/diag/check-baseline.mjs <bench-one 结果>` 比对，回退 >0.5% 即退出码 1。可直接接进 CI。
8. **候选预筛选**：试探前用 O0/熵估计淘汰明显不可能的候选（`ooffice` 86% 时间在试探）。

### P2 — 需要专门投入

9. **攻 `mozilla` 型数据**（唯一显著输给 xz 的形态）：方向是"小区域延迟合并 / 分组先验"，而不是继续加规则。
10. **并行**：分组级并行编码（Worker 池）+ 分组级并行解码；`STORE`/`FILL`/`RLE` 直通。
11. **64 MiB 预算**：UI 给出预计时间（按区域数 × 候选数线性外推），并提供"快速模式"（跳过次级候选 + 跳过全区复核）。

## 8. 附录：复现命令

```sh
cd universal-adaptive-compression-system
npm ci

# 正确性
npx tsc --noEmit
npm run test:codec            # codec + worker，约 140 s
npm run build

# 全语料（12 个 Silesia 文件，约 40 分钟）
scripts/diag/run-corpus.sh /path/to/silesia /tmp/corpus-results.jsonl

# 单文件全量诊断（区域构成 / 耗时 / 内存 / zstd / brotli / 单一 CM）
node scripts/diag/run.mjs bench-one /path/to/file --no-single

# 地形分析（很快，看区域数与分类构成）
node scripts/diag/run.mjs probe-analyze /path/to/file

# 阶段耗时拆分
node scripts/diag/run.mjs probe-timeline /path/to/file

# CM 内核速率（ns/bit）与上下文数的关系
node scripts/diag/run.mjs probe-bitrate

# 转置分组的重复编码量化
node scripts/diag/run.mjs probe-transpose-cost /path/to/file 8

# 规则归一的价值（samba 4 MiB：633,586 B → 609,117 B）
node scripts/diag/run.mjs probe-unify /path/to/file 4

# 采样选错规则的上限（sao / x-ray / nci / osdb）
node scripts/diag/run.mjs probe-ceiling /path/to/file

# 区域数量对头部的影响
node scripts/diag/run.mjs probe-header

# 与固化的基线比对（bench-one 的 JSON 输出作为输入）
node scripts/diag/run.mjs bench-one /path/to/samba > /tmp/samba.json
node scripts/diag/check-baseline.mjs /tmp/samba.json        # 回退 >0.5% 退出码 1

# 健壮性
node scripts/diag/run.mjs probe-fuzz 300
node scripts/diag/run.mjs probe-bomb
node scripts/diag/run.mjs probe-regions
node scripts/diag/run.mjs probe-tiny
```

外部对照：`zstd -19` / `Brotli 5` 由 `bench-one` 内置（Node 22 `zlib.zstdCompressSync` / `brotliCompressSync`）；`xz -6` 用系统命令 `xz -6 -c <file> | wc -c` 单独测得。

**注意**：`scripts/diag/` 不参与 `tsc`（`tsconfig.json` 只 include `src`）与 `vite build`，可安全保留。

### 已知测量噪声

- `probe-timeline` 把 `pct >= 15` 的第一个事件当作分析结束，`xml` 的 `analyze()` 实测约 0.92–1.0 s，表中取 1.0 s。
- 所有耗时为单次运行、单线程、2 vCPU 共享环境下的观察值，**不是统计基准**。（`probe-cold` 在 `xml` 上连续三遍编码 14.9/15.0/14.8 s，稳定在 ±1%，故同机同版本内的相对比较是可靠的。）
- `mozilla` 的解码 198 s 与编码 1246 s 均为单次观察，用于说明量级而非精确基准。
