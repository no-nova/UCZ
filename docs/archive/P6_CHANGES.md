## 二、P6-2：双路细粒度混洗器（核心）

### 做法

主权重 `weightsAlt` 只有 24 组（`bit × 匹配状态`），看不到"前一个字节是什么类别"。新增第二套
辅权重 `weights2`：**64 组 × 8 bit × 10 路 = 5,120 个 int32（约 20 KB）**，**初始值 0**，
因此初始预测与 P5 **完全一致**，只是在其上叠加一个学习到的修正项。

索引：

```
wbase1 = (bit*3 + mstate) * N            // 原有主权重，未动
wbase2 = ((mctx2 << 3) | bit) * N        // 新增辅权重
dot    = Σ weights[wbase1+i]*in[i] + Σ weights2[wbase2+i]*in[i]
```

`mctx2` 按 profile 分三套（每组 6 位）：

| profile | mctx2 |
|---|---|
| text | `(charClass8(b1)<<3) \| ((c0&3)<<1) \| (mlen>0)` |
| bin | `((pos&3)<<4) \| (binClass4(b1)<<2) \| ((b1===b2)<<1) \| (mlen>0)`（`pos&3` = 4 字节对齐相位） |
| res / res2d / o0 | `(magClass8(b1)<<3) \| (magClass4(b2)<<1) \| (b1===b2)` |

学习：主权重的步长不变（`err*8 >> 16`），辅权重半速（`err2 = ((y<<12)-pr)*2`，`lr2=2`）。

### 学习率扫描（1 MiB 切片，`probe-mixer`）

|---|---:|---:|---:|---:|

| webster | 193,198 | **192,806 (−0.20%)** | 192,907 | 193,238 |

`lr2=2` 在 6/6 上最好（`lr2=8` 甚至在大文件上反转），锁定 2。

## 三、P6-1：a2 的适用范围——按实测修正为"保持 P5"

原计划把 `a2Eligible` 改成 `profile !== 'res2d'`，理由是 P5 一刀切后全量反涨
mozilla +1,509 / samba +175 / ooffice +38 = **+1,722 B**。沙箱端到端实测发现 `'res'` 是**双向**的：

* mozilla / samba / ooffice 的窄步长残差（`DELTA_V3` s=2、`STRIDE4_DELTA`、`XOR_V3`、
  `SUB_ANCHOR_V3`）：a2 正收益，合计 +1,722 B；
* **x-ray**：a2 负收益。`xray2m` 切片 a2 开 **882,701** / 关 **881,756**（−0.11%），整份 x-ray
  P4 3,669,156 / P5 3,664,677，即 **4,479 B**。改完之后沙箱实测 x-ray 立刻回到 3,669,156。

合计 = +1,722 − 4,479 = **净亏 2,757 B**，直接违反"12/12 不得回退"。

根因：x-ray 的 `WIDE_GRAD(s=1)` 经 `dualProfile` 映射成 `profile='res', s=2, r=1`，
与 mozilla 的 `DELTA_V3`（同样是 `res`, s=2）**在 CM 层完全同形**，光看 `(profile, s)`
区分不出来。试过的替代判据 `res && s >= 8` 无效（x-ray 走的是 s=2）。

> 结论：本轮保持 `a2Eligible = text || bin`。要拿到那 1,722 B，需要把 `spec.id` 一路传进
> a2 判定（`WIDE_GRAD` 永远关 a2，其余 `'res'` 开），这是下一轮的小改动，已记录。

单测同步锁死：`text` / `bin` 上 a2 必须生效，`res2d` **和** `res` 上必须与"关掉 a2"逐字节相同。

## 四、P6-3：两项内核改造——已实现，实测净负，默认关闭

**(a) bin 的 4 字节步长上下文**：`H[8]` 由 `(b1,b2,pos&3)+b4+b5` 换成 `+b4+b8`
（`match3Tuning.binCtx8`）。

**(b) v15 断续匹配恢复**：匹配被单字节差异打断后记 `lastDist = pos - mptr`，
12 个字节边界内若 `buf[pos-1] === buf[pos-1-lastDist]` 就 `mptr = pos-lastDist, mlen = 2`
（`match3Tuning.gapResume`）。

`probe-match3`（v15 内核，相对基线）：

| 文件 | 1 MiB ctx8 | 1 MiB gap | 2 MiB ctx8 | 2 MiB gap |
|---|---:|---:|---:|---:|
| mozilla | −0.01% | 0 | −0.01% | 0 |
| samba | −0.11% | +0.02% | −0.03% | +0.02% |
| osdb | +0.01% | −0.11% | +0.02% | −0.05% |
| ooffice | +0.07% | +0.02% | +0.06% | +0.02% |
| dickens / webster | 0 | +0.02% | — | — |

四个 bin 文件的 2 MiB 净和接近 0 甚至为负，而且 (a) 会改变共享的 `H[8]`，污染双流里那条
v13 基线（`base == v13` 的断言当场失败）。按"净胜才合入"的标准，两者**默认关闭**，代码保留
（带完整实测注释），换语料可一键复核。

## 五、P6-4：sao 破冰（3,750,902 → 3,748,341）

### 诊断（`probe-sao` / `probe-sao3` / `probe-sao4`）

1. 分段：**1 段**，规则 `id=10`（**v12 的 `TRANSPOSE_GROUP`**，步长 28，标签显示 "TRANSPOSE-G3"），
   容器 `ver=13`。
2. 因为整份 ≤ `MAX_SUB_CHUNK`（8 MiB），它走的是 `encodePlanTranspose` 那一支，
   **`chooseGroupV15` 从来没被调用过**（打印 `__V15_STATS` 一直是空的）——
   v15 内核在这类数据上是彻头彻尾的死代码。这就是"sao 五轮不动"的真正原因。
3. 即便补上调用，`id=10` 也**不在** `V15_PROFILES` 里，`chooseGroupV15` 第一行就 return false。
4. 28 字节记录按列拆开：**14 列（0–4、8–13）是纯噪声**（逐列 CM 把 37,449 B 编码成 37,486 B，
   完全不压缩）；列 7、15 是常数；真正可压的只有 5、6、14、16–27。
5. 逐列独立 CM 之和 **651,018** > 一条拼接 CM **659,123** > 实际分组载荷 **544,521**（1 MiB 切片）
   —— 说明"逐列隔离/清模型"是**错误方向**：分组编码已经在吃跨列冗余，隔离反而丢掉它。
   sao 的理论地板约 50%（一半的列是均匀噪声），当前 51.69%，剩余空间只有 ~1.5%。

### 修法（零新增 Codec ID）

1. `V15_PROFILES` 加入 `ID.TRANSPOSE_GROUP`，转置组在 ≤8 MiB 那一支里补上 v15 择优。
2. 转置组 ≥1 MiB 时再比一个 **V3 布局 + v15** 的候选（`id 10 → 30`）：sao 上 id 10 + v15 只省
   12 B，而 V3 布局 + v15 省 2,562 B。
3. **转置 + v15 内层一律不用 a2、也不用辅混洗**（`transposeInnerSuppress`）。
   全文件 7.25 MB 实测：

   | 配置 | 字节 |
   |---|---:|
   | v13（基线） | 3,750,881 |
   | v15 + a2 + 混洗 | 3,750,867 |
   | v15 无 a2 + 混洗 | 3,749,615 |
   | **v15 无 a2 无混洗** | **3,748,319** |

   这是**结构性**规则（spec 属转置族 + 内核是 v15），编解码两侧各自推导，不需要在比特流里
   加标记位，也不碰 v13。

### 结果

`sao` = **3,748,341 B（51.69%）**，`ver 15`，`verified: true`，enc 105.6 s / dec 16.1 s。
代价：转置大组要多跑一遍整段编码（sao +45 s）；≤1 MiB 的组不触发，其它文件几乎无感。
