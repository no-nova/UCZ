# UCZ v18：分组尺寸定档与23位表

> P10历史协议。P11已采用独立[v19](UCZ_V19.md)，新增24位档与mht4分档；本文的mht4=20只适用于旧v18。

## 格式决策

P10 经用户明确确认采用新版本 **18**。v17 的 `0x02` 原为全局 text-a2-off，`0x04` 原为匹配表扩展，不能在 v17 内改成新含义。v18 使用新的位编号；解码入口先校验版本再选择解释，未知版本直接拒绝。实现保留 v1–v17 的独立读取分支，但不让旧格式限制 v18 的新语义。

```
55 43 5a 12 <modelFlags:u8> <rawLen:varint> <segmentCount:varint>
<groupCount:varint> <规则字典 / 段长 / 分组位图 / 载荷>
```

`12` 是十六进制版本18。字典形状不变：`r | 0x8000` 表示该组确实采用 v15 内核，`r | 0x4000` 表示 WORD-PRE；不占合法行宽8192的 `0x2000`。没有实际新语义的最终载荷仍使用适用的 v7–v15，不无故增加配置字节。

## v18 配置位（不是v17的定义）

| 位 | 导出常量 | 含义 |
|---|---|---|
| `0x01` | `V18_FLAG_TEXT_A2_OFF` | 全局 text a2 关闭 |
| `0x02` | `V18_FLAG_BIG_TABLE_22` | 被选中载荷实际使用22位 CM 表 |
| `0x04` | `V18_FLAG_TABLE_23` | 被选中载荷实际使用23位 CM 表 |
| `0x08` | `V18_FLAG_MATCH_21` | 被选中载荷实际使用21位匹配表 |
| `0x10` | `V18_FLAG_MATCH_22` | 被选中载荷实际使用22位 mht8 |
| `0x20` | `V18_FLAG_RES_A2_OFF` | res a2 关闭 |
| `0x40` | `V18_FLAG_WORD_PRE_A2_OFF` | 仅 WORD-PRE text a2 关闭 |
| `0x80` | `V18_FLAG_UNSCOPED` | 历史诊断的全局21/22、match20/21模式；默认绝不设置 |

组的 flags 取最终序列化子载荷的并集，容器再对最终组取并集。23位是该类表的最高档：一条23位流不用再同时声称自己使用22位；不同组分别用22/23时可同时有两位。匹配表独立记录，避免把未分配的 mht8 说成已使用。

`0x01` 优先于 `0x40`。默认仍是 raw-text a2开启、WORD-PRE text a2关闭、res开启；原有按规则抑制的限制继续生效。

诊断 `largeOnly=false` 只支持 CM上限21/22、match20/21，不允许全局23/22；v18拒绝 `0x80` 与 `0x04`/`0x10` 的冲突组合。不要拿诊断模式冒充默认分档。

## 尺寸语义

默认 `modelTuning = { maxTableBits: 23, matchTableBits: 22, largeOnly: true }`。

| 完整编码组 / 独立块的原始字节数 | CM 上限 | mht8 上限（仅存在该模型时） | mht4 上限 |
|---|---:|---:|---:|
| `<512 KiB` | 21 | 20 | 20 |
| `[512 KiB, 4 MiB)` | 22 | 21 | 20 |
| `>=4 MiB` | 23 | 22 | 20 |

- 普通共享规则组按整个组；WORD-PRE完整编码也继承原始组长度，不再因词元坍缩缩短而掉档。
- `TRANSPOSE_GROUP_V3` 实际经过 `encodeGroupedTranspose` / `decodeGroupedTranspose`。最终列组继承完整转置组长度，不按被切薄的列数据判断门槛。
- SUB 按现有最多8 MiB的独立块，子通道继承该块长度，不跨块、不借整个文件长度。
- 独立二维转置按每个区域的大小；PEEL终端规则按其实际子区域。作用域在编解码相应边界上对称建立，并用 `finally` 恢复。
- 小组保留原来的自适应长度公式；大组的最终 CM 通道可按完整组分配到对应档位。真实 CM 输入/输出缓冲区仍只按该子流长度分配。
- 变换如果膨胀 CM 流，不会把 `<4 MiB` 的原始组错误升至23位。空 CM 流不继承大尺寸。

**探针与完整载荷严格分开：** TG列布局搜索、SUB模式搜索、二维转置筛选及 WORD-PRE前缀筛选均不继承大组作用域。否则16 KiB窗口就可能反复分配288 MiB表，抵消优化并增加内存风险。

### sao路径的可证明部分

标准 sao 为7,251,944 B，步长28时单列258,998 B。P9按实际子流长度定档，该单列低于512 KiB，因此仍为21位。v18最终列组用7,251,944 B作尺寸预算，该路径可真实达到23位、相应v15/bin通道的mht8达到22位。

这是代码路径与无分配策略检查，**不是本轮运行完整 sao 的测量**。本轮未读取其真实列分组计划，不声称每个旧列组都曾是21位，也不把预计15–25 KB写成已实现收益。完整输出中的 `modelFlags & 0x04`、`codecs[].modelFlags` 可供本地确认实际选中载荷用了23位表。

## 内核与并行

- TG的v15入口现在只编码真正的v15候选，不再内部返回 `min(base,v15)` 却由外层统一标 `0x8000`；外层已有base，负责严格完整成本比较。升级为ID30时始终使用对应V3布局。
- 通用v15候选直接编码alt；保留双流探针做字节等价验证，不生成/误用不可当作旧v13的 `dual.base`。
- ByteWriter/封装继续只继承序列化载荷的flags；worker通过显式数值传回，缓存键绑定规则、原始顺序/边界、配置及选择策略。丢弃候选不污染头部。
- 默认线程数按每worker **512 MiB**预算估算（9上下文23位表本身288 MiB，另有匹配表、输入与GC）。这是估算，不是RSS硬上限。显式 `UCZ_THREADS` 仍优先，不暗改用户的8线程设置。

## 验证边界

P10新增测试的实际输入最大48 KiB。512 KiB/4 MiB及sao列尺寸用纯策略算术检查；另用128 B raw-CM输入和显式大组作用域检查实际表分配及v18配置作用域下的raw-CM对称解码。它不是一份128 B或虚构4 MiB的UCZ容器测量。真实worker小输入检查合批、缓存、字节一致性和失败回退；既有完整codec套件另作为最终门禁执行。
