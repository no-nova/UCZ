### 1.3 三个必须声明的限制

1. **段级实验是"每段独立编码"**，而线上 `buildPlanGroups` 会把同规则段合成一个共享模型的分组。
   因此 §3 的 A/B/C 是**相对诊断信号**（谁比谁好、差多少、差在哪个族），不是全量字节的预言。
   §3.4 已用 1 MiB 尺度复核了结论中唯一的大项（mozilla 转置），结论保持。
2. **神谕 C 不是全空间**：它只覆盖 18 个核心族 + 锚点/剥离族（实际见 §3.2 名单）。
   C 与"候选池"取并集后再比较，才能保证 B−C ≥ 0 的分解成立。
3. 任务书里出现的 `XOR_V3`、`SUB_PEEL`、`O0_V3`、`TRANSPOSE_V3`、`MIN_SEG = 4096`、`MAX_SUB_CHUNK = 10 MiB`
   **在代码里都不存在**（`XOR` 只在注释里出现过一次）。实际对应物：`TRANSPOSE_V3 → TRANSPOSE_GROUP_V3(30)`、
   `SUB_PEEL → PEEL(14)`、`O0_V3 → O0(3)`（v3 内核只覆盖 text/bin/res/res2d）、`MAX_SUB_CHUNK = 8 MiB`、
   短段下限实际是 **2 个 512 B 块（1 KiB）**（`analyze.ts:179`，另加 `<16 B` 的 `cleanTinySeams`）。
   这类"术语与代码不一致"本身就是风险：它让人以为测过的东西其实没测。

## 2. 环节二：分块、特征与 32 个方法的数学本质

### 2.1 为什么 webster / dickens / nci / osdb / sao 会合成 1 段？因为它们真的是 1 段

`analyze()` 每个 512 B 块算零阶熵/差分熵/文本率/4-gram 重复率等，然后做**多数滤波 + `mergeShortRuns(2)`（2 块=1 KiB）**。
下表第 3、4 列是"滤波前/滤波后的标签 run 数"（探针用与源码完全相同的阈值重算）。

| 文件 | 字节 | 512 B 块 | 滤波前 runs | 滤波后 runs | 压缩比 runs | 最终段 | ≥4 KiB 段 | 段长度中位 | 全局步长 | 段内块熵标准差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| xml | 5,345,280 | 10,440 | 44 | 38 | 0.864 | 38 | 19 | 5,948 | 6 | 0.214 |

| ooffice | 6,152,192 | 12,016 | 2,427 | 836 | 0.344 | 838 | 303 | 2,560 | 2 | 0.263 |
| mr | 9,970,564 | 19,474 | 12,840 | 62 | **0.005** | 64 | 54 | 91,687 | 2 | 0.821 |

判读：

* **webster / dickens / nci / sao**：整份文件在一个 512 B 网格上一个标签都没有变过；段内块熵标准差 0.07–0.48 bit。
  "合成为 1 段"是**正确**结果，不是滤波抹平。给它们强行切小段只会付冷启动成本（§5.1：webster 每切一次 ~8.6 KB）。
* **osdb**：14 runs → 2 runs，1.5 runs/MiB；`segMedian = 10,070,836`。段内块熵标准差 **0.050 bit**——比文本还平。
  也就是说 **osdb 内部没有 512 B 尺度上的"页/记录"子结构**（下一小节还有多尺度证据）。
* **真正被 512 网格 + 多数滤波抹平的是 mr**：12,840 runs → 62 runs（**0.5%**），
  和 **mozilla**（20,942 → 8,895，42%）、**x-ray**（25%）、**ooffice**（34%）。
  这些文件里"地形标签"本身就在大量抖动，说明 512 B 网格落在**结构边界的两侧**。
  但注意：mozilla 的最终 9,035 段与 ooffice 的 838 段都**远多于** filter 之后保留的 run 数，
  因为 refine/clean 只是合并了同类紧邻块；真实损失不在"段数"上，而在"候选池"（§3）。

### 2.2 六类地形到底在区分什么？——它本质是 4 个标量的阈值级联

各类的实测特征区间（`text` = 合法 UTF-8/ASCII 占比，`hi` = 高位字节占比）：

| 文件 | 类分布（按字节） |
| --- | --- |
| webster / dickens / nci | text 100.0% |
| sao | binary 100.0% |
| osdb | repeat 99.9%, binary 0.1% |
| reymont | text 99.4%, noise 0.6% |
| xml | text 99.5%, repeat 0.34%, fill 0.11% |
| mr | repeat 84.6%, smooth 14.3%, fill 1.0% |
| ooffice | binary 71.1%, repeat 20.7%, smooth 7.5%, fill 0.5%, text 0.1% |
| x-ray | smooth 86.2%, binary 12.2%, repeat 1.6% |
| samba | text 85.8%, repeat 7.2%, noise 5.5%, binary 1.1%, smooth 0.2% |
| mozilla | repeat 39.0%, binary 21.7%, smooth 20.1%, text 10.2%, noise 6.6%, fill 2.4% |

* `text` 类要求 `text > 0.93 且 h0 < 7.0`（`analyze.ts:154`）：**这就是一个 ASCII 率阈值**。
  webster/dickens 的块 `text ∈ [0.933, 1.0]`，恰好压线通过。
* `osdb` 的块 `text ∈ [0.736, 0.893]`、`h0 = 6.28`，因此**永远进不了 `text`**；
  它落进 `repeat` 只是因为 `rep = 0.705 > 0.6`。同一份数据若字典/阈值微调就会跳到 `binary`——
  而实测 §3 显示 osdb 上 `CM-BIN`/`CM-TEXT3`/`TRANS` 的差距 <1%，**标签错不错完全不重要**。
* `sao` 全文件 `text ∈ [0.344, 0.613]`，被判 `binary`，但它的最优规则是 `TRANSPOSE-G(步长 28)`——
  分类器**看不到 28 这个维度**（`bestS` 只在 `smooth/repeat/binary` 分支里作为 "lag 探测的种子" 使用）。
* 与"仅用 `text > 0.5` 的决策桩"对比：全块一致率 mozilla 0.309 / sao 0.812 / osdb 0.000（桩说 text，实际 repeat）；
  但**只在 text∪binary 块上**一致率 0.968–1.0。即：六类在地形真正混杂的文件上几乎没有超出"ASCII 率"的信息量。

**结论（环节二 Q2）**：分类器不是"地形模型"，是 `(text, h0, hd, rep)` 的四维标量分区；
它缺的维度恰好是**周期/字段宽/相位**（sao=28、samba=38、mozilla=4、nci=3、mr=2 这些真步长全靠
`detectRecordStride` 的独立启发式，而它的返回值只用来"加候选"，从不参与分类与分块）。
特征"够不够"的实测答案是：**对"选恒等 vs CM"够用，对"选几何变换"不够用**——后者靠试压。

### 2.3 固定 512 网格 vs 真实结构边界：损失 ≤0.2%，不是瓶颈

对每个文件取中部 128 KiB，把窗口起点相对结构边界平移 0..s−1 字节，用同一规则真实重编码：

| 文件 | 步长 s | 规则 | 最优点 | 最差点 | 极差 | 极差 % |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| xml | 6 | DELTA_V3 | 19,061 | 19,099 | 38 B | 0.199% |
| xml | 6 | BIN_V3 | 4,176 | 4,179 | 3 B | 0.072% |
| samba | 38 | DELTA_V3 | 32,718 | 32,757 | 39 B | 0.119% |
| mozilla | 4 | DELTA_V3 | 69,328 | 69,396 | 68 B | 0.098% |
| sao | 28 | DELTA_V3 | 84,157 | 84,230 | 73 B | 0.087% |
| nci | 3 | DELTA_V3 | 17,003 | 17,011 | 8 B | 0.047% |
| ooffice | 2 | DELTA_V3 | 96,406 | 96,447 | 41 B | 0.043% |
| mr / x-ray | 2 | 两者 | — | — | ≤13 B | ≤0.039% |

再把同样多的片（8×32 KiB）分别按 **512 网格**与**步长倍数**切分后独立编码：

| 文件 | BIN_V3 差 | DELTA_V3 差 |
| --- | ---: | ---: |
| reymont | 12 B | 170 B |
| sao | 236 B | 339 B |
| samba | 1 B | 73 B |
| nci | 4 B | 78 B |
| mr / osdb / x-ray / ooffice | 0 B | 0 B |

想靠"精确结构边界"再挖几十 KB，必须在**换掉变换族**之后才成立（例如转置对相位敏感，
但转置的收益本身是 10–20%，见 §3.3）。

### 2.4 32 个 Codec ID：14 个共用同一个核，17 个在语料上一次都没被选中

按数学算子归类（源码 `codec.ts:24-63` + `encodeSpec:145`）：

| 类别 | ID | 数学本质 | 与其他 ID 的重合 |
| --- | --- | --- | --- |
| 逃生/退化 | 0 STORE, 1 FILL, 2 RLE | 恒等/常量/游程，**不用模型** | 唯一不可替代的是 STORE（熵≈8 时的兜底） |
| 纯统计（算术编码） | 3 O0, 4 TEXT, 5 BIN, 18 TEXT2, 19 BIN2, 20 BCJ2, 23 TEXT3, 24 BIN3, 25 BCJ3 | **同一个比特级 CM**：19 个"特征槽"取不同上下文集合；v1=4–8 上下文、v2=更宽/词模型、v3=9 上下文+相位稀疏 | 18/23、19/24、20/25 只是"同 profile 的三代"；`BCJ*` = BCJ 变换 + 上面的 bin 核 |
| 一维线性残差 | 6 DELTA, 27 DELTA3, 8 D16, 17 MICRO | `x[i]-x[i-s]`（D16 在 16 位上、MICRO 是**现场拟合**的量化线性预测） | DELTA/DELTA3 同算子不同核；D16(s=1,order=1) 就是 16 位一阶差分（≈ DELTA(s=2)，只是残差按 16 位模打包） |
| 二维预测 | 7 GRAD, 21 GRAD2, 26 GRAD3, 31 WIDE_GRAD | MED（LOCO-I）梯度预测，`s`=像素跨度、`r`=行跨度 | GRAD* 三连同算子；WIDE_GRAD = MED 与 D16 二选一 |
| 转置/列分流 | 9 TRANSPOSE, 10 TRANSPOSE-G, 22 TRANSPOSE-2D, 30 TRANSPOSE-G3 | 按记录宽 s 做矩阵转置；逐列/逐组编码 | **四种布局是同一族**，22/30 只是"几何 vs 传统 vs v13 增强"的选择器 |
| 锚点/语法 | 12 ANCHOR, 13 ANCHOR_FOLD | 以某字节为行分隔做**列折叠** | 13 是 12 的无损变长版本 |
| 子通道 | 15 SUB-TRANSPOSE, 28 SUB-TRANSPOSE3, 16 SUB-ANCHOR, 29 SUB-ANCHOR3 | 转置/锚点后再按"同源列"分模态独立建模 | 与 9/13 同数据布局，只是模型分离方式不同 |
| 递归 | 14 PEEL | 对每列**再跑一次地形扫描** | 唯一真正的"递归"结构 |
| 位置相关 | 11 BCJ | E8/E9 rel32 → 绝对地址 | 只有可执行代码段需要 |

**真实命中率**（12 个 1 MiB 切片，`p8-census`）：**17/32 个 ID 一次都没被选中**
（STORE, RLE, O0, GRAD-2D, TRANSPOSE-G(10), BCJ-x86(11), ANCHOR-ALIGN(12), ANCHOR-FOLD(13), PEEL(14),
MICRO(17), CM-TEXT2(18), CM-BIN2(19), GRAD-2D2(21), BCJ3(25), SUB-ANCHOR3(29), WIDE-16(31)）。
被选中的 15 个里，`24 CM-BIN3` 覆盖 3.07 MB / 12 MB 原始（120 段）、`20 BCJ2` 1.02 MB、
`16 SUB-ANCHOR` 1.34 MB、`26 GRAD-2D3` 0.98 MB、`28 SUB-TRANSPOSE3` 0.76 MB、`8 LIN-16` 0.62 MB。

**两个"结构性缺失"**（这次审计最重要的一条代码事实）：

```
候选池从不包含 30:TRANSPOSE-G3   →  "从未进入任何候选池的 ID：22:TRANSPOSE-2D, 30:TRANSPOSE-G3"
候选池从不包含 22:TRANSPOSE-2D   →  它们只能由 10/9 被选中后，在分组编码时"升级"得到
```

`sao` 之所以用上 `30`，是因为候选池先选了 `10:TRANSPOSE-G`，再走 `encodePlanTranspose` 的升级；
**mozilla 上候选池连 `10` 都没选中**（`10` 在 12 个切片里只进过 7 次候选池、0 次被选），于是 `30` 永远不可达。
§3 会证明：mozilla 的赢家恰好就是 `30`。

### 2.5 为什么线性差分/预测打不过恒等？——用桶归因量化"破坏匹配模型"

对同一份 1 MiB 数据分别编码 恒等（`BIN_V3/TEXT_V3`，profile=bin/text）与 `DELTA_V3(s=2)` 的残差（profile=res），
用 `p8-attrib` 的桶归因看**比特都花在哪**：

| 文件 | 恒等输出 | bpb | 桶0 长匹配（字节%/比特%） | 差分(s=2) 输出 | 桶0 占比 |
| --- | ---: | ---: | --- | ---: | --- |
| webster | 202,230 | 1.543 | **94.16% / 87.76%** | 338,249 (**+67%**) | **0% / 0%** |

机制一目了然：**CM 的主引擎是 4/8 字节哈希的匹配模型**（文本上 94–96% 的字节、88–94% 的比特都由它承担，
平均 1.4–1.9 bit/字节）。字节级差分把"可匹配的字节串"变成"与邻居相关的残差"，
残差流的 4-gram 不再重复，**匹配覆盖率归零**；而差分换来的好处只有"残差幅值更集中"，
这点好处被 `res` profile 的 8 个上下文（比 text/bin 少 1 个、且没有词/结构相位）抵消。

**为什么 mr 是例外**：它是 16 位采样（音频），`deltaFwd(s=2)` 恰好等于 16 位一阶差分，残差仍有强匹配
（`mlen` 命中在残差上依旧成立），所以 `DELTA_V3(2)` 与 `GRAD-2D3` 都能赢恒等 16%（§3.3）。
这解释了为什么"差分有时赢、有时输"不是玄学，而是**"差分是否保留可匹配结构"**。

这也直接回答了任务书里的"哪些方法其实是重合的、能不能配合"：
`DELTA/GRAD/D16/MICRO` 与"恒等 + CM"的**不重合部分只有"残差分布更尖"**，
而它们与匹配模型的冲突是**零和**的：变换越彻底，匹配越没用。当前内核的混合器无法用"两路并行"弥补，
因为二者共享同一个 `mht`（变换后位置语义变了）。**这是 §7 建议里要写清楚的一条设计结论。**

## 4. 环节四：采样、断裂与经验惩罚系数

### 4.1 `sampleWindows` 的真实机制（先纠正一个误解）

任务书认为"从段首/段中/段尾各切 13.6 KB **拼成**一个 40 KB 数组，制造两个相位硬断裂"。
读源码（`codec.ts:1019-1028`）与实测都是：**三个窗口各自独立编码、把字节数相加**，
数组从不被拼接，因此**不存在人为拼接造成的相位断裂**。真实的偏差是另一件事：

* 每个窗口只有 `budget/3` 字节。`sampleLimit` 在 `n > 5 MiB` 时被压到
  `min(16000, max(4096, 8 MiB / 段数))`（`codec.ts:2080`），于是**窗口长度只有 1.3–5.3 KB**：

| 文件 | `analyze` 段数 | sampleLimit | 每窗字节 |
| --- | ---: | ---: | ---: |
| webster / dickens / nci / osdb / sao / mr / xml / reymont | 1–64 | 16,000 | **5,333** |
| ooffice | 838 | 10,010 | 3,336 |
| x-ray | 1,719 | 4,879 | 1,626 |
| **samba** | 2,247 | **4,096** | **1,365** |
| **mozilla** | 9,035 | **4,096** | **1,365** |

  1.3–5.3 KB 远小于 `O4/O6` 与匹配表收敛所需（§5 的冷启动实验显示 256 KiB 块的冷启动损失约 8–11 KB，
  即前 256 KiB 都在"热身"）。**但实测这几乎没有代价**：

| 采样法 | top-1 命中 | Regret 合计 | Kendall τ（vs 真实排序） |
| --- | --- | ---: | --- |
| 现状（3 窗 × ~1.3–5.3 KB） | 100/100/100/100/75/25/25/63 % | **34 B** | 0.933–0.991 |
| 单窗 40 KB 连续 | 100/100/100/100/63/25/25/63 % | **54 B** | 0.933–0.991 |

  原因：大多数段的候选之间差 5–50 倍（samba 的 64 KiB 段最优 631 B、恒等 2,586 B），
  采样再短也能分出量级；真正接近的候选只在同族内部（例：`CM-BIN3` vs `CM-BIN2`），而同一段的同族差距本来就 <1%。

### 4.2 经验惩罚系数：52 段里改错 6 段，净亏 646 B，0 次改对

`adj()` 的硬编码系数（`codec.ts:1256`）：`MICRO ×1.03`、`SUB_* ×1.006`、`PEEL ×1.04`、
`ANCHOR ×1.024/1.05`、`BCJ ×1.024`、`text 区的 BIN ×1.03`、其余 `×1.003`。

用同一批采样估计分别按"有惩罚/无惩罚"排序，再用真实整段编码结算：

| 指标 | 值 |
| --- | --- |
| 两种排序选中同一规则 | 44 / 50 段 |
| 有惩罚更好 | **0 段** |
| 有惩罚更差 | **6 段** |
| 净字节差 | **+646 B（+0.067%）** |
| 最差 4 例 | ooffice：`BCJ2`(31,367) 覆盖 `BCJ-x86`(31,204) → **+163 B**；同类 161 B / 153 B / 152 B |
| 其余 2 例 | xml：`ANCHOR-GRID` 覆盖 `SUB-ANCHOR3` → +12 B；又一段 ooffice `BCJ2` → +5 B |
| 惩罚"救回"的最差候选 | 无 |

也就是说：`BCJ` 被 `×1.024` 罚、`BCJ2` 不罚，于是选了更差的 v2 核——**惩罚系数的方向与真实代价无关，
它只是把"我们不信任的规则"整体拉高 0.3–5%**。而真实容器头部代价是多少？

* 一个额外分组的头部：`id/s/r/payloadLen` 四个 varint ≈ **7 B**（`planHeader:1851`）；
* 一个额外段的长度 varint ≈ **2–3 B**；组归属位图 ≈ 1 bit/段。
* 即：**每个"多出来的段+组"真实成本 ≈ 10–12 B**。
  而 `×1.003` 作用在 64 KiB 段上 = **197 B**，作用在 1 MiB 段上 = **3,146 B**——
  比真实头部代价大 **20–300 倍**。`×1.024`（BCJ）在 64 KiB 段上是 1,573 B。

**结论**：惩罚系数应当整体删除，改用**精确的 `headerBits/sampleRatio`**（把 `planHeader` 的 varint 长度
按候选是否新增分组算出来，再加 ~1 bit 位图），量级是 10–100 B 而不是 200–3,000 B。
这一条不改变任何比特流格式，且实测立刻省 646 B / 3.3 MB（≈0.07%）。

### 4.3 能否用解析熵替代试压？不能（实测相关系数 0.149）

对 208 组（段 × 差分步长 1/2/4/bestS）同时计算：一阶条件熵 `h1(x)`、`h1(残差)` 与真实 CM 字节数。

| 指标 | 值 |
| --- | --- |
| 参与的 (段, 差分) 组合 | 208 |
| `h0` 认为"差分更好" | 24 |
| `h1` 认为"差分更好" | 38 |
| 真实"差分更好" | 14 |
| **`h1` 说差分更好但真实更差** | **24 / 38 = 63%** |
| 平均"熵预测增益" | −16.6%（即平均预测差分变差） |
| 平均"真实增益" | −61.8% |
| 预测增益 vs 真实增益 的相关系数 | **0.149** |

最典型的"熵骗人"样本：`mr`（16 位音频）某段 `delta(s=1)` 让一阶熵从 **1.86 降到 1.08**（预测 **省 42%**），
真实 CM 字节数却是 **+3.5%**（匹配模型失效，§2.5）。

**为什么必然如此**：CM 的输出是 `mix(9 个上下文, 匹配状态, APM 校准)`，
它对"分布形状"不敏感、对"可预测的结构重复"极敏感；零阶/一阶熵只看**边缘分布**，
完全看不到 `mlen`（匹配覆盖）与 `count`（上下文成熟度）。
用低阶熵做候选排序，等于用"字母频率"预测"LZ 能不能找到长匹配"。

**替代方案的最低试压代价**：不必 40 KB×3 窗，**单窗 8 KB 连续 + 强制包含 ≥2 个完整记录**即可保持
top-1（实测 3 窗 Regret 合计 34 B、单窗 40 KB 合计 54 B，两者只差 20 B）。
真正需要"试压"的只有**同族内部**（`BIN3` vs `BIN2`、`DELTA3(s)` 的不同 s），
跨族（恒等 vs 转置 vs 差分）差距是数量级，解析特征或 1 KB 试压就能判断。

## 5. 环节五：分组编码、冷启动与"内部潜力上限"

### 5.1 先纠正前提：`MAX_SUB_CHUNK` 不切纯 CM 分组

```
codec.ts:391  const MAX_SUB_CHUNK = 8*1024*1024
codec.ts:392  function encodeSubGroups(parts, sp) { ... 每满 8 MiB 开一条新的列模型 ... }   // 只有 SUB_* 族
codec.ts:886  encodeTerrainGroupImpl → 对 TEXT_V3/BIN_V3/DELTA_V3/… 一律 encodeCM(joined …)  // 整组一条流
```

所以"每 8 MB 把 18 MB 的 CM 表清零重来"**在纯 CM 分组上并不存在**：webster 41 MB 就是**一条** 41 MB 的 CM 流。
真正会因 8 MiB 触发重置的是 `SUB_TRANSPOSE/SUB_ANCHOR`（samba/xml 会用到），
以及**每一个不同 spec 的分组**（每个 `PlanGroup` = 一个全新 `Model` = 空表）。

那么 8 MiB 这个数字的真实影响是什么？两条，都是"间接"的：

1. **候选门槛**：`SUB_*` 只在 `seg.length ≤ MAX_SUB_CHUNK` 时生成（`codec.ts:1155,1228`），
   `TRANSPOSE_GROUP` 的分组升级只在 `seg.rawLen ≤ MAX_SUB_CHUNK` 时允许；
   超过 8 MiB 的段直接失去这些族 —— 对 41 MB 的 webster 无所谓（它不想要），
   对 51 MB 的 mozilla **意味着整文件级转置永远不可能被考虑**。
2. **模型表位宽被夹在 2²¹**：`coder.ts:506`

```ts
const bits = Math.min(21, Math.max(10, Math.ceil(Math.log2(Math.max(n,1)*8)) + 1))
```

   只要数据 ≥ 256 KiB，`bits` 就**恒为 21**（2 M 槽/上下文）。41 MB 的 webster 与 256 KiB 的片段用同样多的槽位：
   41 MB / 4 字节 4-gram ≈ 1,000 万个不同上下文抢 2 M 个槽位。这不是"清零"，是"表被压扁"，
   后果与冷启动同类（互相污染），但**无法靠"续传热表"解决**。

| mozilla | 1,936,998 | +13,668 (0.7%) | **+5,928 (0.3%)** |

三点：

* **每切一次 8 MiB 边界的代价是 13.7–40.4 KB**（不是几十字节）。对 41 MB 的 webster，
  如果按 8 MiB 硬切 5 块，代价约 **4×40 KB ≈ 160 KB（占其 UCZ 6.9 MB 的 2.3%）**。
  我们**没有**这么做，这正是"合成为 1 组"的价值。
* **mozilla 例外**：4×2 MiB 比 2×4 MiB 更接近一条流（+5,928 < +13,668）。
  说明在异构数据上，**"更小更纯的组"能反过来赚回冷启动成本**——这动摇了"越大越省"的直觉，
  也说明"分组粒度"应该由实测（`consolidateOrphans` 那类严格择优）决定，而不是常数阈值。
* 冷启动损失与块大小**近似线性**（表学到的东西按字节数摊销），因此红线可以写成：
  `切一个边界 ≈ 0.6–1.5% × 该块字节数`（文本/数据库取上界，图像取下界）。

### 5.4 为什么文本文件"看起来很努力其实没什么可做"？

webster / dickens 的归因非常干脆：**94–96% 的字节、88–94% 的比特都在长匹配桶里**，
平均 1.4–1.9 bit/字节；`O4`+`O6` 只覆盖 0.07–0.08% 的字节；冷上下文只占 2.5–3.5% 的字节但吃掉 3.8–7.5% 的比特。
换句话说：**这两份 41 MB / 10 MB 的英文文本，其压缩几乎完全由"LZ 匹配 + 匹配状态混合器"完成**，
9 个上下文表、双 APM、辅混洗、词模型加起来只贡献个位数百分比的比特。
这解释了 P5/P6/P7 在 webster/dickens/reymont/nci 上"怎么调都是 0.01%"：
**这些文件的剩余熵不在我们调参的地方**（它要么在匹配模型里，要么在对不齐的长距重复里）。

反过来，`sao`/`ooffice`/`mozilla` 的碰撞桶占 16.6–50.1% 的比特——
但它们同时也是"转置/BCJ 能赢 9–20%"的文件，说明**它们的结构信息本来就没被 CM 的逐比特上下文抓住**，
抓住它们的是**几何变换**（把定长字段排到同一列），而不是更大的表。

## 6. 我们凭什么判定"潜力到头了"？——三条内部判据（不引用任何世界纪录）

**判据 A：神谕差（Oracle Gap）**＝在同一段划分下，暴力神谕 C 与现状 A 的真实字节差。
它度量"规则选择与候选生成"还剩多少。本次：**A−C = 14,121 B / 916,226 B = 1.54%**，
且 95% 集中在 1 个文件 mozilla 的 1 个族。**当 A−C < 0.1% 时，规则层就可以宣布收敛。**

**判据 B：冷启动下限**＝按当前模型，把一个分组切成 n 块的必然代价
（实测 0.6–1.5% × 每块字节数）。它给出"分组粒度"的最优边界：
`期望的结构纯度收益 > 切分冷启动代价` 才值得切。本次 mozilla 的 8 MiB 实验（切 4×2 MiB 反而更好）
说明这个判据必须用**实测**而不是常数阈值来评估。

**判据 C：桶归因上界**＝把比特按"是谁预测的"分开后，看**最弱的那一桶**还有多少空间：
* 桶0（匹配）已经 1.4–1.9 b/B，且匹配模型是 LZ 级——提升要动 `mht` 结构与最小匹配长度；
* 桶2/3/4（冷/碰撞/薄）合计吃掉 6–60% 的比特，但它们要么是**真随机**（osdb 的冷上下文 5.06 b/B 与
  干净命中 5.30 b/B 差不多，说明"学到的上下文"并没有比"没学过"好多少 —— **数据本身接近条件无关**），
  要么是**结构没对齐**（sao/ooffice 的碰撞桶 = 转置该上场的地方）。
* 因此**"还剩多少"可以从桶的形状直接读出**：若某文件的桶2 的 b/B 已经接近桶1，
  说明再加高阶上下文/更大表都是白费（osdb 就是这样）；若桶3 远高于桶0，
  说明应该换"几何"而不是"统计"（sao/ooffice/mozilla）。

**判据 D（可选）：参数灵敏度**＝把"无参数可调"的旋钮（表位宽、`minLen`、`limit`、`slt`）
推到算力/内存允许的上界，看收益是否已经 <0.5%。本次表位宽 +2 位只有 0.14–0.77%，
说明**"CM 参数调优"这条路的上限就在 1% 以内**——这才是"到头"的可证伪定义，
而不是"离 cmix 还差多少"。

## 7. 卡点排序与建议（按"字节/改动量"排序，全部不触碰比特流格式）

### 关于"我们是不是只是把现有内容拼接在一起"

本次实测的答案是：**不是，但结构性创新的落点错了**。
* 现有流水线的收益分解（按机制，而非按 ID）：**匹配模型**（文本 88–94% 的比特）、
  **几何变换**（sao −18.4%、mr −16.4%、ooffice BCJ −9.2%、xml 锚点 −12.3%）、**统计上下文**（0.1–17.6% 的比特）。
* 真正**新**的东西只有"几何变换的选择 + 分组归一"。而 P5/P6/P7 的微调全部发生在
  "统计上下文"这一侧——**那正是实测占比最小、且已被匹配模型掩盖的一侧**。
* 因此下一步的正确方向不是新启发式、不是调系数，而是：
  **把"几何"这一侧的候选空间打开（P9-1/P9-4），并用严格择优保证单调不劣**；
  再加一条**结构级**的重构（把匹配模型与残差模型解耦，允许"转置后的列"并行匹配，而不是二选一），
  那才是能把 sao/ooffice/mozilla 这类文件从 5.12/3.41/2.35 bpb 再往下压的地方。
