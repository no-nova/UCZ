## 0. 结论先行

### 0.1 一句话根因

> **你卡在环节五，不在环节二/三/四。**
> 在 12 个文件 × 512 KiB 切片（合计 6,291,456 B）的暴力神谕实验里：
> - 环节四（采样筛选）的总损失 = **6,431 B（0.339 %）**
> - 环节三（地形分类 + 候选池封锁）的总损失 = **2,546 B（0.134 %）**
> - 而环节五（模型内核本身）里，**光是上下文哈希碰撞**在 4 MiB 切片上就吃掉
>   **1,765 ~ 32,075 B（0.21 % ~ 2.29 %）**（表宽 2²¹ → 2²³，4 MiB 切片，8 个文件全测），
>   并且随文件变大而恶化（表宽被硬钉在 2²¹）。

## 1. 环节二审计：分块拆分、特征提取、32 个方法的数学本质

### 1.1 “为什么大文件只剩 1~2 个段”——不是平滑干的，是分类器干的

`probe-p8-seg` 用新增的 `analyzeTuning` 开关把“3 点多数滤波 + 短游程吸收”整体关掉，
对同一份数据跑两遍 `analyze()`，逐块比对标签（2 MiB 切片）：

| 文件 | 512 块数 | 段数（未平滑→线上） | 被平滑改标签的块 | 占比 |
|---|---|---|---|---|
| dickens | 4,096 | 1 → 1 | 0 | 0 % |
| nci | 4,096 | 1 → 1 | 0 | 0 % |
| webster | 4,096 | 1 → 1 | 0 | 0 % |
| reymont | 4,096 | 1 → 1 | 0 | 0 % |
| sao | 4,096 | 1 → 1 | 0 | 0 % |
| xml | 4,096 | 20 → 15 | 3 | **0.07 %** |
| osdb | 4,096 | 14 → 2 | 6 | **0.15 %** |
| mozilla | 4,096 | 219 → 80 | 78 | 1.90 % |
| samba | 4,096 | 455 → 235 | 111 | 2.71 % |
| ooffice | 4,096 | 725 → 245 | 271 | 6.62 % |
| x-ray | 4,096 | 2,274 → 648 | 943 | 23.02 % |
| mr | 4,096 | 2,352 → 10 | 1,176 | **28.71 %** |
| **合计** | **49,152** | – | **2,588** | **5.27 %** |

**读数**：12 个文件里 **5 个（dickens/nci/webster/reymont/sao）的原始 512 网格分类本来就只有
1 个游程**——平滑根本没有参与。
osdb 从 14 → 2 看着吓人，但只改了 **6 个块（3 KB）**：那是 6 个 512 B 的孤岛，
吸收它们只影响 0.15 % 的字节。真正把 osdb 变成 1 个段的是**分类器本身**：
它的 `terrainRawPct` 就是 `repeat 99.2 % / binary 0.8 %`——2 MB 里 99.2 % 的块拿到了同一个标签。

> **结论**：512 网格 + 多数滤波**不是**瓶颈（12 个文件合计只改 5.27 % 的块标签，
> 其中 5 个文件改 0 个块）。瓶颈是 6 类硬标签把 2 MB 判成一类。
> 这一点被 §1.6 的粒度阶梯实验独立证实。

### 1.2 “8 个特征”其实只有 2 个进了决策

`analyze()` 为每个 512 B 块算 8 个特征（`h0 / hd / text / rep / uniq / hi / zero / mad`），
但下游只消费两个派生标量：

```
codec.ts:1135  export function candidatesFor(seg, cls, bestS, lagSample)
```

- `cls`：6 选 1 的互斥标签；
- `bestS`：块级 `bestS` 的众数投票。

证据（可核对）：`analysis.blocks` 在 `codec.ts` 里只出现在 2187 与 2346 行，
且只读 `bl.end - bl.start`（块长，用于成本图）。`codec.ts` 里所有 `.h0/.hd/.rep`
都来自 `segFeatures(lagSample)`——**在采样上重新算的 3 个数**，与 `analyze` 的块特征无关。
PCA 输出只喂 UI（`viz.ts`）。

> **结论**：环节二的“结构化”= 把 8 维特征压成 1 个 6 类标签 + 1 个整数步长。
> 8 个特征里 6 个（`text/uniq/hi/zero/mad/rep`）在决策上是**纯装饰**。

### 1.3 32 个 Codec ID 的数学本质：只有 3 个正交轴

把 `ID` 表按算子本质归类，32 个 ID 实际是 **8 个可逆变换 × 4 代熵编码内核** 的叉积：

| 前端变换 T | 数学算子 | 对应 ID |
|---|---|---|
| 恒等 | `x` | STORE(0) FILL(1) RLE(2) O0(3) TEXT(4) BIN(5) TEXT_V2(18) BIN_V2(19) **TEXT_V3(23) BIN_V3(24)** |
| 1D 差分 | `x[i] − x[i−s]` | DELTA(6) DELTA_V3(27) |
| 2D MED | `x − median(左,上,左上)` | GRAD(7) GRAD_V2(21) GRAD_V3(26) |
| 16 位差分 | 16 bit 小端一阶差分 | D16(8) WIDE_GRAD(31, s=1) |
| 宽行 2D MED | 行距 r 的 MED | WIDE_GRAD(31, s=2) |
| x86 rel32 重写 | `E8/E9 + rel32 + 绝对地址` | BCJ(11) BCJ_V2(20) BCJ_V3(25) |
| 列/列组重排 | 按步长 s 转置 | TRANSPOSE(9) TRANSPOSE_GROUP(10) TRANSPOSE_2D(22) TRANSPOSE_GROUP_V3(30) PEEL(14) SUB_TRANSPOSE(15) SUB_TRANSPOSE_V3(28) |
| 锚点重排 | 按锚点字节折行/聚列 | ANCHOR(12) ANCHOR_FOLD(13) SUB_ANCHOR(16) SUB_ANCHOR_V3(29) |
| 现场线性预测 | 5 参数岭回归种子 | MICRO(17) |

内核只有 4 代：`false`(v1) → `true`(v2) → `'v13'` → `'v15'`，
差别**只是上下文集合与校准层**（`coder.ts:467`：`nctx` = 7/8 → 9，v15 再加 APM+辅混洗+mht8）。

> 所以 `TEXT / TEXT_V2 / TEXT_V3` 不是三种方法，是**同一个算子的三代容器版本号**。
> 它们之间的“择优”本质是在选容器版本，不是在选变换。

### 1.4 命中率普查：10 / 32 个 ID 在真实语料上一次都没赢

`probe-p8-seg`，**12 个文件 × 2 MiB = 25,165,824 B、1,240 个区域决策**，
统计每个 ID“进过多少次候选池”与“最终胜出多少次”（完整表见 §6.4）：

| 分组 | ID | 进池 | 胜出 |
|---|---|---|---|
| **零命中（10 个）** | RLE、ANCHOR、ANCHOR_FOLD、O0、MICRO、GRAD、GRAD_V2、PEEL、WIDE_GRAD、SUB_TRANSPOSE_V3 | **2,893** | **0** |
| 近乎零命中 | BIN_V3（1,210 进池 / 1 胜）、BCJ（522/1）、SUB_ANCHOR（563/1）、TRANSPOSE_GROUP（18/1）、SUB_TRANSPOSE（71/3）、DELTA（640/6） | – | – |
| 真正的主力 | TRANSPOSE（985/538）、BCJ_V2（522/219）、BIN（1,210/115）、TEXT_V3（886/70）、DELTA_V3（322/67）、BIN_V2（1,210/50） | – | – |

**最刺眼的一条：`BIN_V3` 进池 1,210 次、只胜出 1 次（覆盖 0.26 % 字节），
而更老的 `BIN_V2` 胜出 50 次（覆盖 8.95 %）。**
同一 profile、同一 v13 内核、只多一个上下文，却系统性更差——
这不是“新的一定好”，是**第 9 个上下文在结构化二进制上抢梯度**（§4.5 的消融给了同向证据：
osdb 的 `a1` 值 7,143 B、`mixer2` 值 2,505 B，说明 osdb 对“多一层模型”异常敏感）。

> **成本核算**：这 10 个零命中 ID 在 12 个文件上被完整试压了 **2,893 次**，
> 每次都是一个真实的 `encodeSpec` 采样编码。它们对体积的贡献是 **0 字节**，
> 对编码时间的贡献是实打实的。这是环节二最确定、最安全的可回收项。

### 1.5 差分/预测变换为什么打不过恒等——机制实测

差分族（DELTA/GRAD/D16/MICRO）在文本/混合区几乎必输。机制是**双重打击**：

1. **破坏精确高阶上下文**：`H[2..5]` 是 `hh(b1,b2,b3,b4[,b5,b6])` 的**精确**哈希。
   原文里 `b1..b4` 是自然语言的 4-gram，重复率极高；差分后 `b1..b4` 变成残差序列的
   4-gram，几乎处处不同 → 高阶表退化成“每个上下文只见一次”。
2. **打断匹配模型**：`mht`/`mht8` 找的是**原文**的长重复串；差分把
   “完全相同的 32 字节”变成“完全相同的 32 个 0”，看起来更好，但只要重复块之间有
   1 字节差异，差分后就是**整段错位污染**，`mlen` 直接归零。

§4.3 的归因实测给了这两个机制的硬数字：samba 有 **93.38 %** 的字节落在 `mlen ≥ 4`
的长匹配里，osdb **78.54 %**，ooffice **67.91 %**。任何让 `mlen` 归零的变换，
等于把 2/3 以上的字节从“几乎免费”推回“高阶冷启动”。这就是差分族打不过恒等的根本原因，
**不是参数没调好**。

> 1~3 KB/512 KiB。真正该修的是**分组的代价没有被计入选规则的代价函数**（§3.3）。

## 2. 环节三审计：地形分类是否封锁了候选（暴力神谕实验）

### 2.1 实验设计

`probe-p8-oracle`，12 个文件各取 512 KiB，**完全相同的 `analyze` 段划分**下跑 7 种策略：

| 策略 | 规则来源 | 编码口径 |
|---|---|---|
| **A** 现状 | `compressAdaptive` 全流程 | 真实容器 |
| **A′** 现状第一阶段 | `chooseSpecSync`（采样 + 512 KB 复核） | `evaluatePlan` |
| **B** 去采样偏差 | `candidatesFor` 候选池，**每段整段真实编码**取最小 | `evaluatePlan` |
| **C** 全局暴力神谕 | **无视地形**，44 个核心变换族整段真实编码取最小 | `evaluatePlan` |
| **D** 纯恒等单段 | 整份切片一个段，TEXT_V3 / BIN_V3 取小 | `evaluatePlan` |
| **G / H** 恒等对照 | 同一 analyze 分段，全部强制 TEXT_V3 / BIN_V3 | `evaluatePlan` |
| **E** 无分组参照 | C 的逐段独立编码之和（不共享 CM、不含头部） | 直接求和 |
| **F** 粒度神谕 | 64 KiB 均匀网格 + C 的暴力选规则 | `evaluatePlan` |

`A′ − B` = 环节四损失；`B − C` = 环节三损失；`C − min(G,H,D)` = 空间变换的净贡献。

### 2.3 直接回答提问里的三问

**(1) `A′ − B`（环节四采样筛选损失）= 6,431 B / 0.339 %。**
但它的符号**不稳定**：reymont +4,854、mozilla +3,533、nci +1,373 是真损失，
osdb **−3,485**、xml −281、samba −144 是“采样反而更对”。
原因见 §3.2：整段独立编码的神谕**不知道分组会共享 CM**，它选出来的规则会把组打散。

**(2) `B − C`（环节三地形分类漏选损失）= 2,546 B / 0.134 %。**
12 个文件里 **8 个是 0**。只有 mozilla(1,057)、x-ray(1,279)、ooffice(237)、samba(−27) 非零。

> **判定：地形分类几乎没有封锁任何有价值的候选。**
> 六类地形确实很粗（§1.1 已证：osdb 99.2 % 的块拿到同一个标签），
> 但 P7-2 的 `featureCandidates` 已经把候选池的钥匙从 `cls` 手里拿走了——
> `candidatesFor` 里真正决定候选的是 `detectRecordStride / detectLagCandidates /
> detectAnchors / detectWide16Lag / segFeatures` 这五个**独立探测器**，
> `cls` 只剩下“要不要放 BCJ/ANCHOR”这种粗门禁。所以“分类不准”不再等于“候选被封锁”。

**(3) 暴力神谕 C 在 12 个文件里的 8 个上没有赢过纯恒等。**
`C − min(G,H,D)`（神谕 vs 该文件最好的恒等对照）：

| 神谕**更小**（变换必需） | 差 | 打平（差 0） | 神谕**更大** | 差 |
|---|---|---|---|---|
| sao | **−60,830** | dickens | osdb | **+7,905** |
| ooffice | **−25,683** | webster | samba | **+4,651** |
| x-ray | −921 | reymont | xml | **+2,502** |
| mr | **−6,779** | nci | mozilla | **+2,063** |

> 这就是提问里那个判断的**实测确认**：
> “如果连暴力神谕都只比纯 BIN_V3/TEXT_V3 小一点点，问题就不在环节三/四”。
> 实测比这更强——12 个文件里 **4 个神谕更大、4 个打平**，只有 4 个（sao/ooffice/x-ray/mr）神谕更小。
> 原因不是神谕算错了，
> 而是**逐段贪心 ≠ 分组最优**：每段独立最优的规则组合，会把共享 CM 组切碎，
> 每个新组都要重付一次冷启动 + 一份规则头。这条在 §3.3 量化。

## 3. 环节四审计：试压采样、窗口设计与经验系数

### 3.1 先纠正：全语料没有任何一个文件用到 40 KB 采样

`codec.ts:2089-2091`：

```ts
const sampleLimit = n > 5 * 1024 * 1024
  ? Math.min(16000, Math.max(4096, Math.floor(8 * 1024 * 1024 / Math.max(1, analysis.segs.length))))
  : SAMPLE           // SAMPLE = 40000，只在 n ≤ 5 MiB 时生效
```

代入 `baseline.json` 里的真实段数：

| 文件 | 大小 | 段数 | **实际 sampleLimit** |
|---|---|---|---|
| mozilla | 51.2 MB | 5,580 | **4,096 B** |
| samba | 21.6 MB | 2,188 | **4,096 B** |
| ooffice | 6.15 MB | 213 | 16,000 B |
| xml | 5.35 MB | 35 | 16,000 B |
| dickens / mr / osdb / x-ray / sao / nci / webster / reymont | 6.6~41.5 MB | 1~13 | 16,000 B |

再叠上 `codec.ts:1250`：`seg.length < 32 KiB` 的区域**只跑 1 个窗口**。
mozilla 平均段长 51.2 MB / 5,580 ≈ **9.6 KB**，所以 mozilla 的绝大多数区域是
**用一个 ≤ 4,096 B 的单窗口**去决定一条将作用于 51 MB 共享流的规则。

> **这是环节四真正的结构性缺陷，而且方向与直觉相反**：
> 采样预算 `8 MiB / 段数` 意味着**越碎的文件、每个决策拿到的证据越少**，
> 而恰恰是碎文件的决策会被 `mergePlanSegments` 合并进同一个大共享组，影响面最大。

### 3.2 “3 段拼接制造相位断裂”不成立，但“窗口太短”成立

`codec.ts:1250-1259` 的实际行为：

```ts
const windows = sampleWindows(seg, budget, candidateAlignment(sp, bestS), seg.length < 32 * 1024 ? 1 : 3)
let size = 0, sampled = 0
for (const {sample, start} of windows) {
  const encodedSize = encodeSpec(sample, sp, undefined, 0, base + start).length   // ← 每个窗口独立编码
  size += encodedSize                                                            // ← 只把字节数相加
  sampled += sample.length
}
```

- 窗口位置是 **25 % / 50 % / 75 %**（`codec.ts:1019`），不是段首/段中/段尾；
- 三个窗口**分别独立跑一遍 `encodeSpec`**，模型状态在每个窗口开头重置，**从不拼接**。
  所以“在 13.6 KB / 27.2 KB 处制造两个上下文硬断裂”这个机制**不存在**。

真正的缺陷是**每个窗口太短**：`budget/3` 在 mozilla 上是 **1,365 B**。
9 个上下文的高阶表 + 匹配表在 1.3 KB 上根本没热身完，
排出来的名次主要是“谁的冷启动便宜”，不是“谁在长流上更强”。

### 3.3 分组收益没有被计入选规则的代价函数（这才是 A′−B 符号乱跳的原因）

`E` = 逐段独立编码之和（不共享 CM、不含头部）；`C` = 同样规则但走真实分组：

| 文件 | C 神谕(plan) | E 无分组 | 分组净收益 | % |
|---|---|---|---|---|
| xml | 16,478 | 17,402 | 924 | 5.61 |
| dickens | 128,684 | 129,183 | 499 | 0.39 |
| ooffice | 196,141 | 240,588 | **44,447** | **22.66** |
| mr | 101,387 | 101,400 | 13 | 0.01 |
| osdb | 148,211 | 148,185 | −26 | −0.02 |
| x-ray | 230,094 | 240,534 | 10,440 | 4.54 |
| sao | 275,255 | 279,371 | 4,116 | 1.50 |
| reymont | 94,365 | 95,708 | 1,343 | 1.42 |
| nci | 28,330 | 31,049 | 2,719 | 9.60 |
| samba | 206,100 | 216,933 | 10,833 | 5.26 |
| webster | 101,106 | 101,622 | 516 | 0.51 |
| mozilla | 367,620 | 374,629 | 7,009 | 1.91 |
| **合计** | **1,893,771** | **1,976,604** | **82,833** | **4.37** |

**共享 CM 分组值 82,833 B（4.37 %）**，ooffice 上高达 22.66 %。
但 `chooseSpecImpl` 的目标函数是 **`encodeSpec(单段)` 的字节数**——
它完全不知道“我选的规则会不会把 5,580 个段的共享组打散”。

这就解释了 §2.2 里 `A′ − B` 的符号为什么乱跳：
- 在 **osdb** 上，采样选了 `BIN_V2`（能把两段并成一个组），整段神谕选了会分组的规则，
  于是**采样反而好 3,485 B**；
- 在 **reymont / nci / mozilla** 上，单段只有一个组、打散无从谈起，
  采样的短窗口欠拟合就暴露成真损失（+4,854 / +1,373 / +3,533 B）。

> **结论**：环节四的问题**不是“采样不准”，是“采样的目标函数与最终代价函数不同构”**。
> 修采样窗口只能拿回 0.34 %；把“分组后果”计入选择，理论上界是 §2.2 最后一列的**正向合计 19,477 B**
> （xml 1,157 + osdb 4,420 + x-ray 448 + reymont 4,854 + nci 1,373 + samba 1,989 + mozilla 5,236）。
> **注意这是上界不是实测增益**：本轮没有实现“分组感知选择器”，无法给出它的真实收益；
> 而且神谕 C 在 4 个文件上更大、4 个打平（§2.3(3)），说明“逐段最优”并不自动等于“整组最优”。

### 3.4 经验惩罚系数：实测影响（见 §3.5 表）

`codec.ts:1262-1266` 的系数全表（`chooseSpecImpl` 里的 `adj()`）：

### 3.5 采样保真度实测：三种窗口口径完全等价，解析熵完全不能用

`probe-p8-sample`：对 osdb / mozilla / webster / ooffice 的 512 KiB 切片
（共 **116 个真实区域决策**），把候选池里每个规则都用**整段真实编码**测出真值，
再和四种口径的排名对比：

| 口径 | top-1 命中 | 命中率 | 累计遗憾 | 平均遗憾 | 最大遗憾 | Spearman ρ |
|---|---|---|---|---|---|---|
| **pipeline**（线上 3 窗口） | 113/116 | **97.4 %** | **584 B** | 0.007 % | 0.40 % | **0.996** |
| w1-40k（单段连续 40 KB） | 113/116 | 97.4 % | 584 B | 0.007 % | 0.40 % | 0.997 |
| w3-40k（3 窗口，同预算） | 113/116 | 97.4 % | 584 B | 0.007 % | 0.40 % | 0.997 |
| **h0**（零阶解析熵排名） | 105/116 → 逐文件 1/2、15/49、15/50、74/116 | – | – | – | – | 明显更差 |
| **h1**（一阶解析熵排名） | 逐文件 1/2、11/49、11/50、64/116 | – | – | – | – | 明显更差 |

**三个硬结论**：

1. **窗口口径完全不重要**：3 窗口拼接、3 窗口独立、单段连续 40 KB 三种做法的
   top-1 命中数（113）、累计遗憾（584 B）、ρ（0.996/0.997）**一模一样**。
   “把窗口改成长连续流”这个优化方向**没有可回收的收益**。
2. **在 40 KB 预算下采样已经足够准**：97.4 % top-1、总遗憾 584 B / 0.007 %。
   所以环节四在**切片**上不是瓶颈——真正的问题是 §3.1 的预算公式：
   全量 mozilla / samba 上预算只有 **4,096 B**，不是这里的 40,000 B。
3. **解析熵不能替代试压**：零阶熵排名在 webster 上只有 **15/50** 命中
   （试压是 47/50），一阶只有 **11/50**。原因是 CM 的收益来自
   *9 个上下文的非线性混合 + 匹配模型*，而 H0/H1 是**线性泛函**，
   无法表达“这个变换让长匹配变长了”这种离散事件。
   > 提问里“能否用零阶/一阶解析熵直接替代试压”——**实测答案是不能，差 3 倍命中率。**

### 3.6 经验惩罚系数 A/B：净影响 ±400 B，不是瓶颈

用 `planTuning.neutralPenalties` 把 §3.4 的全部系数置 1，其余完全不变，
同一份切片跑 `evaluatePlan`：

| 文件 | 带系数 | 系数全 1 | 差 | 改变选择的段数 |
|---|---|---|---|---|
| osdb | 144,726 | 144,726 | 0 | 0 |
| mozilla | 372,210 | 372,577 | **系数省 367 B** | 4 |
| webster | 101,106 | 101,106 | 0 | 0 |
| ooffice | 196,768 | 196,378 | **系数亏 390 B** | **62** |

系数在 ooffice 上改变了 **62 个段**的选择，净效果只有 −390 B；在 mozilla 上反而是正收益。
> **判定：拍脑袋系数不是瓶颈。**换成“精确的容器头比特成本”最多拿回几百字节，
> 而且必须同时解决 §3.3 的分组代价问题，否则省下的会被打散的组吃回去。

## 4. 环节五审计：分组、冷启动、模型内核与“内部潜力上限”

### 4.1 先纠正：主力分组**从不**中途清零，`MAX_SUB_CHUNK` 只管子通道

`probe-p8-cold` 直接读 `compressAdaptive` 的分组清单（8 MiB 切片）：

| 文件 | 分组数 | 主力规则 | 主力组原始字节 | 该组是否触及 8 MiB 上限 |
|---|---|---|---|---|
| dickens | **1** | CM-TEXT3 | 8,388,608 | 否（连续编码，无中途清零） |
| webster | **1** | CM-TEXT3 | 8,388,608 | 否 |
| osdb | **1** | CM-BIN2 | 8,388,608 | 否 |
| nci | **1** | CM-TEXT3 | 8,388,608 | 否 |
| samba | **18** | CM-TEXT3 | 6,154,840 | 否——碎片化来自**规则切换**，不是 8 MiB 上限 |
| mozilla | **43** | CM-BIN2 | 2,046,001 | 否——同上 |

`buildPlanGroups`（`codec.ts:1523`）把**同规则的所有段**收进一个组，
`encodeTerrainGroupImpl`（`codec.ts:782`，通用分支 `codec.ts:845-866`）把它们拼成**一个缓冲区**、
`new` 一个 `Model`、一次 `encodeCM` 到底。`MAX_SUB_CHUNK = 8 MiB`（`codec.ts:391`）
只出现在 `encodeSubGroups`（`SUB_*` 子通道族）与若干候选门禁里。

> 所以“每达到 MAX_SUB_CHUNK 就把 18 MB 的 CM 表清零重来”**在主路径上不存在**。
> mozilla 51 MB 的主力组是一次连续的 51 MB CM。

### 4.2 但冷启动的代价是真实的，而且正是 samba 亏损的机制

同一探针把主力组的数据切成 K 块、每块独立冷启动编码，与连续编码对比（8 MiB）：

| 文件 | 组数 | 主力组原始字节 | 连续编码 | K=2（4 MiB×2） | K=4 | K=8 | 热身曲线 bits/B（首→尾） |
|---|---|---|---|---|---|---|---|
| dickens | **1** | 8,388,608 | 1,926,886 | **+25,504** | +68,522 | +129,669 | 2.1092 → 1.6189 |
| webster | **1** | 8,388,608 | 1,439,424 | **+36,697** | +78,499 | +136,268 | 1.7054 → **1.3771** |
| osdb | **1** | 8,388,608 | 2,043,986 | **+35,856** | +88,646 | +162,519 | 2.3381 → 1.9039 |
| nci | **1** | 8,388,608 | 444,469 | +7,214 | +17,502 | +31,282 | 0.4497 → 0.3818 |
| **samba** | **18** | 6,154,840 | 763,183 | **+36,754** | +121,644 | +160,939 | **1.4196 → 0.6817** |
| **mozilla** | **43** | 2,046,001 | 489,182 | +7,128 | +21,991 | +36,579 | 1.7834 → 2.3398 |

**一次冷启动 ≈ 7~37 KB**（与该组数据的可压性成正比：dickens/osdb/samba 每次 25~37 KB，
nci/mozilla 每次 7 KB）。热身曲线说明模型从 2.11 bit/B 收敛到 1.62 bit/B——
**每个组的前几百 KB 都在白交学费**；samba 的曲线跨度最大（1.4196 → 0.6817），
而它恰好被切成了 **18 个组**。

把这条和 §5 的整份文件对照放在一起，samba 的亏损机制就完全闭合了：
samba 有 **2,247 个 analyze 段**，每段只有 **4,096 B** 采样预算，
选出的规则把数据打散成多个组，每个组重付一次 20~30 KB 级别的冷启动。

### 4.3 内部交叉熵归因：钱到底花在哪几个字节上

`probe-p8-attrib`（`setAttribHook` 只读探针，4 MiB 切片，v13 内核）。
桶定义：桶1 `mlen ≥ 4`；桶2 无匹配但 4 阶槽 `count ≥ 2`；
桶2b 无匹配且 `count == 1`；桶3 无匹配且 `count == 0`。

| 文件 | 主力规则 | bits/B | 桶1 %字节 | 桶1 %比特 | 桶1 bit/B | 桶2 %字节 | 桶2 %比特 | **桶2 bit/B** | 哈希碰撞率 | 表放大到 2²³ 省下 |
|---|---|---|---|---|---|---|---|---|---|---|
| mozilla | BCJ3→bin | 6.175 | 24.31 | 2.34 | 0.593 | **69.53** | **89.90** | **7.984** | **64.36 %** | 7,015 B (0.22 %) |
| webster | CM-TEXT3 | 1.404 | **97.27** | **88.62** | 1.279 | 0.91 | 3.90 | 6.021 | 13.14 % | 15,691 B (**2.13 %**) |
| dickens | CM-TEXT3 | 1.869 | 97.98 | 93.86 | 1.790 | 0.64 | 1.99 | 5.855 | 17.07 % | 1.96 % |
| samba | CM-TEXT3 | 1.148 | 93.38 | 60.64 | 0.746 | 2.78 | 16.03 | 6.612 | 12.18 % | **2.29 %** |
| osdb | CM-BIN2 | 1.983 | 78.54 | 32.25 | 0.814 | 15.83 | **49.92** | 6.251 | 27.84 % | 1.51 % |
| ooffice | BCJ2→bin | 3.333 | 67.91 | 45.88 | 2.252 | 26.89 | 45.47 | 5.636 | 40.99 % | 1.84 % |
| mr | GRAD-2D3→res2d | 1.602 | **0.00** | 0.00 | – | **99.35** | **96.93** | 1.563 | 31.72 % | 0.34 % |
| sao | TRANSPOSE-G | 5.164 | 41.24 | 17.91 | 2.243 | 52.91 | **73.97** | **7.220** | **56.02 %** | 0.58 % |

**四条硬结论**：

1. **文本类文件 = 匹配模型**：webster 97.27 % 的字节在长匹配里，
   它们只花 1.279 bit/B，却占了 88.62 % 的输出。dickens/samba 同构。
   → 环节二的任何空间变换只要打断 `mlen`，就是直接砍掉 60~94 % 的输出效率（§1.5）。
2. **mozilla 的钱全花在“模型完全没预测力”的字节上**：
   69.53 % 的字节吃掉 **89.90 % 的比特**，单价 **7.984 bit/B**（上限是 8）。
   也就是说 CM 在这部分数据上**几乎等于随机猜**。
   sao 同病：52.91 % 的字节、73.97 % 的比特、7.220 bit/B。
   → **这才是“几十上百 KB 级损失”的所在**，而且它与分段/分类/采样**完全无关**。
3. **`res`/`res2d` profile 根本没有匹配模型**：`coder.ts:468`
   `this.useMatch = profile === 'text' || profile === 'bin'`。
   mr 整份 10 MB 走 GRAD-2D3（res2d），归因表里 **桶1 = 0.00 %**——
   一个长程匹配都没用上，全靠 99.35 % 的 4 阶命中硬撑。
   DELTA_V3 / GRAD_V3 / WIDE_GRAD / MICRO 全都吃这个亏。
4. **桶3（`count == 0`）恒为 0 是碰撞造成的假象**：碰撞率 12~64 % 意味着
   槽位里几乎总有别人的统计量，`count` 永远非 0。**冷上下文被伪装成了热上下文**，
   这既是桶3 读不出来的原因，也正是碰撞要吃掉字节的原因。

**m₃/N > 0.2 的 5 个文件（mozilla/sao/ooffice/osdb/x-ray），4 MiB 样本装不下它们的上下文空间**，
插入式熵估计已经饱和（mozilla 的 H3 甚至读出 0.423 bit/B 这种不可能的值，
Miller–Madow 一阶校正也救不回来）。所以“用经验熵当上限”这条路对这些文件**天然不通**。

**可用的内部判据是这三条的组合**（全部只依赖数据自身与编码器自身）：

1. **归因单价 vs 该文件可估的最低阶熵**（唯一严格的内部下界）。
   以 mozilla 为例：桶2 的 69.53 % 字节实际花 **7.984 bit/B**，
   而同一份数据**可靠可估**的 H1 = 7.085 bit/B（m₁/N = 0.016，估计可靠）。
   → 光是把这部分做到“一阶水平”就能省 `0.899 × 0.6953 = 0.625 bit/B`，
   即 **7.8 % 的输出**；做到 H2 = 4.899（m₂/N = 0.67，仅供参考）则空间更大。
   **这个差额不需要任何外部参照，就是内部可量化的剩余潜力。**
2. **消融阶梯的残差**（§4.5）：把每个部件都加上之后还剩多少。
   v15 全家桶之后 mozilla 仍有 6.175 bit/B，而它的 H0 = 7.703——
   模型只比“完全不看上下文”好 1.53 bit/B。**残差大 = 模型族到顶了，不是筛选没做好。**
3. **LZ 覆盖率**：能被前文 ≥L 字节串覆盖的比例。
   mozilla 只有 25.85 %（≥4）、6.63 %（≥64），x-ray 的 ≥8 覆盖率是 **0.04 %**。
   → 这两个文件的长程冗余**本来就少**，匹配模型再怎么调也榨不出东西；
   反观 nci（≥16 覆盖 76.63 %）与 xml（52.90 %），匹配模型才是主战场。

> **一句话判据**：
> **“潜力到头”= 归因表里高单价桶的 bit/B 已经逼近该文件可估的最低阶经验熵，
> 且消融阶梯上每个部件的边际收益都掉到 0.1 % 以下。**
> mozilla/sao 现在**远未到头**（7.98 / 7.22 bit/B vs H1 = 7.09 / 5.80）；
> dickens/webster **基本到头**（1.79 / 1.28 bit/B，且 97 %+ 字节已在长匹配里）。

| samba | 21,606,400 | **2,247** | 3,646,793 | TEXT_V3 **3,503,477** | **+143,316（流水线输 3.93 %）** | **纯亏损** |

| dickens | 10,192,446 | 1 | 2,319,296 | TEXT_V3 **2,318,397** | +899（0.039 %） | 基本等价 |
| osdb | 10,085,684 | 2 | 2,372,218 | BIN_V3 **2,372,216** | **+2** | **完全等价** |

| 文件 | TEXT_V3 | BIN_V3 | 取小 |
|---|---|---|---|
| samba | **3,503,477** | 3,643,567 | TEXT_V3 |
| webster | **6,763,509** | 7,076,401 | TEXT_V3 |
| dickens | **2,318,397** | 2,422,572 | TEXT_V3 |

三条读法：

1. **osdb：整条流水线（512 网格分析 → 6 类地形 → 21 个候选 → 采样试压 → 合并分组 → v15 择优）
   的最终产物，比“无脑一个 BIN_V3”大 2 个字节。**
   那 2 个字节正好是多出来的一个段长 varint。
   → 环节二/三/四在 osdb 上**净贡献 0 字节**，只是把平凡解重新推导了一遍。
2. **samba：流水线的 2,247 段 + 4,096 B 采样预算，让它比单一 TEXT_V3 大 143,316 B。**
   `probe-p8-cold` 给出了机制**方向**的直接证据：samba 的 8 MiB 切片被切成 **18 个组**，
   主力组的热身曲线从 **1.4196 bit/B 一路收敛到 0.6817 bit/B**——每个组都要重交一次这笔学费。
   实测的**边际**冷启动成本（主力组 6,154,840 B 切 K 块）：
   K=2 → **+36,754 B**、K=4 → +121,644 B（每刀 40,548）、K=8 → +160,939 B（每刀 22,991），
   即**每多切一刀值 23~41 KB，且切片越小越便宜**。
   17 次额外冷启动按这个上界算是 390~690 KB，**远大于**实测亏损 143,316 B——
   差额说明真实的 18 个碎片组远小于 8 MiB/18，冷启动成本随数据量递减。
   > **诚实标注**：本轮**没有**把 samba 的 143,316 B 逐项分解成“冷启动 + 选错规则 + 头部”，
   > 只能说机制方向一致、量级同阶。要做归因分解需要按组重放编码器，属下一轮工作。
3. **mozilla：流水线赢 639 KB（4.46 %）。** 所以不能一刀切地说“分段无用”——
   mozilla 有 9,035 个真实结构段，BCJ/差分/转置在上面确有收益（§2.2 里 ooffice/sao/mr 同理）。

> **这就是全链路审计的最终定位**：
> 损失不在“某个环节算错了”，而在**分段粒度 × 采样预算 × 分组冷启动**这三者的乘积上。
> 段数越多 → 每段采样预算越小（`8 MiB / 段数`）→ 选错规则的概率越高 →
> 组越碎 → 冷启动越多。samba 是这条链的极端，mozilla 是它的反面。

## 6. 综合结论与修复优先级

### 6.1 四个环节的最终判定

| 环节 | 判定 | 实测依据 |
|---|---|---|
| **二** 分块/特征/32 方法 | **大部分是假忙活**，但“段数”是真变量 | 多数滤波在 12 个文件上合计只改 **5.27 %** 的块标签（5 个文件改 0 个块，最坏 mr 28.71 %）；粒度切细到 4 KiB 后逐段独立之和恶化 77 %（webster），而 plan 体积几乎不随粒度变化（mozilla 全距 1,305 B）；32 个 ID 里 **10 个零命中**（RLE/ANCHOR/ANCHOR_FOLD/O0/MICRO/GRAD/GRAD_V2/PEEL/WIDE_GRAD/SUB_TRANSPOSE_V3），进池 2,893 次、胜出 0 次；8 个特征里 6 个不进决策 |
| **三** 地形分类/候选封锁 | **不是瓶颈** | `B − C` = 2,546 B / **0.134 %**，12 文件里 8 个是 0 |
| **四** 采样试压 | **目标函数错了，不是采样不准** | 40 KB 预算下 top-1 已 97.4 %、总遗憾 584 B；但全量 mozilla/samba 预算只有 **4,096 B**；窗口口径改动收益为 **0**；系数净影响 ±400 B |
| **五** 分组/模型内核 | **主战场** | 哈希碰撞 0.21~2.29 %（4 MiB 上 1,765~32,075 B，8 文件合计 122,038 B / 1.03 %，且随 n 恶化）；mozilla 89.9 % 的比特花在 7.984 bit/B 的字节上；`res/res2d` 无匹配模型；v15 全部增益 0.22~7 %；a2/gap 在多文件上净亏损 |

### 6.2 按“可回收字节 / 工作量”排序的修复清单

| 优先级 | 动作 | 预计收益 | 依据 |
|---|---|---|---|
| **P0** | **把采样预算从 `8 MiB / 段数` 改成与段数无关的下限**（例如每段至少 32~64 KB，或按段长比例分配） | samba 级别 **100 KB+**（§5 实测 143,316 B）；mozilla 512 KiB 切片上 **3,533 B** | §3.1、§5 |
| **P0** | **选规则时把“分组后果”计入代价**：候选比较用“该规则并入现有最大组后的整组字节”，而不是单段 `encodeSpec` | 上限 **19,477 B**（12 文件 512 KiB 上 `A − 最优恒等` 的**正向合计**：xml 1,157 + osdb 4,420 + x-ray 448 + reymont 4,854 + nci 1,373 + samba 1,989 + mozilla 5,236）。这是**可回收上限而非实测增益**——神谕 C 本身在 4 个文件上更大、4 个打平（§2.3(3)） | §2.2、§3.3 |
| **P1** | **上下文哈希表宽度与输入解耦**：`bits` 上限从 **2²¹** 提到 **2²³**（或按 `n` 自适应到 2²³~2²⁴），内存换体积 | 4 MiB 上 **1,765~32,075 B / 0.21 %~2.29 %**，8 文件合计 **122,038 B**，且随文件变大而变大 | §4.4 |
| **P1** | **给 `res`/`res2d` 加匹配模型**（`useMatch` 目前只允许 text/bin） | mr 整份 10 MB 现在 0 个长匹配 | §4.3 结论 3 |
| **P2** | 关掉/条件化 **a2** 与 **gapResume**（多文件净亏损） | 2 MiB 上 dickens 1,836 B、webster 1,923 B、mr 491 B；`gapResume` 在 8/10 文件上净亏 | §4.5 |
| **P2** | **删掉零命中 ID 的候选生成**（RLE/ANCHOR/ANCHOR_FOLD/O0/MICRO/GRAD/GRAD_V2/PEEL/WIDE_GRAD/SUB_TRANSPOSE_V3） | 不改体积，**大幅省编码时间**（12 文件 2 MiB 上它们进池 2,893 次、胜出 0 次） | §1.4 全量普查 |
| **P3** | 合并 `TEXT/TEXT_V2/TEXT_V3`、`BIN/BIN_V2/BIN_V3` 的**选择**（保留容器版本号，但不要在采样阶段比较它们） | 减少短样本上的“代际误判”（osdb 上 BIN_V2 胜 BIN_V3） | §1.3、§1.4 |

### 6.3 明确**不要**做的三件事（已被实测否证）

1. **不要改采样窗口的拼接方式**（3 窗口 vs 单窗口，收益实测为 0）。
2. **不要再堆地形类别**（六类→N 类）：`B − C` 只有 0.134 %，天花板就在那里。
3. **不要把段切得更细**：4 KiB 网格让逐段独立之和恶化 77 %（webster 101,622 → 180,116）。

### 1.3 三个必须声明的限制

1. **段级实验是"每段独立编码"**，而线上 `buildPlanGroups` 会把同规则段合成一个共享模型的分组。
   因此 §3 的 A/B/C 是**相对诊断信号**（谁比谁好、差多少、差在哪个族），不是全量字节的预言。
   §3.4 已用 1 MiB 尺度复核了结论中唯一的大项（mozilla 转置），结论保持。
2. **神谕 C 不是全空间**：它只覆盖 18 个核心族 + 锚点/剥离族（实际见 §3.2 名单）。
   C 与"候选池"取并集后再比较，才能保证 B−C ≥ 0 的分解成立。
3. 任务书里出现的 `XOR_V3`、`SUB_PEEL`、`O0_V3`、`TRANSPOSE_V3`、`MIN_SEG = 4096`、`MAX_SUB_CHUNK = 10 MiB`
   **在代码里都不存在**（`XOR` 只在注释里出现过一次）。实际对应物：`TRANSPOSE_V3 → TRANSPOSE_GROUP_V3(30)`、
   `SUB_PEEL → PEEL(14)`、`O0_V3 → O0(3)`（v3 内核只覆盖 text/bin/res/res2d）、`MAX_SUB_CHUNK = 8 MiB`、
   短段下限实际是 **2 个 512 B 块（1 KiB）**（`analyze.ts:179`，另加 `<16 B` 的 `cleanTinySeams`）。
   这类"术语与代码不一致"本身就是风险：它让人以为测过的东西其实没测。

### 2.2 六类地形到底在区分什么？——它本质是 4 个标量的阈值级联

各类的实测特征区间（`text` = 合法 UTF-8/ASCII 占比，`hi` = 高位字节占比）：

| 文件 | 类分布（按字节） |
| --- | --- |
| webster / dickens / nci | text 100.0% |
| sao | binary 100.0% |
| osdb | repeat 99.9%, binary 0.1% |
| reymont | text 99.4%, noise 0.6% |
| xml | text 99.5%, repeat 0.34%, fill 0.11% |
| mr | repeat 84.6%, smooth 14.3%, fill 1.0% |
| ooffice | binary 71.1%, repeat 20.7%, smooth 7.5%, fill 0.5%, text 0.1% |
| x-ray | smooth 86.2%, binary 12.2%, repeat 1.6% |
| samba | text 85.8%, repeat 7.2%, noise 5.5%, binary 1.1%, smooth 0.2% |
| mozilla | repeat 39.0%, binary 21.7%, smooth 20.1%, text 10.2%, noise 6.6%, fill 2.4% |

* `text` 类要求 `text > 0.93 且 h0 < 7.0`（`analyze.ts:154`）：**这就是一个 ASCII 率阈值**。
  webster/dickens 的块 `text ∈ [0.933, 1.0]`，恰好压线通过。
* `osdb` 的块 `text ∈ [0.736, 0.893]`、`h0 = 6.28`，因此**永远进不了 `text`**；
  它落进 `repeat` 只是因为 `rep = 0.705 > 0.6`。同一份数据若字典/阈值微调就会跳到 `binary`——
  而实测 §3 显示 osdb 上 `CM-BIN`/`CM-TEXT3`/`TRANS` 的差距 <1%，**标签错不错完全不重要**。
* `sao` 全文件 `text ∈ [0.344, 0.613]`，被判 `binary`，但它的最优规则是 `TRANSPOSE-G(步长 28)`——
  分类器**看不到 28 这个维度**（`bestS` 只在 `smooth/repeat/binary` 分支里作为 "lag 探测的种子" 使用）。
* 与"仅用 `text > 0.5` 的决策桩"对比：全块一致率 mozilla 0.309 / sao 0.812 / osdb 0.000（桩说 text，实际 repeat）；
  但**只在 text∪binary 块上**一致率 0.968–1.0。即：六类在地形真正混杂的文件上几乎没有超出"ASCII 率"的信息量。

**结论（环节二 Q2）**：分类器不是"地形模型"，是 `(text, h0, hd, rep)` 的四维标量分区；
它缺的维度恰好是**周期/字段宽/相位**（sao=28、samba=38、mozilla=4、nci=3、mr=2 这些真步长全靠
`detectRecordStride` 的独立启发式，而它的返回值只用来"加候选"，从不参与分类与分块）。
特征"够不够"的实测答案是：**对"选恒等 vs CM"够用，对"选几何变换"不够用**——后者靠试压。

### 2.3 固定 512 网格 vs 真实结构边界：损失 ≤0.2%，不是瓶颈

### 2.4 32 个 Codec ID：14 个共用同一个核，17 个在语料上一次都没被选中

按数学算子归类（源码 `codec.ts:24-63` + `encodeSpec:145`）：

| 类别 | ID | 数学本质 | 与其他 ID 的重合 |
| --- | --- | --- | --- |
| 逃生/退化 | 0 STORE, 1 FILL, 2 RLE | 恒等/常量/游程，**不用模型** | 唯一不可替代的是 STORE（熵≈8 时的兜底） |
| 纯统计（算术编码） | 3 O0, 4 TEXT, 5 BIN, 18 TEXT2, 19 BIN2, 20 BCJ2, 23 TEXT3, 24 BIN3, 25 BCJ3 | **同一个比特级 CM**：19 个"特征槽"取不同上下文集合；v1=4–8 上下文、v2=更宽/词模型、v3=9 上下文+相位稀疏 | 18/23、19/24、20/25 只是"同 profile 的三代"；`BCJ*` = BCJ 变换 + 上面的 bin 核 |
| 一维线性残差 | 6 DELTA, 27 DELTA3, 8 D16, 17 MICRO | `x[i]-x[i-s]`（D16 在 16 位上、MICRO 是**现场拟合**的量化线性预测） | DELTA/DELTA3 同算子不同核；D16(s=1,order=1) 就是 16 位一阶差分（≈ DELTA(s=2)，只是残差按 16 位模打包） |
| 二维预测 | 7 GRAD, 21 GRAD2, 26 GRAD3, 31 WIDE_GRAD | MED（LOCO-I）梯度预测，`s`=像素跨度、`r`=行跨度 | GRAD* 三连同算子；WIDE_GRAD = MED 与 D16 二选一 |
| 转置/列分流 | 9 TRANSPOSE, 10 TRANSPOSE-G, 22 TRANSPOSE-2D, 30 TRANSPOSE-G3 | 按记录宽 s 做矩阵转置；逐列/逐组编码 | **四种布局是同一族**，22/30 只是"几何 vs 传统 vs v13 增强"的选择器 |
| 锚点/语法 | 12 ANCHOR, 13 ANCHOR_FOLD | 以某字节为行分隔做**列折叠** | 13 是 12 的无损变长版本 |
| 子通道 | 15 SUB-TRANSPOSE, 28 SUB-TRANSPOSE3, 16 SUB-ANCHOR, 29 SUB-ANCHOR3 | 转置/锚点后再按"同源列"分模态独立建模 | 与 9/13 同数据布局，只是模型分离方式不同 |
| 递归 | 14 PEEL | 对每列**再跑一次地形扫描** | 唯一真正的"递归"结构 |
| 位置相关 | 11 BCJ | E8/E9 rel32 → 绝对地址 | 只有可执行代码段需要 |

**真实命中率**（12 个 1 MiB 切片，`p8-census`）：**17/32 个 ID 一次都没被选中**
（STORE, RLE, O0, GRAD-2D, TRANSPOSE-G(10), BCJ-x86(11), ANCHOR-ALIGN(12), ANCHOR-FOLD(13), PEEL(14),
MICRO(17), CM-TEXT2(18), CM-BIN2(19), GRAD-2D2(21), BCJ3(25), SUB-ANCHOR3(29), WIDE-16(31)）。
被选中的 15 个里，`24 CM-BIN3` 覆盖 3.07 MB / 12 MB 原始（120 段）、`20 BCJ2` 1.02 MB、
`16 SUB-ANCHOR` 1.34 MB、`26 GRAD-2D3` 0.98 MB、`28 SUB-TRANSPOSE3` 0.76 MB、`8 LIN-16` 0.62 MB。

**两个"结构性缺失"**（这次审计最重要的一条代码事实）：

```
候选池从不包含 30:TRANSPOSE-G3   →  "从未进入任何候选池的 ID：22:TRANSPOSE-2D, 30:TRANSPOSE-G3"
候选池从不包含 22:TRANSPOSE-2D   →  它们只能由 10/9 被选中后，在分组编码时"升级"得到
```

`sao` 之所以用上 `30`，是因为候选池先选了 `10:TRANSPOSE-G`，再走 `encodePlanTranspose` 的升级；
**mozilla 上候选池连 `10` 都没选中**（`10` 在 12 个切片里只进过 7 次候选池、0 次被选），于是 `30` 永远不可达。
§3 会证明：mozilla 的赢家恰好就是 `30`。

### 2.5 为什么线性差分/预测打不过恒等？——用桶归因量化"破坏匹配模型"

对同一份 1 MiB 数据分别编码 恒等（`BIN_V3/TEXT_V3`，profile=bin/text）与 `DELTA_V3(s=2)` 的残差（profile=res），
用 `p8-attrib` 的桶归因看**比特都花在哪**：

| 文件 | 恒等输出 | bpb | 桶0 长匹配（字节%/比特%） | 差分(s=2) 输出 | 桶0 占比 |
| --- | ---: | ---: | --- | ---: | --- |
| webster | 202,230 | 1.543 | **94.16% / 87.76%** | 338,249 (**+67%**) | **0% / 0%** |
| dickens | 255,132 | 1.947 | **96.02% / 94.18%** | 395,451 (**+55%**) | 0% |
| mozilla | 308,365 | 2.353 | 72.64% / 59.30% | 457,932 (**+48%**) | 0% |
| ooffice | 446,777 | 3.409 | 60.85% / 53.12% | 745,655 (**+67%**) | 0% |
| sao | 670,894 | 5.119 | 38.59% / 21.63% | 834,014 (**+24%**) | 0% |
| mr | 244,547 | 1.866 | 89.48% / 77.29% | 238,905 (**−2.3%**) | 0% |
| osdb（256 KiB） | 74,860 | 2.285 | 70.38% / 32.38% | 118,216 (**+58%**) | 0% |

机制一目了然：**CM 的主引擎是 4/8 字节哈希的匹配模型**（文本上 94–96% 的字节、88–94% 的比特都由它承担，
平均 1.4–1.9 bit/字节）。字节级差分把"可匹配的字节串"变成"与邻居相关的残差"，
残差流的 4-gram 不再重复，**匹配覆盖率归零**；而差分换来的好处只有"残差幅值更集中"，
这点好处被 `res` profile 的 8 个上下文（比 text/bin 少 1 个、且没有词/结构相位）抵消。

**为什么 mr 是例外**：它是 16 位采样（音频），`deltaFwd(s=2)` 恰好等于 16 位一阶差分，残差仍有强匹配
（`mlen` 命中在残差上依旧成立），所以 `DELTA_V3(2)` 与 `GRAD-2D3` 都能赢恒等 16%（§3.3）。
这解释了为什么"差分有时赢、有时输"不是玄学，而是**"差分是否保留可匹配结构"**。

这也直接回答了任务书里的"哪些方法其实是重合的、能不能配合"：
`DELTA/GRAD/D16/MICRO` 与"恒等 + CM"的**不重合部分只有"残差分布更尖"**，
而它们与匹配模型的冲突是**零和**的：变换越彻底，匹配越没用。当前内核的混合器无法用"两路并行"弥补，
因为二者共享同一个 `mht`（变换后位置语义变了）。**这是 §7 建议里要写清楚的一条设计结论。**

## 4. 环节四：采样、断裂与经验惩罚系数

### 4.1 `sampleWindows` 的真实机制（先纠正一个误解）

任务书认为"从段首/段中/段尾各切 13.6 KB **拼成**一个 40 KB 数组，制造两个相位硬断裂"。
读源码（`codec.ts:1019-1028`）与实测都是：**三个窗口各自独立编码、把字节数相加**，
数组从不被拼接，因此**不存在人为拼接造成的相位断裂**。真实的偏差是另一件事：

* 每个窗口只有 `budget/3` 字节。`sampleLimit` 在 `n > 5 MiB` 时被压到
  `min(16000, max(4096, 8 MiB / 段数))`（`codec.ts:2080`），于是**窗口长度只有 1.3–5.3 KB**：

| 文件 | `analyze` 段数 | sampleLimit | 每窗字节 |
| --- | ---: | ---: | ---: |
| webster / dickens / nci / osdb / sao / mr / xml / reymont | 1–64 | 16,000 | **5,333** |
| ooffice | 838 | 10,010 | 3,336 |
| x-ray | 1,719 | 4,879 | 1,626 |
| **samba** | 2,247 | **4,096** | **1,365** |
| **mozilla** | 9,035 | **4,096** | **1,365** |

  1.3–5.3 KB 远小于 `O4/O6` 与匹配表收敛所需（§5 的冷启动实验显示 256 KiB 块的冷启动损失约 8–11 KB，
  即前 256 KiB 都在"热身"）。**但实测这几乎没有代价**：

| 采样法 | top-1 命中 | Regret 合计 | Kendall τ（vs 真实排序） |
| --- | --- | ---: | --- |
| 现状（3 窗 × ~1.3–5.3 KB） | 100/100/100/100/75/25/25/63 % | **34 B** | 0.933–0.991 |
| 单窗 40 KB 连续 | 100/100/100/100/63/25/25/63 % | **54 B** | 0.933–0.991 |

  原因：大多数段的候选之间差 5–50 倍（samba 的 64 KiB 段最优 631 B、恒等 2,586 B），
  采样再短也能分出量级；真正接近的候选只在同族内部（例：`CM-BIN3` vs `CM-BIN2`），而同一段的同族差距本来就 <1%。

### 4.2 经验惩罚系数：52 段里改错 6 段，净亏 646 B，0 次改对

`adj()` 的硬编码系数（`codec.ts:1256`）：`MICRO ×1.03`、`SUB_* ×1.006`、`PEEL ×1.04`、
`ANCHOR ×1.024/1.05`、`BCJ ×1.024`、`text 区的 BIN ×1.03`、其余 `×1.003`。

用同一批采样估计分别按"有惩罚/无惩罚"排序，再用真实整段编码结算：

| 指标 | 值 |
| --- | --- |
| 两种排序选中同一规则 | 44 / 50 段 |
| 有惩罚更好 | **0 段** |
| 有惩罚更差 | **6 段** |
| 净字节差 | **+646 B（+0.067%）** |
| 最差 4 例 | ooffice：`BCJ2`(31,367) 覆盖 `BCJ-x86`(31,204) → **+163 B**；同类 161 B / 153 B / 152 B |
| 其余 2 例 | xml：`ANCHOR-GRID` 覆盖 `SUB-ANCHOR3` → +12 B；又一段 ooffice `BCJ2` → +5 B |
| 惩罚"救回"的最差候选 | 无 |

也就是说：`BCJ` 被 `×1.024` 罚、`BCJ2` 不罚，于是选了更差的 v2 核——**惩罚系数的方向与真实代价无关，
它只是把"我们不信任的规则"整体拉高 0.3–5%**。而真实容器头部代价是多少？

* 一个额外分组的头部：`id/s/r/payloadLen` 四个 varint ≈ **7 B**（`planHeader:1851`）；
* 一个额外段的长度 varint ≈ **2–3 B**；组归属位图 ≈ 1 bit/段。
* 即：**每个"多出来的段+组"真实成本 ≈ 10–12 B**。
  而 `×1.003` 作用在 64 KiB 段上 = **197 B**，作用在 1 MiB 段上 = **3,146 B**——
  比真实头部代价大 **20–300 倍**。`×1.024`（BCJ）在 64 KiB 段上是 1,573 B。

**结论**：惩罚系数应当整体删除，改用**精确的 `headerBits/sampleRatio`**（把 `planHeader` 的 varint 长度
按候选是否新增分组算出来，再加 ~1 bit 位图），量级是 10–100 B 而不是 200–3,000 B。
这一条不改变任何比特流格式，且实测立刻省 646 B / 3.3 MB（≈0.07%）。

### 4.3 能否用解析熵替代试压？不能（实测相关系数 0.149）

对 208 组（段 × 差分步长 1/2/4/bestS）同时计算：一阶条件熵 `h1(x)`、`h1(残差)` 与真实 CM 字节数。

| 指标 | 值 |
| --- | --- |
| 参与的 (段, 差分) 组合 | 208 |
| `h0` 认为"差分更好" | 24 |
| `h1` 认为"差分更好" | 38 |
| 真实"差分更好" | 14 |
| **`h1` 说差分更好但真实更差** | **24 / 38 = 63%** |
| 平均"熵预测增益" | −16.6%（即平均预测差分变差） |
| 平均"真实增益" | −61.8% |
| 预测增益 vs 真实增益 的相关系数 | **0.149** |

最典型的"熵骗人"样本：`mr`（16 位音频）某段 `delta(s=1)` 让一阶熵从 **1.86 降到 1.08**（预测 **省 42%**），
真实 CM 字节数却是 **+3.5%**（匹配模型失效，§2.5）。

**为什么必然如此**：CM 的输出是 `mix(9 个上下文, 匹配状态, APM 校准)`，
它对"分布形状"不敏感、对"可预测的结构重复"极敏感；零阶/一阶熵只看**边缘分布**，
完全看不到 `mlen`（匹配覆盖）与 `count`（上下文成熟度）。
用低阶熵做候选排序，等于用"字母频率"预测"LZ 能不能找到长匹配"。

**替代方案的最低试压代价**：不必 40 KB×3 窗，**单窗 8 KB 连续 + 强制包含 ≥2 个完整记录**即可保持
top-1（实测 3 窗 Regret 合计 34 B、单窗 40 KB 合计 54 B，两者只差 20 B）。
真正需要"试压"的只有**同族内部**（`BIN3` vs `BIN2`、`DELTA3(s)` 的不同 s），
跨族（恒等 vs 转置 vs 差分）差距是数量级，解析特征或 1 KB 试压就能判断。

## 5. 环节五：分组编码、冷启动与"内部潜力上限"

### 5.1 先纠正前提：`MAX_SUB_CHUNK` 不切纯 CM 分组

```
codec.ts:391  const MAX_SUB_CHUNK = 8*1024*1024
codec.ts:392  function encodeSubGroups(parts, sp) { ... 每满 8 MiB 开一条新的列模型 ... }   // 只有 SUB_* 族
codec.ts:886  encodeTerrainGroupImpl → 对 TEXT_V3/BIN_V3/DELTA_V3/… 一律 encodeCM(joined …)  // 整组一条流
```

所以"每 8 MB 把 18 MB 的 CM 表清零重来"**在纯 CM 分组上并不存在**：webster 41 MB 就是**一条** 41 MB 的 CM 流。
真正会因 8 MiB 触发重置的是 `SUB_TRANSPOSE/SUB_ANCHOR`（samba/xml 会用到），
以及**每一个不同 spec 的分组**（每个 `PlanGroup` = 一个全新 `Model` = 空表）。

那么 8 MiB 这个数字的真实影响是什么？两条，都是"间接"的：

1. **候选门槛**：`SUB_*` 只在 `seg.length ≤ MAX_SUB_CHUNK` 时生成（`codec.ts:1155,1228`），
   `TRANSPOSE_GROUP` 的分组升级只在 `seg.rawLen ≤ MAX_SUB_CHUNK` 时允许；
   超过 8 MiB 的段直接失去这些族 —— 对 41 MB 的 webster 无所谓（它不想要），
   对 51 MB 的 mozilla **意味着整文件级转置永远不可能被考虑**。
2. **模型表位宽被夹在 2²¹**：`coder.ts:506`

```ts
const bits = Math.min(21, Math.max(10, Math.ceil(Math.log2(Math.max(n,1)*8)) + 1))
```

   只要数据 ≥ 256 KiB，`bits` 就**恒为 21**（2 M 槽/上下文）。41 MB 的 webster 与 256 KiB 的片段用同样多的槽位：
   41 MB / 4 字节 4-gram ≈ 1,000 万个不同上下文抢 2 M 个槽位。这不是"清零"，是"表被压扁"，
   后果与冷启动同类（互相污染），但**无法靠"续传热表"解决**。

### 5.4 为什么文本文件"看起来很努力其实没什么可做"？

webster / dickens 的归因非常干脆：**94–96% 的字节、88–94% 的比特都在长匹配桶里**，
平均 1.4–1.9 bit/字节；`O4`+`O6` 只覆盖 0.07–0.08% 的字节；冷上下文只占 2.5–3.5% 的字节但吃掉 3.8–7.5% 的比特。
换句话说：**这两份 41 MB / 10 MB 的英文文本，其压缩几乎完全由"LZ 匹配 + 匹配状态混合器"完成**，
9 个上下文表、双 APM、辅混洗、词模型加起来只贡献个位数百分比的比特。
这解释了 P5/P6/P7 在 webster/dickens/reymont/nci 上"怎么调都是 0.01%"：
**这些文件的剩余熵不在我们调参的地方**（它要么在匹配模型里，要么在对不齐的长距重复里）。

反过来，`sao`/`ooffice`/`mozilla` 的碰撞桶占 16.6–50.1% 的比特——
但它们同时也是"转置/BCJ 能赢 9–20%"的文件，说明**它们的结构信息本来就没被 CM 的逐比特上下文抓住**，
抓住它们的是**几何变换**（把定长字段排到同一列），而不是更大的表。

## 6. 我们凭什么判定"潜力到头了"？——三条内部判据（不引用任何世界纪录）

**判据 A：神谕差（Oracle Gap）**＝在同一段划分下，暴力神谕 C 与现状 A 的真实字节差。
它度量"规则选择与候选生成"还剩多少。本次：**A−C = 14,121 B / 916,226 B = 1.54%**，
且 95% 集中在 1 个文件 mozilla 的 1 个族。**当 A−C < 0.1% 时，规则层就可以宣布收敛。**

**判据 B：冷启动下限**＝按当前模型，把一个分组切成 n 块的必然代价
（实测 0.6–1.5% × 每块字节数）。它给出"分组粒度"的最优边界：
`期望的结构纯度收益 > 切分冷启动代价` 才值得切。本次 mozilla 的 8 MiB 实验（切 4×2 MiB 反而更好）
说明这个判据必须用**实测**而不是常数阈值来评估。

**判据 C：桶归因上界**＝把比特按"是谁预测的"分开后，看**最弱的那一桶**还有多少空间：
* 桶0（匹配）已经 1.4–1.9 b/B，且匹配模型是 LZ 级——提升要动 `mht` 结构与最小匹配长度；
* 桶2/3/4（冷/碰撞/薄）合计吃掉 6–60% 的比特，但它们要么是**真随机**（osdb 的冷上下文 5.06 b/B 与
  干净命中 5.30 b/B 差不多，说明"学到的上下文"并没有比"没学过"好多少 —— **数据本身接近条件无关**），
  要么是**结构没对齐**（sao/ooffice 的碰撞桶 = 转置该上场的地方）。
* 因此**"还剩多少"可以从桶的形状直接读出**：若某文件的桶2 的 b/B 已经接近桶1，
  说明再加高阶上下文/更大表都是白费（osdb 就是这样）；若桶3 远高于桶0，
  说明应该换"几何"而不是"统计"（sao/ooffice/mozilla）。

**判据 D（可选）：参数灵敏度**＝把"无参数可调"的旋钮（表位宽、`minLen`、`limit`、`slt`）
推到算力/内存允许的上界，看收益是否已经 <0.5%。本次表位宽 +2 位只有 0.14–0.77%，
说明**"CM 参数调优"这条路的上限就在 1% 以内**——这才是"到头"的可证伪定义，
而不是"离 cmix 还差多少"。

## 7. 卡点排序与建议（按"字节/改动量"排序，全部不触碰比特流格式）

### 关于"我们是不是只是把现有内容拼接在一起"

本次实测的答案是：**不是，但结构性创新的落点错了**。
* 现有流水线的收益分解（按机制，而非按 ID）：**匹配模型**（文本 88–94% 的比特）、
  **几何变换**（sao −18.4%、mr −16.4%、ooffice BCJ −9.2%、xml 锚点 −12.3%）、**统计上下文**（0.1–17.6% 的比特）。
* 真正**新**的东西只有"几何变换的选择 + 分组归一"。而 P5/P6/P7 的微调全部发生在
  "统计上下文"这一侧——**那正是实测占比最小、且已被匹配模型掩盖的一侧**。
* 因此下一步的正确方向不是新启发式、不是调系数，而是：

0.1 为什么不看"世界纪录"
世界纪录（paq8/cmix/zpaq 满分档）与我们差的不只是"几个参数"，而是模型族：
满分档用整文件两遍、混合/神经网络预测、几十个上下文、无损上下文的精确映射表。
用"离纪录还差 X%"来判定"潜力到顶"既无法归因也无法执行。本报告改用三个内部判据
（全部由文件自身实测，不依赖外部实现）：

神谕差（Oracle Gap）：同一段划分下，把候选/采样换成暴力全测，能省多少字节（§3/§4）。
能力消融（Ablation）：同一内核逐级加能力（O0→O1→7ctx→9ctx→APM），每级买到多少比特（§5.2）。
自热身上限（Self-warm）：用同一文件的前 P 字节给模型预热，再看后段边际码率能降多少（§5.5）。
这是"任何更好的初始化/两遍编码"能达到的内部上界参考。

"1 段"不是合并出来的，是分类器在第一层就判成了单一标签。

cleanTinySeams（只吞 <16 B 的非 fill 碎片）和 mergeShortRuns(.., 2)（<1 KiB）。

因此"DELTA/GRAD/XOR/D16/PEEL/MICRO 打不过恒等"不是 bug，而是信息论上正确的：
它们是对"局部平滑"的先验，而我们语料里绝大多数区域的冗余是长程重复而不是局部平滑。
想靠"再补几个差分变体"提升，收益上限就是 x-ray 上的 −3.3%（且 x-ray 已经有 WIDE_GRAD 吃掉）。

另外，你提到的 XOR / STRIDE4_DELTA / TRANSPOSE_V3(s=2,4,8) 在代码里不存在：
32 个 ID 里没有 XOR；STRIDE4_DELTA 只在 coder.ts 的注释里出现过一次（是历史实验名）；
TRANSPOSE_V3 不存在，转置族是 9/10/22/30 四个 ID。这一点很重要：
候选池的"数学覆盖面"比任务描述里假设的要窄，但更关键的是——即使把核心族全暴力测一遍，
也几乎不赚（§3.2）。

3. 环节三：地形分类模型的准确性 —— 暴力神谕实验
3.1 实验设计
同一批段（默认 64 KiB 均匀网格；--analyze 用 analyze 的真实边界再按 64 KiB 切细），
三条策略的真实完整编码字节数：

B（去采样偏差）：同一个 candidatesFor 池，但每个候选都整段真实编码取最小
C（全局暴力神谕）：无视 cls，对 {STORE, O0, TEXT_V3, BIN_V3, BCJ_V3, DELTA_V3(s=1,2,3,4,8,bestS), GRAD_V3(s=bestS, r∈{bestS,2,4,16,64,256})} 整段真实编码取最小
体积 = Σ 段最优字节 + 每段 8 B 头部估计（三策略同口径，因此差值=选择损失）

读法：

唯一上 0.5% 的是 xml（+127 B / 21,000 B）和 ooffice（+1,195 B / 221,000 B），
原因都是"惩罚系数把某个更优的非 CM 规则压掉了"（§4.2 会给出明细）。
B−C 在 8 个文件上 ≤ 0.7%，且全部是负数（= 现状池比"无视地形的暴力核心族"更好）。
这不是 C 写得不够暴力，而是C 的家族里没有 transposition / anchor / BCJ 变换——
而这些恰恰是 xml（SUB-ANCHOR3）、sao（TRANSPOSE-G3）、mr（GRAD-2D3）、x-ray（WIDE-16）
的真实赢家。C 在 sao 上差 22.8%、mr 上差 6.6%、xml 上差 3.7%，就是这三族的价值证明。
webster / dickens / nci 上 A=B=C 完全相等：这三个文件上"选规则"这件事已经到顶了。
任何"再优化分类器/再优化采样"都不会带来 1 字节。
3.3 直接回答你的问题
"地形分类是否合理、是否最优？判地形是否准确？"

准确：与 ASCII 二分类的一致率 99.5%~100%（§2.2）。
合理但不是瓶颈：分类标签唯一的作用是给 candidatesFor 开闸（哪些族进入候选池）。
而 planTuning.featureCandidates = true（P7-2）之后，候选池已经按"多维特征并集"生成，
不再被单一 cls 封锁——probe-idstat 显示 CM-TEXT3 在 binary 段里也进了 2,646 次池、
GRAD-2D3 在 text 段里也进了 517 次。地形现在只是"成本很低的启发式排序"，
不再是"硬门禁"。
不最优的地方不在标签，而在"标签之后没有东西"：分类完成后，每个段都要走
"40 KB 采样 + 惩罚系数 + 部分复核"，而这套机制的排序保真度已经到 99.5%（§4.1）。
也就是说：把分类器换成完美神谕，最多也只能赚 §3.2 的 A−B 那一列（≤0.61%）。

Regret 只有 0.03%。"三段拼接制造相位断裂"这个担心在实测中不成立
——因为 chooseSpecImpl 是把三个窗口分别独立编码再求和（size += encodedSize），
不是把三段拼成一个数组喂给模型。代码里没有"拼接"，所以也就没有"断裂"。
你在任务里描述的"拼成一个 40 KB 数组"并不符合 sampleWindows 的实现
（它返回的是 3 个 {sample,start}，逐个 encodeSpec）。
在单个巨大段（nci 1 MiB 单段）上，三段采样确实会选错，而且错得很贵：
SUB-ANCHOR3('\n',0x08) 整段真实 60,958 B，采样把它排到第 1（0.11488），
但 CM-BIN3 采样 0.10683 排第 1 —— 采样把它排成第 7，最终选了 CM-BIN3（63,386 B），
多花 2,428 B = 3.98%。原因不是"断裂"，而是 13.6 KB 的窗口对 SUB-ANCHOR3 的
列模型而言太短（每列只有 ~1.7 KB，行长表 + 列上下文都没热）。
→ 这是"窗口太短"，不是"窗口拼接"。 单段 256 KB 就能把 Regret 打到 0。
nci 的 Kendall 逆序率高达 33%，说明短窗口下候选的相对名次是乱的；
窗口一长（256 KB）就降到 7.7%。
4.2 经验惩罚系数审计
chooseSpecImpl 的 adj() 实际是：

TypeScript

t.ratio * (cls==='text' && id===BIN ? 1.03 : 1)
        * (id===MICRO ? 1.03
         : sub* ? 1.006
         : id===PEEL ? 1.04
         : id===ANCHOR ? (len<=1MiB ? 1.024 : 1.05)
         : id===BCJ ? 1.024
         : id===STORE ? 1
         : 1.003)
实测后果（probe-oracle 的 topFlipAB / probe-rank）：

关于"用 headerBits / sampleRatio 替代拍脑袋系数"：可行，而且应该做，但收益很小。
现状每段头部 8 B（varint×4），对 64 KiB 段是 0.012% —— 用精确头部成本替代 1.003
只会改变 0.01% 量级的决策。真正需要的是把惩罚系数从"乘在 ratio 上"改成
"乘在实际字节上并显式建模热身摊销"：

现在 1.003 是比例惩罚，它对大段（1 MiB）意味着 3 KB，对小段（4 KiB）意味着 12 B。
但真正的成本差异（大段热身更充分、小段冷启动更贵）恰好与段长成正比，
所以比例惩罚方向是对的，只是量级太小（实测冷启动成本是 3%~18%，见 §5.3）。
1.024（BCJ/ANCHOR）和 1.04（PEEL）是"防止采样过拟合"的保险，但它们的方向
与实测相反：probe-idstat 显示 BCJ 族 1,360 次进池、BCJ-x86 只赢 3 段，
BCJ 系的问题不是"被低估"，而是"三个版本并存、互相压价"。

STORE 组在 mozilla 上占输出体积的 13.7%（1.88 MB），而这 1.88 MB 里
有 55.5 KB 是"本来就能压、只是被逐段 STORE 判决埋掉的"。机制很简单：

orphans 过滤也排除 STORE/RLE/FILL），所以这条路是关着的。

这是一处纯粹的接线 bug 级浪费：55.5 KB ≈ 全文件的 0.11%，是 mozilla 与 xz 差距
（+2.51% ≈ 344 KB）的 16%。 而且修复不需要任何新算法：允许 STORE/RLE 组参与
consolidateOrphans 的"并进主力 CM 组"择优即可（严格更小才吸收，单调不劣）。

这张表的意义（以及它的陷阱）：

我们的 bpb 已经低于 H4（dickens 1.891 < 2.03、webster 1.411 < 1.58、nci 0.434 < 0.73）。
这不是矛盾，而是因为 H4 是"静态两遍、每上下文独立混合"的交叉熵，
而我们的模型有匹配模型（长程重复）——匹配能拿到 H4 拿不到的东西。
所以H_k 不是可达下界，而是一条"参照线"：低于它说明匹配在起作用，
高于它说明连静态 k 阶都没做到。
sao（4.984 vs H4=3.28）和 mozilla（6.015 vs H4=2.96）显著高于 H4，
这才是真正的"没做到"：sao 需要 28 字节记录内的列上下文（H4 只是字节 4 阶），
mozilla 需要"跨文件类型的自适应上下文选择"。
但注意 H4 的"新上下文占比"：sao 94.7%、mozilla 97.6% —— 这意味着
静态 k 阶模型在这两个文件上根本不可达（每个 4 字节上下文平均只出现 1 次，
无处学习）。要拿到 H4 的收益，必须做上下文共享/回退（context mixing with
confidence-based backoff），而不是"再加一个哈希槽"。

所以它不是"名单漏了"，而是名单里明明有、却按 parts.length 一道闸门把单分片全部拒掉，
而拒掉的理由（"alt 与 base 必然相同"）只对 encodeSpec 这条 v9 固定入口成立（缺陷 A）。
两个缺陷互为因果，形成闭环：A 让单分片不可能有 v15 → B 因此可以合法地不试 → B 不试就永远发现不了 A。

6. 三个必须纠正的认知（本轮实测直接推翻）
6.1 "我们把整份文件合成了 1 个段、1 个组"——是好事，不是坏事
文件	段数	分组	现状 vs 整片单组（probe-onegroup/probe-regroup）
dickens	1	1	2,318,397 vs 2,318,374（+23 B，容器头）
webster	1	1	6,763,509 vs 6,763,486（+23 B）
osdb	2	1	2,372,218 vs 2,372,193（+25 B）
nci	1	1	1,325,325 vs 1,535,996（−13.7%，现状更好）
reymont	13	6	1,109,363 vs 1,108,077（−1,286 B，现状略差）
mozilla 4 MiB	205	12	3,272,858 vs 3,230,084（−42,304 B，现状明显更差）
"1 段 1 组"在这些文件上已经是"整片一条规则"的极限配置——
它意味着模型从第一个字节跑到最后一个字节、只热身一次、没有组头、没有接缝。
这正是 §5.3 里 webster/samba 那种"截断就亏 3%~19%"的数据最需要的形态。
所以"1 段 1 组"不是"我们偷懒/坍缩"，而是"这个文件的地形本来就单一"。

真正该担心的是反例：mozilla 的 12 组、samba 的 18 组、ooffice 的 16 组——
mozilla 的 12 组比 1 组贵 42.3 KB，samba 的 3 组在 4 MiB 切片上反而更好（+0.25%），
说明分组数不是单调坏，而是"每个分组是否赚回了它自己的冷启动成本"。

6.2 "95%~100% 的字节没有做任何空间变换，直接裸进 TEXT_V3/BIN_V3"——这是正确的选择
probe-delta 用 5 个文件 × 9 种变换做了 45 组实测，结论是：

DELTA/GRAD 在 osdb 上 +50%~+215%、sao 上 +17%~+51%、mozilla 上 +12%~+29%；
唯一负收益是 x-ray 的 DELTA(2)/GRAD(2,2)（−3.2%），而 x-ray 已经被 WIDE-16 吃掉；
原因是差分把匹配覆盖从 19.6%~83.4% 打到 0.0%，而匹配桶贡献 60%~69% 的体积（§5.1）。
"不做空间变换"不是缺陷，而是"信息在哪里"的正确判断。 需要改的不是"多做变换"，
而是"在匹配桶里把匹配编得更便宜"（§5.7：覆盖率已到 LZ77 的 98%，单价才是问题）。

6.3 报告中"nci STORE"的口径问题——STORE 在真实容器里不会以 STORE 形式存在
probe-onegroup 对 nci 全量给 1,535,996 B（4.58%），而管道给 1,325,325 B（3.95%）；
差值来自 nci 的 STORE 段：在 compressAdaptive 里它们被 consolidateOrphans
并进主力组，而 probe-onegroup 用 encodeCM 直接整片编码没有这层重组。
这提醒我们：任何"分段/单组"的对照实验都必须用 evaluatePlan（真实容器路径），
不能用裸 encodeCM 的字节数直接比较。 本报告 §5.4 的结论全部来自 evaluatePlan。

7. 四个环节的最终裁决
环节	现状损失（实测）	裁决
环节二（分块/特征/方法本质）	分段本身 0.000%（§2.1、probe-split）；11 个死 ID 零命中	不是瓶颈，但有"死代码负担"：11 个 ID 在 20,000+ 段上零命中，却每次都占 sampleLimit 的 1/3~1/2 时间。省时间不改字节。
环节三（地形分类）	A−B ≤ 0.61%，多数 ≤ 0.05%（§3.2）	不是瓶颈。分类器 = ASCII 二分类（99.5%~100% 一致），而分类标签已不参与硬门禁（P7-2 之后）。把它换成完美神谕最多赚 0.61%。
环节四（采样/惩罚）	0 ~ 0.61%，Regret 最大 2,428 B（nci）	不是瓶颈，但有一个真 bug：巨大单段上 13.6 KB 窗口会让 SUB-ANCHOR 类规则名次错乱（nci 33% Kendall 逆序）。改法：单段长度 >1 MiB 时窗口取 256 KB，而不是三段 13.6 KB。这是唯一"低成本高确定性"的环节四改动。
环节五（分组/编码/内核）	3.0%~7.7%（单分片内核接线，§5.8）+ 1.31%（mozilla 分组，§5.4）+ 2.9%（STORE 组回收 55.5 KB / 1.88 MB 裸存）+ 3%~10%（自热身，内部上界但解码端不可得）	就是这里。四个环节里唯一有"数量级正确"的钱可捡的地方。 三条可执行修复（F1/F2/F3）+ 一条需要换模型的长期方向（F7）。
"我们凭什么判定潜力到头？"——三个内部判据的答案：

神谕判据：在"选哪条规则"这一层，我们已经离暴力全测 ≤0.61%，离"池 ∪ 核心族"神谕

消融判据：把能力逐级加上去，7ctx→9ctx 值 0.7%~2.7%，v13→v15 值 0.5%~6.1%。
再加同类能力的边际收益 < 1%/级，也到顶了。
内部上界判据：自热身（完美预热 1 MiB）只值 3.2%~10.2%，且解码端不可得（没有未来数据）。
与 xz 的差距是 12%~19%（文本类）。差距不在"热身"，在模型族。
覆盖率判据：匹配模型覆盖了 25.4%~98.2% 的字节，而贪心 LZ77（窗口=整片、链长 64）能覆盖
27.9%99.4% —— 差 1%~8 个百分点，即"就算把匹配查找做到 LZ 极限，也只能多覆盖这么多"，
且这些多出来的匹配还要按当前单价（桶 0：0.301.34 bit/B）付费。"找匹配"这一层也接近到顶。
归因判据：文本类文件 60%~69% 的输出比特来自"匹配桶"，只有 0.35%~1.53% 来自"冷上下文"。
这意味着任何以"冷启动/初始化"为名的改动，理论收益上限就是那 1% 量级；
而 mozilla 的 41.97% 来自"高阶全冷"，sao 的 24.08% 来自"列内冷上下文"——
这两个文件的瓶颈不是匹配，而是"上下文共享/回退没做"。
