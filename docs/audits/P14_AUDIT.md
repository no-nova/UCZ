## 1. 范围、方法与证据

实现基准是 P13.1 `ed09309`。全部 `src/lib/*.ts` 聚合 SHA：

`3f6971ff4feff664f7fc16f50c6d89a7ac92622ee57d1b4c586ce52c722b62a3`

与该提交逐文件一致，包括 `coder.ts`、变换、路由、WORD-PRE 准入及生成 worker。基线更新只改数据/文档及相关 metadata 测试预期；P14 实验只给 `.diag-state/p14/` 中的源码副本应用补丁。

### 方法

1. 每个 shell 命令均外包 `timeout --signal=KILL 19s`，单探针内部预算 17 s。原文诊断窗口 **<=262144 B**；复制的 CM 编解码入口有 **<=524288 B** 硬守卫。语料下载仅恢复并核对标准 size/SHA，不执行完整文件 CM。
2. 复用 P12/P13 在本轮结果产生前已固定的窗口，详见 `scripts/diag/p14/slices.json`。除 sao 的记录对齐窗 **262136 B** 外，主实验均为 **262144 B**；sao 规划另用 <=64 KiB 输入、内部 <=16000 B 窗口。不是随机总体抽样。
3. 实验为实际 **v20 CM 算术编码**，不是只报 H0 或理论熵。修改后的模型在同一实验解码器逐字节 roundtrip；sao 两份固定 TG3 控制另由现有生产解码器复验。
4. 改变上下文/布局的实验模型只是研究载荷，**不能按原 v20 语义保证解码**（位流不变的插桩等对照除外），未生成可部署的实验 UCZ。后续需要独立版本/内核标识，不能把这些补丁直接塞进现有 v20 解码规则。
5. 回执保存原源码、逐条唯一锚点补丁、实验源码、输入窗口、脚本历史、bundle 的 SHA。`verify.mjs` 只读重建补丁并核验，不伪称重跑了编码。
6. WORD-PRE 词表在该 256 KiB 窗口上构建；后续复用 SHA 绑定缓存。缓存不改变模型输入，冷准备与编码耗时分开。切片 CM 表一般为 21 bit，而完整大组可用 22/23/24 bit，并有长距匹配/模型热身差异。

**计价约定：**下表为实际 payload B，`Δ=实验−控制`，负数才是改善。WORD-PRE 表中的 CM 字节已含共同压缩的字典，不含恒定 **4 B** 长度前缀；和 raw 比较时另加这 4 B。WIDE/TG 表计入其内部实际长度/列组头，但不含 UCZ 外层头；未来新增格式成本尚不能冒充已经测量。

完整 **60 项成对比较、每条回执路径和 SHA、条件性外推**：`scripts/diag/p14-results/summary.json`，由 `scripts/diag/p14/summary.mjs` 确定性生成。

## 2. Unit 1 — WORD-PRE 与词上下文

### 2.1 源码事实：原假说不是当前 v20 路径

- `wordpre.ts` 当前 v1 是 **最多 120 个单字节 token（0x80–0xF7）+ 0x7F 转义**。没有 `0xFE/0xFF + idx` 双字节 token，也没有 `0x01/02/03` 大小写前缀。
- 词条为 **3–24 B 任意高频子串**，可含空格、标点、多个词或部分单词；不是一个 token 必然等于一个完整词。
- `coder.ts::byteUpdate` 已对 `wordTokens && byte>=128` 单独推进 `prevWord <- curWord`，把新 token 哈希放入 `curWord`。当前 v20 的词上下文实际为 **H[6]/H[7]**；H[8] 是稀疏字节上下文。`wh/pwh` 的高位字节累积不是 v20 在用的这两个词状态。
- 因此“不推进 prevWord、把整句 token 视为一个词”的说法不适用于当前实现。确实存在更细的语义不匹配：一个任意子串 token 被视为一个完整词。
- `encodeWordPrePayload` 把 **字典头与 body 一起交给 text CM**；不是裸存字典。词条数/长度已经用 varint。不能把字典原始长度当作可直接删掉的压缩字节。

五个主窗口的字典原始长度分别是 webster **552 B**、dickens **595 B**、reymont **270 B**、nci **509 B**、xml **386 B**。NCI 的 token 命中多数含前导空格（11815/15721），XML 则仅 63/15392；不能把“多数 token 吸收空格”套到所有文件。

源码也没有区分 `0x7F` 后的高位字面量和真正 token，这是潜在扩展点；但**五个主窗口的 escapedLiterals 都为 0**，不能给本轮 Silesia 收益记账。以下 lexical 实验不是“修复转义后省了多少”的证明。

### 2.2 实验定义

- `wp-lexical`：仅在副本中因果解析已编码/已解码的字典头；遇 token 时用字典展开的字符更新真正 ASCII 词边界。无字典或原文未来信息，编码/解码一致；H[8] 不改。
- `wp-token3`：保留现有 token 词状态，增加前前词历史，**替换 H[8] 为三元词/token 上下文**，不增加表数量。
- `wp-merge`：反事实消融，把高位 token 字节也按连续 word-hash 累积。不是“正确分词修复”，用于检验边界细化是否一定更好。

|---|---:|---:|---:|---:|---:|
| webster-mid | 56444 | 57182 | 56558 (-624) | 57230 (+48) | 57420 (+238) |
| dickens-mid | 69544 | 77420 | 73661 (-3759) | 77513 (+93) | 78114 (+694) |
| reymont-mid | 47358 | 47539 | 47530 (-9) | 47559 (+20) | 47516 (-23) |
| nci-mid | 13257 | 12491 | 12511 (+20) | 12572 (+81) | 12442 (-49) |
| xml-mid | 5850 | 4683 | 4688 (+5) | 4538 (-145) | 4517 (-166) |

**不能把相对一个较差 WP 候选的改善算作系统收益：**

- Webster lexical 从 57182 降至 56558，但加 4 B 后是 **56562 > raw 56444，仍多 118 B**。
- Dickens lexical 省 3759 B，但加前缀后 **73665 > raw 69544，仍多 4121 B**。
- Reymont 最小的已测 WP 是 merge **47516+4=47520**，仍比 raw **47358** 多 162 B。
- XML/NCI 仍是适合 WP 的目标；不存在“修正分词后自然语言就全部应启用 WP”的证据。

## 3. Unit 2 — WIDE 几何与跨平面

### 3.1 真实调用链

当前没有 `getTransformGeomStride()`。行宽来自序列化规则 **`sp.r`**，不是 `buf[1] | buf[2]<<8`。WIDE1 为 D16 特例，不能把 s=1..8 都当作同一个二维布局；WIDE3/4/5 为交织 LE16 残差，WIDE6/7/8 为 ZigZag 残差高、低平面。

`encodeWide16` 的低平面已经是 `res2d, s=1, r=W/2`，包含上/左上/右上邻域；高平面独立使用 `res,1,1`。因此：

- 额外传 `geomStride` 是**替换 H[6]/H[7] 上下文定义**，不是修复遗漏的 W/2。
- 低平面模型 buffer 只有低平面，`pos-halfLen` 不会取得高平面；需显式使用先已解码的高平面。
- 高平面是 **ZigZag residual 的 MSB**，不是原图像像素的 MSB。

### 3.2 同布局实际 CM

`geom` 对低平面额外传 W/2；`msb` 把 H[8] 替换为低字节邻域 + MSB=0/1/>1；`msb-add` 保留原九表、新增第十表，用 MSB 位长条件；`high2d` 把高平面也改用二维 profile。MSB 侧信息在解码端只来自已解码的高平面，没有原文 oracle。

### 3.3 sao：不能从较差布局的改善偷算收益

当前 TG3 把相邻列组在记录内交织，独立 CM 编码不同列组；不是一条全文件逐字节平面流。生产 `planColumnGroups` 的大窗搜索此前在 P13 超时，P14 **没有重试那个长路径**：单独在 <=64 KiB 输入上生成固定计划（内部 <=16000 B），随后在同一 **262136 B** 窗口编码完整固定方案。其规划与自动完整 256 KiB TG3 选型不等价，不能声称找到后者 oracle。

- `tg-side`：利用已解码前一列组的同记录字节，替换当前组的一个上下文；两边逐组对称，计入实际组头。
- `tg-flat-side`：另一个新布局，把 28 个独立字节平面放进同一 CM，再访问已解码前一平面。其控制是新的 flat 布局，不是现有 TG3。

| 窗口 / 比较 | 控制 | 实验 | Δ |
|---|---:|---:|---:|
| sao-mid / tg-control→tg-side | 139989 | 139987 | -2 |
| sao-late / tg-control→tg-side | 137894 | 137896 | +2 |
| sao-mid / tg-flat→tg-flat-side | 168401 | 154094 | -14307 |

flat-side **154094 B** 仍比该窗合法固定 TG3 控制 **139989 B** 大 **14105 B**，而且尚未计新布局标记。**14307 B 的 flat 内部改善不能记为现系统收益。** 实际 TG3 侧上下文是 -2/+2 B，留出窗翻转，淘汰。

该主窗固定计划中 11 个 STORE 列合计 **102982 B**；高随机性字段与其它可压列已被分开。不能从 H0 高或 STORE 选择证明它们信息论上不可压，但目前“只连一个前平面上下文”的实验没有打败现方案。两份 TG3 控制均另通过现有生产 `decodeTerrainGroup` 逐字节解码，避免把手写错误布局当作基准。

## 4. Unit 3 — 二进制对齐、稀疏上下文、分段

### 4.1 当前已有与真正缺口

v20 BIN 无几何跨度时：H[4]=`hh(b1,pos&3)`，H[5]=`hh(b1,b3)`，H[7]=`hh(b1,b4)`，H[8]=`hh(b2,b4)`。b1/b3 稀疏上下文本来就存在。旧 v15 的 b4/b8 机制没有原样留在 v20，**同相位长一点的历史**才是本轮实测的有价值候选。

- `stride4`：H[8] 改为 `hh(b4,b8,b12,pos&3)`，保持九表。
- `opcode`：H[8] 改为 b4/b8 + **前一完整 32 位字**的高 6 位 opcode + phase。只读已编码字节，不使用当前字尚未编码的高位。
- `word-prefix`：已知的当前 4 字节字首字节 + phase + b1；phase=0 时退到已知历史，避免未来信息。

Mozilla 代码窗沿用先前已识别的 Alpha ECOFF `mozilla/components/libgkcontent.so` .text 偏移；资源窗与留出窗也在实验前固定。全部强制组起点为 0，未模拟未知最终多片段拼接相位/接缝。

word-prefix 在 Mozilla code 为 **72058→72680（+622 B）**、resources 为 **24466→24721（+255 B）**，淘汰。opcode 在主代码窗仅比 stride4 好 20 B，留出代码窗却差 4 B，两个资源窗均差于 stride4；不值得为它再堆一套全局上下文。

`analyze.ts::BLOCK` 是 **512 B**。现有多数滤波、短游程吸收会减少碎片；最终 orphan/family/macro 又有独立的成本门。分析类别不等于最终 codec ID，不能把 smooth/repeat 直接计作 BIN、SUB 或 TG。

- Mozilla resources 的 lag8 字节相等率约 **75.47%**，lag16 约 **71.99%**；ooffice code 的 lag4 仅 **5.86%**。这些是原始窗口（不是 BCJ 后残差）的对齐线索；不能用其解释全部 BCJ 后行为或证明全文件收益。
- 上述四窗没有命中“同一分析段同时含 H0>7.5 与 H0<5.5 的 512B 块”的预设筛查；只是否定这些窗口里的该项现象，**不证明整个文件没有高熵污染**。本轮未改孤儿/合并策略。
- samba-mid 的标签全部为 text，但该窗 raw BIN **12553 B** 比 raw TEXT **13688 B** 小；分类标签不能直接当作压缩优劣。没有把这段文本窗包装成 Samba 的机器码段。

为解除这个限制，新增 `scripts/diag/p14/inspect-container.mjs`：对**已有** v19/v20 `.ucz` 只读 <=512 KiB 头部，解析规则、成员位图和精确 group payload 长度，零 CM/零解码。与实际生产 `planHeader` 的 13 项合成元数据断言通过，包含 `r=8192`、混合 v15/v20、WORD-PRE 与跨字节成员位图。它不验证原文 SHA/roundtrip，也不把 `bench-one` 的按段成本分摊误称为精确载荷。

## 5. Unit 4 — osdb 结构、状态学习与匹配

### 5.1 可观测结构

osdb-mid/late 的 ASCII/空白占比约 **80.35% / 80.23%**，混有二进制字段与 NUL。主窗标签为 repeat **244224 B** + binary **17920 B**，而非纯自然语言；raw BIN **72707 B** 明显优于 raw TEXT **75008 B**。

对非全同字节四元组作精确最近重复距离统计：两窗的 **43–55 B 距离计数均为 0**；主导短距离为 2，以及 84/88/89/92/96 等。这里统计的是相同四字节串，不是一个已验证的记录解析器，不能据此断言不存在 43B 记录；但**没有支持把 43–55B 硬编码为主周期的证据**。

### 5.2 实际状态表，不是不存在的 STATE_TABLE

- 每槽 Uint32：高 16 位概率、低 8 位计数；初始 `p=32768,n=0`。
- `DT[n]=floor(65536/(n+1.6))`。text/bin 计数上限 **80**，res/res2d **250**；到上限后继续以非零固定学习率更新，不是冻结。
- 主混合器学习率 **8**，v20 辅混合器 **2**；有按匹配长度分桶及 APM。
- 模型规模：256 KiB 为 CM21/mht4=20/mht8=20；512 KiB 为 22/20/21；4 MiB 为 23/20/22；8 MiB 为 **24/20/23**。这里只读了大尺寸配置，没编码长流。

`profile` 插桩在每个比特更新前记录专家概率，不影响输出：BIN/TEXT 两种插桩结果都与未插桩控制 **SHA 完全一致**。

## 6. 正收益、全文件外推与目标距离

### 6.1 只是条件性算术估算，不是完整文件收益

计算方法：`切片 savedBytes × 标准文件原始字节数 / 切片原始字节数 / 1000`，单位 **十进制 KB**。假设每个输入字节都属于同样的可用规则、具有同样的冷窗收益密度；实际条件显然未全部成立。

**真实最终 group 覆盖未知、完整 CM 表更大、匹配/模型热身不同、词表不同、接缝/格式成本不同，因此这些区间不是置信区间、不是收益上/下界，也不是已经实现的承诺。Mozilla 的代码/资源情景以及同一文件的不同变体不能相加。**

| 候选 / 条件范围 | 各窗实省 B | 全文件机械外推 KB | 判断 |
|---|---|---:|---|
| Mozilla 普通 BIN / Alpha 代码型 | 1480 / 1948 | 289.18–380.62 | 首优先，覆盖未知 |
| Mozilla 普通 BIN / 资源表型 | 3739 / 4064 | 730.57–794.07 | 与上一行互斥的全文件情景 |
| osdb 普通 BIN / 同相位 | 236 / 284 | 9.08–10.93 | 次收益，需完整候选门 |
| MR WIDE6 / low geom | 371 / 464 | 14.11–17.65 | 两个窗口同号 |
| x-ray WIDE7 / low geom | 4 / 7 | 0.13–0.23 | 量级过小，不单独立项 |
| XML WORD-PRE / token3 | 145 / 121 | 2.47–2.96 | XML 有效，NCI 回退 |
| XML WORD-PRE / merge 消融 | 166 / 46 | 0.94–3.38 | 不能与 token3 相加 |
| NCI WORD-PRE / merge 消融 | 33 / 49 | 4.22–6.27 | 自然语言反例，低优先 |

其余正的局部数也在 `summary.json`，但不全是可兑现方案：例如 Webster/Dickens lexical 仍输给 raw；WIDE3 geom 仍输给现有 split 布局；sao flat-side 仍输给合法 TG3。raw text 字符类的单窗外推约 Webster **3.00 KB**、Dickens **3.73 KB**，只有单窗依据；osdb 禁 mht8 约 **2.04–2.62 KB**，存在明确跨文件反例及长流风险。

更可用的下一步公式是 **`适用 group 的真实输入覆盖 × 实测每原文字节收益密度`**，先用既有容器目录确定覆盖，再做完整候选/容器门。当前不能给 Mozilla 的代码型和资源表型擅自分配权重或填入 BIN/BCJ 百分比。

### 6.2 与目标对齐

- 当前锁：**40,233,692 B**。
- 用户给出的 Cubrim v0.3.2 max 约 **40,058,000 B**：差约 **175,692 B**；是用户比较值，不是本轮同机器测量。
- 严格 `<40,000,000 B`：至少再省 **233,693 B**，不是恰好 233,692 B。
- 若按用户的 zpaq **38.83 MB=38,830,000 B** 作近似参照：差约 **1,403,692 B**，仍有 MB 级距离，不能靠本轮零碎几 KB 的机会声称已铺平。

Mozilla 的条件性收益密度有足够数量级支撑 P14.1 实验，但没有已确认的完整 group 覆盖与全文件 CM 增益。**本审计没有把任何这些外推记入基线，也不提供一个虚构的 P14 总量。**

## 7. P14.1 实施优先级（尚未授权本轮修改生产代码）

| 优先级 | 方案 | 投入产出与零回退要求 | 编码/内存影响 |
|---|---|---|---|
| **P1** | 普通 BIN 可选 b4/b8/b12 + phase 内核 | Mozilla 代码/资源四窗、osdb 两窗均正；先限有证据的直接 BIN 候选，BCJ25 回退必须能被完整门拒绝。不能只改全局 bin 分支 | 仍九表、每字节增加少量历史读取。需要考虑新增完整候选本身的成本，不能把单个内核速度等同于流水线速度 |
| **P2** | WIDE6 低平面 geom 上下文候选 | MR -464/-371 B，改动小；x-ray 仅个位数字，不单独推广。完整旧布局/载荷保留 | 表数不变；多算几何哈希，仍需额外候选比较。不要新增无收益的 MSB 表 |
| **P3** | WORD-PRE 上下文候选 | XML token3 -145/-121；merge 在 XML/NCI 小幅正、自然语言负。保留 P13.1 准入及旧 WP/v20，不能因 raw 新内核胜出而跳过旧 WP 胜者 | 不是重做词典格式。lexical 展开还增加字符处理却未赢 raw；不作为主实现 |
| **P4 / 延后** | raw text 字符类、osdb mht8 策略 | 收益小，部分仅单窗；mht8 有跨文件回退及长流风险，需更多证据 | 不值得为几 KB 增加所有文件的完整试探；不全局调学习率/表上限 |
| **淘汰** | WIDE 第十表、粗 MSB 替换、sao 当前跨组/flat 接法、当前字首上下文、全局减半学习率/加倍计数 | 多数明确回退，或只赢较差控制却输给已有候选 | 不增加生产维护/内存负担 |

**P1 的孤立时序对照：**两个串行、非并发的 256 KiB Mozilla-code 进程，旧/新编码分别 **1151 / 1087 ms**，解码 **1047 / 1089 ms**；同一 payload 分别与初测 SHA 一致。只说明这一对试验未出现数量级开销，**单次对照不是可信的 -5.6% 吞吐结论**。其它探针很多并行运行，其耗时不能拿来排名百分比；1687.0 s 本机流水线时间没有在 Arena 重测。

### 必须守住的实现边界

1. 新上下文改变码流数学：必须有可区分的内核/版本语义（如后续独立 v21 设计）；现有 v20 及 <=v19 解码不变，不占用真实 `r=8192/0x2000`，也不把容器 recovery 0x2000 当空闲位。
2. 先保留 **实际 P13.1 完整载荷/容器**，再严格计入全部格式、group 与容器成本。短探针只决定是否值得尝试，不能证明被跳过旧赢家不会回退；不要重演 P13 XML 失准入。
3. 不调整本轮已经有效的 BCJ25 路由/缓存机制，不顺带修改 family/macro/orphan 启发式。若后续扩展 SUB/TG 内部 bin，须另测其真实变换后流，不能借普通 BIN 的收益外推。
4. 增加一次完整候选可能抵消此前调度节省；可以另研究共享不变上下文的双流评估，但**本轮未实现/测量其速度**。只有本机同口径 12 文件/16 核复验才可承诺总量和时间。
5. “更深红利”下一层值得量化的是实际 Alpha/资源 group 覆盖、8 字节表结构、长流上下文冲突与 field 类型；这些只是后续研究方向。没有用 zpaq 的总量反推本系统某一未测模型能省多少。
