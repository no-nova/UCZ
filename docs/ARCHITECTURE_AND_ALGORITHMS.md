# UCZ 架构与算法

本文是 `src/lib/` 的完整技术说明：流水线怎么走、容器怎么写、33 个变换各自在算什么、CM 内核的概率模型如何工作、上下文策略如何分派，以及——同样重要——**这套设计在理论上哪里看不见**，以及实测差距的来源。

写作原则：
- 每个数字都来自仓库内的源码、冻结回执（`scripts/diag/**/results/`）或用户本机全量验证的转录。凡是沙箱未证明的，都明确标注。
- 不把"有界切片的实验"说成"全文件通过"。
- 不假设读者已经读过 P9–P16 的任何报告。

> 术语：**UCZ** 是容器格式名；**段（segment）** 是容器里一条"规则 + 长度"记录；**组（group）** 是若干段共用一份 CM 模型状态与一条载荷流；**规则（spec）** 是 `{id, s, r}` 三元组。

## 1. 端到端自适应流水线

入口是 `compressAdaptive()`（`src/lib/codec.ts`）。它不是一个"选个算法压一下"的函数，而是一条**逐级筛选、每级都有独立的完整容器复核**的流水线：

```
compressAdaptive
├── compressAdaptiveImpl                 ← 地形分析 + 逐段选规则 + 分组编码
│   ├── analyze()                        1.1 把字节切成地形块
│   ├── chooseSpec()                     1.2 每段试探候选规则
│   │   ├── featureCandidates()          多维特征并集生成候选池
│   │   ├── 采样/探针筛选                 有界预算的代价估计
│   │   └── 完整候选比较                 严格更小才采纳
│   ├── mergePlanSegments()              1.3 同规则相邻段合并
│   ├── orphan 坍缩                      1.4 小孤立组并入主力组
│   ├── macroUniformGate()               1.5 全局"单组化"提案
│   │   └── finishPreparedPlan()         1.6 宏候选的完整容器复核
│   └── encodePreparedPlan()             1.7 按组编码 + 序列化
├── refineContextCandidates()            2   v21 组上下文（mode 1..7）逐组 A/B
├── refineRec2()                         3   整文件二滞后递推残差（id32）
└── refineBitplane()                     4   整文件位平面（id33）
```

**顺序不是随意的**：越靠前的阶段越保守、越贴近旧的字节身份；越靠后的阶段越是"整文件级别的替代容器"。每一层都遵守同一条铁律：

> **候选容器必须严格更小才替换，相等一律保留原方案。**

这条规则让流水线可以安全地叠加许多"可能会输"的启发式——输了的候选只是白花时间，不会让任何文件变差。

### 1.1 地形分析（`analyze`）

`analyze()` 把输入扫成 `blocks`（固定/半固定窗口），再合并成 `segs`，每段带一个 `cls` 类别标签。它的输出是后续所有阶段的坐标系统：候选生成、采样窗口对齐、孤儿组判定、"部分窗口不能借用"的边界检查都以 `segs` 的边界为准。

关键点：**分析只产生"地形提示"，不产生最终决定**。`cls` 会参与候选池的构造，但任何规则都必须自己通过编码比较才能落地。

### 1.2 逐段候选与筛选

每段调用 `chooseSpec()`。候选池由 `featureCandidates()` 按多维特征并集生成（`planTuning.featureCandidates`），而不是被 `analyze` 的单一 `kind` 锁死。候选池可能包含：恒等 TEXT/BIN、各种 DELTA、GRAD-2D、TRANSPOSE 族、BCJ、WIDE-16、MICRO 等。

筛选分三层，成本逐层上升、淘汰逐层收紧：

1. **有界采样**：`sampleBudgetForSegment()` 给出采样预算。预算下限 `planTuning.sampleFloor = 8192`、上限 `sampleCap = 16000`；当"段数 ≤ 4 且单段 ≥ 1 MiB"时用 `soloSampleCap = 65536`，因为这种文件一条规则要作用于几十 MB，16 KB 证据太少。
2. **同步探针**：部分族（TRANSPOSE 布局、TG、SUB 模式、二维列、WORD-PRE 前缀、宽行/锚点小窗）走同步有界探针。
3. **完整比较**：进入最终候选的规则会在真实字节上完整编码一次，严格更小才采纳。

历史 ID 的取舍是显式的旋钮而非隐式行为：`dropZeroHitIds` 剔除普查中**零命中**的 9 个 ID（RLE/ANCHOR/ANCHOR_FOLD/MICRO/GRAD/GRAD_V2/PEEL/WIDE_GRAD/SUB_TRANSPOSE_V3）；`dropLegacyV12Ids`（默认关闭）才剔除被 V3 支配的 v1/v2 代 ID——因为那批**不是**零命中（BIN_V2 曾胜 50 次、覆盖 8.95% 字节），有体积风险，必须单独归因。

### 1.3 段合并

`mergePlanSegments()` 把相邻且规则相同的段并成一段。合并有例外清单：ANCHOR / PEEL / SUB_TRANSPOSE / SUB_ANCHOR / MICRO 不合并（它们的语义依赖单段边界）；FILL 段只有首字节相同时才能并（否则"常量"不成立）。

### 1.4 孤儿组坍缩

碎片化的地形会产生很多"小组"：每个独立组都要付一次 CM 冷启动（实测每多切一刀值 23–41 KB），而这些组的收益往往覆盖不了这笔开销。

`orphanProposalForProbe()` 的准入是**字节数**而非段数：
- `< 2 MiB`（`orphanMaxBytes`）**且** `< 20%` 输入（`orphanMaxFraction`），两个条件都取严格小于；
- 排除 FILL；
- 一次批次，最多 `orphanMaxCount` 个不同规则组（小文件 24，大文件 64）；
- `orphanAllowRawStore` 允许吸收 STORE/RLE 这类"裸存"组——它们本来就是原样存盘，恒等并入主力 CM 流不丢信息，却省掉一整份规则头 + 一次冷启动。

候选最终仍要过完整容器比较。

### 1.5 全局宏提案（macroUniformGate）

孤儿吸收解决的是"小组并进主力组"。但另一种失败模式是**主力组本身就不该有这么多**。P8 §5 的实测：整份 samba 用单一 `TEXT_V3` 连续编码是 3,503,477 B，而当时 2,247 段 / 18 组的产物是 3,646,793 B——流水线输了 143,316 B（3.93%）。

做法：挑一段**跨组交界**的代表性窗口，比较"按当前规则各自编码"（`sep`）与"全部并成单一规则连续编码"（`uni`）。统一方案在窗口上更小且超过 0.2% 边际才提出候选。

三个设计细节值得单独说明，因为它们各自对应过一次真实的失败：

**(a) 窗口预算按"有信息量的字节"计，不按原始跨度计（P16.2 修正）。**

窗口扫描原本用 `merged[hi].end - merged[lo].start > WIN` 判断，即按**原始字节跨度**卡预算。而 `WIN` 在 P13（`269bcdc`）从 1 MiB 收紧成 `GROUP_KERNEL_PROBE_BYTES = 192 KiB`，以复用 P13 的内核筛选预算。两者相撞的后果是：一段长 FILL 游程（常量）就能把窗口撑满，把第二个真实的非 FILL 片段挤出窗口，于是：

- `inWin.length < 2` 或 `bySpec.size < 2` 命中，门直接返回 `null`；
- 门**根本没看见**本来想看的碎片。

这正是 `testP9Macro` 里 `assert.ok(partial.macroComparison?.sample)` 失败的真实原因，而且它在 `0912a8f` **之前**就存在（在 `1d25fec` 上可复现）：`0912a8f` 没有引入这个 bug，只是延续了它。

修正后的不变式是：**窗口内非 FILL 字节总量 ≤ `WIN`**。FILL 段不进 `inWin`、不参与定价，因此把它的长度记入预算只会白白挤掉真正的合作者。修正后探针成本的天花板与原实现完全相同（仍然 ≤ `WIN` 字节被编码），但窗口不再被常量游程劫持。

同时把采样的语义写清楚：`macroComparison.sample.bytes` 现在是**被定价的信息字节数**（`bestInfo`），原始窗口跨度另记为 `sampleSpanBytes`。这个区分是必要的——用原始跨度做断言会得出错误结论（见 §2.6）。

**(b) 窗口下限同样按信息字节计。**

`MIN_PROBE_BYTES = 16 KiB`：判决边际是 0.2%，在 16 KiB 上约 33 B，已经大于实测 ≤30 B 的组间帧头成本；再小的样本只会被帧头噪声支配。

**(c) 统一候选里必须带转置族，但步长只能来自真实证据。**

只试 `TEXT_V3` / `BIN_V3` 时，门看到的最好选择可能比流水线还差，于是正确地拒绝——而那 26,348 B（mozilla 中部 1 MiB 上 `TG_V3(s=4)` 相对流水线的 −8.82%）就全部留在桌上。反过来 samba 上所有统一规则都更差（`TEXT_V3` +919 B、`TG_V3(s=4)` +19,605 B），所以不能"无条件并组"。

步长来源严格限定为三类真实证据，不凭空试无效转置：
1. `detectRecordStride()` 对**被定价的那份字节**的判定（P16.2 起改为拼接后限 64 KiB 的缓冲，使探测成本与窗口跨度脱钩）；
2. 窗口内已存在的转置族规则的 `spec.s`（线上已经认为它是记录宽）；
3. 定长记录的典型宽度 4 / 8。

**成本上限**：`planTuning.macroProbeBytes`（默认 = `GROUP_KERNEL_PROBE_BYTES` = 192 KiB）是显式旋钮。把它调小只会让门看得更少、更容易返回 `null`，**不会**放宽任何采纳条件；最终仍由完整容器严格更小裁决。这条旋钮是为了让"跨度远大于预算"的分支能在有界时间内被测试覆盖（见 §2.6）。

### 1.6 宏候选的完整复核

`finishPreparedPlan()` 做四件事：
1. 编码原方案 → `baseline`；
2. 按提案重写段规则 → 编码 `candidate`；
3. 若提案是恒等 TEXT3/BIN3，再跑一次 `contextMacroProbe`（4 路 × 192 KiB 采样）看上下文是否该跟着换；
4. 记录 `macroComparison`（`baselineBytes` / `candidateBytes` / 双方 header / 版本号 / `accepted`），**只有 `candidate < baseline` 才采纳**。

候选失败（异常、非法 spec、非法 plan）不会破坏已经完成的 `baseline`，错误显式写入 `comparison.error`，不伪装成"已采用"。

### 1.7 分组编码与序列化

`encodePreparedPlan()` 把段按 `(id, s, r)` 分组成 `PlanGroup`，每组：
- 把成员段的字节拼接成一条**逻辑流**；
- 为该逻辑流分配一份 CM 模型状态（这是"组"的定义：共用模型 + 共用一条载荷）；
- 编码出一条载荷 `payload`，记录 `modelFlags`、`context`、`kernel(v15/v20)`、`wordPre`。

然后 `planHeader()` 写出容器头与段表。**成本函数与实际序列化必须调用同一个 `planHeader`**，否则"报价"与"成交"会漂移——这是 P9 反复踩过的坑。

`planSpecReservations()` 保证字典 key 的唯一性：一个 key 标识一条独立的流，不只是规则名；迟到的转置晋升和缓存别名都不能偷别的组的 key。

### 1.8 后处理三级

| 阶段 | 覆盖面 | 触发 | 采纳条件 |
|---|---|---|---|
| `refineContextCandidates` | 逐组 | 组 ≥ `CONTEXT_MIN_BYTES`(16 KiB) | 载荷与容器**都**严格更小 |
| `refineRec2` | 整文件 | 首 2 KiB H0 > 7.5 且 `detectRec2` 命中 | 容器严格更小 |
| `refineBitplane` | 整文件 | 熵门 **或** STORE 主导门 | 容器严格更小 |

这三级的顺序也有含义：上下文细化只改单组模型、不改地形，所以先做；REC2 和位平面是"整文件换一种表示"，会推翻分段结构，所以放最后，且后者永远看到前者的产物。

### 1.9 worker 并行与确定性

`workerTuningMatchesDefaults()` 是并行的**前置条件**：只要任何诊断旋钮与 worker 默认值不同，就显式退回串行（`parallelReport.reason` 会写明原因）。理由很直接——worker 是独立进程，改不了主线程里那些全局 tuning 对象；如果允许"主线程改了旋钮但仍并行"，主进程与 worker 会用不同参数编码同一份数据。

确定性由三条保证：
1. **候选顺序稳定**：并列时按索引裁决（`clearProbeWinners` 的 `a.i - b.i`）。
2. **分组不依赖调度**：组是由 `(id,s,r)` 与段边界决定的纯函数，与哪个 worker 先完成无关。
3. **无模块级可变模型状态**：`bitcm.ts` 的模型状态必须放在 `createBitCMModel()` 返回对象里。早期版本用模块级 `Uint16Array`，并行时非重入，会串味。

## 2. 容器格式 v7–v21

### 2.1 头部

```
magic "UCZ" (55 43 5a) | version (u8) | [version-specific flags] | rawLen (varint) | 段表 | 组字典 | 载荷
```

- 低版本（v7–v15）不写配置头，这是保持 P10 字节身份的一部分。
- 只有**最终实际使用**的模型配置才会被写进 flags：候选即使分配过 24 位表，只要最终没选中，就不能增加任何字节。成本比较与序列化共用同一个 `planHeader`。

### 2.2 版本与能力

| 版本 | 十六进制 | 新增能力 |
|---|---|---|
| v7–v15 | `07`–`0f` | 基础地形 + 分族规则；v15 引入双流内核（`r \| 0x8000` 标记 v15 kernel） |
| v17 | `11` | 分区容器 + `textOn` 语义（`0x4000` 标记 WORD-PRE） |
| v18 | `12` | 24 位 CM 的低 8 位语义，1 B 配置 |
| v19 | `13` | 24/23 位高档配置，2 B 配置（`0x100` CM24、`0x200` mht8-23、`0x400` P11.1 mht4=20） |
| v20 | `14` | 变换族与结构上下文（`V20_FLAG_TRANSFORMS` / `V20_FLAG_CM`） |
| v21 | `15` | 组上下文（`V21_FLAG_CONTEXTS`）+ REC2(id32) / BITPLANE(id33) |

### 2.3 段表与组字典

段表每项记 `(start, end, spec.id, spec.s, spec.r, groupIndex)`。组字典每项记该组的 `payloadLength`、`kernel`、`wordPre` 与上下文码。

`spec.r` 是**按规则解释的复用字段**，这是格式里最容易看错的地方：

| 规则 | `r` 的含义 |
|---|---|
| `TRANSPOSE` / `TRANSPOSE_G` / `SUB_TRANSPOSE` | 记录步长（2..64） |
| `GRAD` / `WIDE_GRAD` | 行跨度（`r ≥ 256`，`wide-geom` 要求 256..8192 且偶数） |
| `REC2` | 恒为 1 |
| `BITPLANE` | `1` = 旧字节 CM 位平面；`2` = bit-CM（`BITPLANE_BIT_CM`） |
| 其余 | 恒为 1 |

### 2.4 modelFlags

v20/v21 的组级标志由**载荷自身**决定（`payloadModelFlags()`），不是调用方声称的：

- `V20_FLAG_CM`：该组使用 v20 CM 内核；
- `V20_FLAG_TRANSFORMS`：变换族可用；
- `V21_FLAG_CONTEXTS`（容器 uint16 的 `0x4000`）：该组带上下文码。

注意 `V21_FLAG_CONTEXTS = 0x4000` 与组级 `r` 的 WORD-PRE 位 `0x4000` **数值相同但命名空间不同**：前者在容器 uint16，后者在组字典的 `r`。这种刻意的值重叠必须靠"哪个字段"来消歧，不能靠数值判断。

组上下文的 3 个比特在 `r` 里：`GROUP_CONTEXT_SHIFT = 17`、`GROUP_CONTEXT_MASK = 0xe0000`，与低位的 v15 kernel / WORD-PRE 位不冲突。

### 2.5 向后兼容与越界拒绝

解码器对非法组合是**响亮拒绝**，不是静默降级：

- v18 的 8 位已全部占用，v19 的 `0x400` 才用于 P11.1 的 mht4=20 分档；孤立 `0x400`（同时没有 `0x100`/`0x200`）拒绝。
- 旧 v19（无 `0x400`）仍按 P11 的 mht4 = 20/21/22/22 分档解码，包括只携带低 8 位的旧 v19。不能简单改旧 v19 的默认 mht4，否则旧流会被错误解码。
- `REC2`/`BITPLANE` 组：必须 v21、必须 v20 CM、不得 WORD-PRE、不得带组上下文、`s = 1`、必须带 `V20_FLAG_TRANSFORMS`；`REC2` 要求 `r = 1`，`BITPLANE` 要求 `r ∈ {1, 2}`。
- 位平面载荷的每平面长度字段用 **bit 31** 标记"这是 bit-CM 模型"；旧 r=1 载荷的字节完全不变。模型/标志不匹配是解码错误，不是静默垃圾。

### 2.6 一个被格式细节咬过的例子（P16.2）

`testP9Macro` 的断言原本只有 `sample.bytes < span.length`（原始跨度）。修好 §1.5(a) 之后，一条 1.13 MiB 跨度、三段各 28 KiB 的用例在中间态报出 `sample.bytes = 581,632`——它确实小于跨度，但**大于**三段的信息总量 86,016。这个数字说明 `sample.bytes` 报的是原始窗口跨度，不是被定价的字节。

两处都要修：门的预算语义（§1.5a）与报告语义（`sample.bytes = 信息字节`，`sampleSpanBytes = 原始跨度`）。为什么必须改报告语义而不是只改断言：`sample.bytes` 的唯一用途就是"门到底看了多少证据"，用跨度冒充它就等于把常量游程算成了证据。修完后的不变式是：

```
sample.bytes ≤ min(INPUT_CAP, 窗口内非 FILL 字节)  且  sample.bytes ≤ 总信息字节
sampleSpanBytes ≤ 输入长度
```

断言改到这两条上，才是这条用例真正想守的东西：**部分窗口不能被借用为全组**（`reusedProbePayload === false`）。

## 3. 变换目录（id 0–33）

所有变换都是**可逆的字节级映射**，且都满足同一个模式：`残差 = f(原始, 邻居)`，然后残差交给 CM。变换的价值完全来自"残差的条件熵低于原始字节的条件熵"，不存在任何针对具体文件的特殊处理。

### 3.1 裸存与游程（id 0–3）

| id | 名称 | 做法 | 数学 |
|---|---|---|---|
| 0 | STORE | 原样存盘 | 恒等。用于"任何模型都无法预测"的高熵区，避免膨胀 |
| 1 | FILL | 单字节 + 长度 | 段内全部相同。`O(1)` |
| 2 | RLE | `(byte, count)` 对 | 适合长游程 |
| 3 | O0 | 零阶算术编码 | 只学字节频率 `H0 = -Σ p log2 p` |

STORE 是"压缩器承认失败"的合法出口，也是位平面路径的触发信号之一（§3.9）。

### 3.2 差分族（id 6, 8, 27）

`DELTA(s)`：`r[i] = d[i] − d[i−s] (mod 256)`。当 `d[i] ≈ d[i−s]` 时 `r[i]` 集中在 0 附近，一阶熵下降。解码是前缀和 `d[i] = r[i] + d[i−s]`。

`D16(ch, order)`：把字节流当 16 位小端采样，
- `order=1`：`pred = a`（前一个采样），`res = sample − pred`；
- `order=2`：`pred = 2a − b`（线性外推），`res = sample − pred`。

这两种都是"把音频类缓变信号压成小残差"的经典手段。`order=2` 在纯音/仪器采样上通常更好，在噪声上更差——所以必须实测择优。

`DELTA_V3(id 27)` 是增强上下文版：**同一份残差**，但交给带"字节相位 + 多阶邻居"上下文的 v20 CM。它在 `context-policy` 里还可以叠加 `xform-bin` / `xform-bin-stride4`。

### 3.3 二维梯度族（id 7, 21, 26, 31）

`GRAD-2D(s, r)`：把一维字节流还原成"像素跨度 `s`、行跨度 `r`"的二维网格，用 **LOCO-I MED** 预测：

```
a = d[i−s]  (左)
b = d[i−r]  (上)
c = d[i−r−s](左上)
med(a,b,c) =  median 意义上最接近 a+b−c 的那个
res[i] = d[i] − med(a,b,c)
```

MED 的性质：`c` 落在 `[min(a,b), max(a,b)]` 之外时退化成 `max/min`（即"取较近的邻居"），落在区间内时用 `a+b−c`（平面拟合）。这是无损图像压缩的标准预测器，对带噪声边缘比线性预测稳健得多。

`WIDE-16(id 31)` 是宽行版本：`detectWide16Lag()` 在一个很宽的滞后范围内找行跨度，然后按实压在"二维 MED"与"16 位差分"之间择优。它的 `wide-geom` 上下文要求 `s ∈ [6,8]`、`r ∈ [256,8192]` 且 `r` 为偶数。

### 3.4 转置族（id 9, 10, 15, 22, 28, 30）

定长记录（结构体数组、定点采样、32 位整数序列）的问题是：同一列的高位字节彼此相似，但线性的高阶上下文模型看到的是"跨列混合"的历史。

`TRANSPOSE(s)`：把 `N` 条 `s` 字节记录按列切成 `s` 条子流，每列独立选择原样/填充/游程/上下文/差分编码。解码时按记录交错回去。

`TRANSPOSE_G(s)`（id 10）与 `TRANSPOSE_G3(s)`（id 30）：不自作主张按列切，而是**自适应组合相邻列**再联合编码，保留记录内的跨列关联。id 30 另外在组内做逆序与相位上下文。id 10 在组编码阶段由 ENCODE 侧对**三种布局**各编一次取最小——所以它不能借用单布局的探针载荷缓存。

`SUB_TRANSPOSE(s)`（id 15/28）与 `SUB_ANCHOR(s)`（id 16/29）：同源列按**模态**分流成独立子通道，并比较"每通道独立模型"与"共享模型"两种，取小者。samba 这类文件最终就是落成一条 `SUB_TRANSPOSE(s=38)` 组。

`TRANSPOSE-2D(id 22)`：类 ST 图像（每个像素"1 字节颜色 + 1 字节属性"）的经典结构。做法是**列采样剥离**：把偶数位（颜色）与奇数位（属性）分开，颜色用二维上下文、属性用转置，并与传统转置实际比较后取小。

> 注意：id 22 的 `desc` 里写的是"列采样剥离及二维跨列上下文，实际比较传统转置"。这句话是本实现与 ST 论文的差别所在——它不假设数据一定是 ST 布局，而是把 ST 当作一个候选。

### 3.5 分支与锚点族（id 11, 12, 13, 14, 20, 25）

`BCJ-x86(id 11)`：x86 的 `E8/E9` 后面跟 32 位小端 `rel32` 相对跳转。**为什么把相对变绝对有用**：同一段代码在不同基址被重定位后，`rel32` 的字节完全不同，但目标地址相同。加/减去 `pc = base + i + 5` 后，函数调用的目标变成稳定的绝对地址，跨版本、跨段落高度重复，CM 才能吃到。

本实现的两个细节：
- 不是标准 XZ BCJ 流，是独立的可逆归一化；
- 位置全部按模 2^32 计算；
- **每个扫描到的 rel32 字段都必须被消费（`i += 4`），即使 filter 拒绝**。否则嵌套的 `E8` 会改写前一个被拒操作数的最高字节，导致逆变换走不同分支——这在非零/回绕基址上尤其致命。

`BCJ3/BCJ25` 是同一个变换接不同 CM 内核（v15 双流 / v20 结构上下文）。

`ANCHOR-ALIGN(id 12)`：按语法锚点划分**变长**行，记录行长，前 32 字节按列组编码、余下顺序编码。
`ANCHOR-FOLD(id 13)`：保持原始长度的变长行/列折叠，再共享上下文编码。
`PEEL(id 14)`：按定长记录分列后，对每列**再次**扫描地形并逐子区域试编码（最多一层）。这是"递归地形"，深度上限 1 是刻意的——再深一层，收益被模型冷启动吃掉。

`MICRO-LIN(id 17)`：在区域内用邻居**现场拟合**一个量化线性预测器，把 5 字节种子写进容器，然后编码可逆残差。它是"为这一小段数据局部训练一个最小模型"的思路。

### 3.6 模型代数（id 4/5 → 18/19 → 23/24）

这是同一族规则的三代演进，`s=1, r=1` 恒成立：

| 代 | id | 名称 | 状态数 |
|---|---|---|---|
| v1 | 4 / 5 | CM-TEXT / CM-BIN | 7 / 8 路 |
| v2 | 18 / 19 | TEXT2 / BIN2 | 词前缀 / 四字节结构相位 |
| v3 | 23 / 24 | TEXT3 / BIN3 | **9 路** |

`NCTX = { o0:1, o1:2, text:7, bin:8, res:6, res2d:8 }` 是**基础**路数；v20 内核在此之上再加结构相位与匹配路，v21 再把 9 路里的一部分换成策略化上下文（§4）。

TEXT3 与 BIN3 的区别不是"数据是文本还是二进制"这种标签判断，而是**九路上下文的内容不同**：TEXT3 用词边界/字符链，BIN3 用结构相位/稀疏跳步。两者最终靠实压比较——这在 P16.2 的固定载荷对照里看得非常清楚：`mozilla-mid` TEXT3 24,705 vs BIN3 22,071（BIN3 好 10.7%），而 `samba-c` 反过来是 10,813 vs 11,262（TEXT3 好 4.0%）。**同一个文件家族里两个方向都存在**，所以只能实测。

### 3.7 WORD-PRE

`wordpre.ts` 是文本专用的预处理：把词切成 token、维护词典，正文只在词典**前缀**上编码。组级用 `r` 的 `0x4000` 位标记。

它有独立的准入规则（P12）：只对 `p12-contiguous-body` 策略的**正文前缀**计价，词典/框架的完整成本在采纳时另付。这个区分是必须的——否则"前缀更小"会被误当成"容器更小"。`wordPreGate` 因此把 `bodyBytes` 与 `plainBytes` 分开记录。

### 3.8 二滞后递推残差 REC2（id 32）

**动机**：有些数据既不是文本、也不可差分，但由递推关系生成——比如"每次 `rand()` 返回值的低字节"。

**检测**（`detectRec2`）：
1. 前 2048 字节的一阶熵必须 **> 7.5**（否则直接放弃，这是必要条件不是充分条件）；
2. 在 `b ∈ [2,63]`、`a ∈ [1,b)`、`op ∈ [0,4]` 上穷举 **1953 个滞后对 × 5 种运算**，每种在前 2048 字节上算残差熵，取最小；
3. 双端验证：**训练窗**与**尾窗**都必须满足 `closeRatio > 0.8` 或 `H < 5`。

固定成本 1953 × 5 × 2048 次运算，与文件大小无关。

**五种运算**：

```
op0: pred = x + y      op1: pred = x − y      op2: pred = y − x
op3: pred = −x − y     op4: pred = x XOR y
res = (x − pred) & 255        (op4: res = x XOR a XOR b)
```

**流格式**：长度恰好 `n + 3`——`[op, a, b]` 三个参数字节，接前 `b` 个**原始**种子字节，接其余残差。种子是必须的：递推只能从 `i ≥ b` 开始有定义。

**为什么它能打到 8.69%**：这份输入的高位字节来自一个 20 位 LFSR，`x_i` 可由 `x_{i−a}, x_{i−b}` 的异或精确重建，残差几乎全是 0。rec2 把"看起来是 8 bit/字节的噪声"翻译成"每字节约 0.7 bit 的残差"，这是**结构**而不是统计，所以任何纯 CM 都拿不到。这是本设计里"变换理论 > 上下文建模"最干净的例证。

**边界**：`a ≥ 1`、`a < b ≤ 63`；`n ≥ 16384`；解码时 `n ≥ b`；参数非法或长度不符直接报错。

### 3.9 位平面 BITPLANE（id 33）

同一份数据，按位切开就是 8 条独立的二值序列。若数据的高位是噪声、低位有结构（或反之），逐字节建模永远看不见——字节模型的上下文是"字节"，跨不过位平面。

**布局**：`q = floor(n/8)` 个完整 8 字节打包成一个平面字节，第 `b` 个平面取每个字节的第 `b` 位（LSB-first 记为 bit 0）。尾部 `n % 8` 字节另存。

**两种平面模型，由 `r` 区分**：

| `r` | `BITPLANE_BYTE_CM = 1` | `BITPLANE_BIT_CM = 2` |
|---|---|---|
| 模型 | 打包成字节后交给字节级 BIN CM | 直接对位建模（§5） |
| 阶数 | 字节阶 | 位阶 16 / 20 |
| 兼容 | 旧路径，字节完全不变 | P16.2 新增 |

**为什么必须要有 r=2**：字节 CM 只能把 k 位历史看成"分数个字节的前缀"，order-16..20 的**位**结构对它不可见。实测 AITDCC/L 的低 4 个平面报告 16..20 阶结构，而旧路径把它整个留在 STORE。

**触发（两个，都是必要条件）**：
1. `bitplaneEntropyGate`：前 2 KiB 的 `H0 > 7.5`；
2. `bitplaneStoreTrigger`：`raw ≥ 16384 && stored*2 > raw`，即"字节级 CM 全线失败、整文件落到 STORE"。

第二个触发是 P16.2 加的，理由是 AITDCC/L 实测：字节级模型处处失败、容器停在 3,000,021 B（ver 7），但它的低位平面有可建模结构。普通文本/代码能压，因此不会被这个条件碰到。

**采纳（不给统计猜测留口子）**：

```
bitplaneFullProof(data) → 对 8 个平面各自跑真实 bit-CM 编码
  平面 b 只有在 coded.length + 4 < q 时才标记 proof[b]
encodeBitplanesBitCM   → 再检查一次
最终                   → 容器严格更小才替换
```

**为什么用全平面仲裁而不是采样**：这是 P16.2 最重要的一条负面结果。order 16 有 65,536 个状态、order 20 有 1,048,576 个，16 KiB 采样几乎填不满任何状态，实测比率会塌向 1.0。在 5% 噪声的 L 形代理上，采样**否决了每一个全量编码能压到 0.09 的平面**（回执 `p16-bitplane-L--noise5` 作为失败证据保留）。全平面仲裁的代价是 ≈1.2 s/MiB 编码、≈0.34 s/MiB 解码，换来的是"随机平面绝不可能被采纳"——因为模型自己的输出就比原始平面大。

**为什么随机数据不会被误伤**：`encodeBitplanesBitCM` 在没有任何平面被采纳时返回 `null`，调用方保留原容器。SHA-256 随机 64 KiB / 256 KiB 实测字节完全不变（回执 `p16-bitplane-production--p162-random`）。

**长度约束**：`n % 8 == 0`（平面布局不能有尾部残缺字节参与仲裁），另受 `MAX_OUTPUT_BYTES` 上限约束。

## 4. 上下文策略（`context-policy.ts`）

v21 把"用哪种上下文"提升为组级、显式、可编码的元数据，而不是内核里的隐式分支。

```ts
CONTEXT_CODES = { 'bin-stride4': 1, 'wide-geom': 2, 'wp-token3': 3, 'wp-merge': 4,
                  'text-sparse5': 5, 'xform-bin': 6, 'xform-bin-stride4': 7 }
```

| mode | 名称 | 允许的规则 | 上下文内容 |
|---|---|---|---|
| 0 | （无） | 任意 | 内核默认 9 路 |
| 1 | `bin-stride4` | BIN / BIN2 / BIN3（`s=1,r=1`），或 `TRANSPOSE_GROUP_V3`（`s∈[2,64]`,`r=1`） | 第 4 字节相位 + 稀疏跳步 |
| 2 | `wide-geom` | `WIDE_GRAD`，`s∈[6,8]`，`r∈[256,8192]` 偶数 | 几何位置（行/列） |
| 3 | `wp-token3` | WORD-PRE 组 | 词 token 三元组 |
| 4 | `wp-merge` | WORD-PRE 组 | 合并后的词上下文 |
| 5 | `text-sparse5` | TEXT / TEXT2 / TEXT3（`s=1,r=1`） | 5 个稀疏字符上下文 |
| 6 | `xform-bin` | `DELTA` / `DELTA_V3` / `TRANSPOSE_2D` / `GRAD_V3` | **同一份残差**喂恒等 BIN v20 |
| 7 | `xform-bin-stride4` | 同 mode 6 | mode 6 + stride-4 的 H[8] 上下文 |

**mode 6/7 是这套设计的一个关键抽象**：它把"变换"与"模型"解耦。传统做法是给每个变换写一个专用模型；这里先做残差变换，再用**恒等的 BIN 模型**去编码残差，只是把上下文换成残差专属的。这样新增变换不需要新增模型，只需要在 `contextSpecAllowed()` 里声明它能配哪些上下文。代价是必须显式约束（`!wordPre`、`s=1`、`r=1`），否则会造出无法解码的组合。

**准入是三重门**：
- `contextSpecAllowed(context, spec, wordPre)` —— 静态合法性，防非法组合；
- `CONTEXT_MIN_BYTES = 16 KiB` —— 太小的组不值得一次模型重跑；
- `CONTEXT_SCREEN_MIN_BYTES = 256 KiB` / `CONTEXT_PROBE_BYTES = 192 KiB` —— 大组先采样筛；
- `contextUpgradeWins(basePayload, baseContainer, candPayload, candContainer)` —— **载荷与容器都必须严格更小**。

最后一条要特别强调：只用载荷比较会出现"载荷更小、容器更大"（多出 r 标志、版本升级等额外字节）。所以两把尺子都要过。

## 5. CM 内核

### 5.1 结构

一个字节 = 8 个比特，逐比特二值建模。每个比特：

1. 用当前部分字节 `c0`（含哨兵 1，从 1..255）与各路上下文 `hashes[i]` 算出表索引；
2. 从每张表读出概率，转换成 stretch 域；
3. 线性混合（点积）→ squash 回概率域；
4. 交给算术编码器；
5. 用实际比特更新每张表与混合权重。

```
idx[i] = ((hashes[i] XOR imul(c0, 0x9e3779b1)) * 0x85ebca6b) >>> shift
```

哈希混合用两个大奇数乘子做扰动，再右移 `shift` 落到表大小。`shift` 由 `maxTableBits` 决定（21..24）。

**表布局**：每张表是 `Uint32Array`，**高 16 位是概率、低 8 位是更新计数**。原实现用 `Uint16Array` + `Uint8Array` 两张表，同一槽位要两次随机访存；合并成一次读改写后，每比特的高延迟访存从 `2·nctx` 降到 `nctx`。这是纯性能改动，不改比特流。

### 5.2 状态表、squash/stretch

```ts
STRETCH[p] = round(ln(p/(1-p)) * 256)      // 概率 → logit，定点
SQUASH[x]  = round(4096 / (1 + e^{-x/256})) // logit → 概率
```

`squash` 用 33 项查表 + 区间插值；`stretch` 用 4096 项查表。定点数的意义：整条热路径只有整数运算与查表，`| 0` 与 `>> 16` 的舍入**必须**在编解码两侧完全一致，否则会漂移出不同的比特流。

概率估计本身用计数对：

```
p = ((2*n1 + 1) * PSCALE) / (2*(n0+n1) + 2)     // Laplace 平滑
```

加 1 的作用是把"没见过的上下文"压到 0.5 附近，而不是 0 或 1。

计数有上限 `limit`：`n0+n1` 超过上限后双双右移一位（halve）。这实现了"旧证据逐渐失效"的指数遗忘，同时把计数保持在 16 位内。

### 5.3 混音器

```
st_i  = STRETCH[p_i]
mixed = Σ w_i · st_i + w_bias · 256
p     = SQUASH[clamp(round(mixed))]
w_i  += lr · (bit·PSCALE − p) · st_i
w_i   = clamp(w_i, 0, 4)
```

关键设计：

- **权重非负且有上界**。`w ∈ [0,4]` 让混合保持凸性，避免"某一路极端自信地反向"导致发散。
- **偏置路**用常数 `BIAS_STRETCH = 256`。它的作用是让混合器能在"全部输入都没信息"时输出 p=0.5，而不必依赖某一路恰好居中。
- **学习率**是乘法混合，不是加法：`wbase` 的选择同时依赖当前比特、匹配状态等，等价于一个**分段线性**的二级混音器（`weights2`，v15 的双流修正）——初始权重为 0，所以初始预测与单流完全一致，只是叠加一个学习到的修正。
- 点积累加顺序固定，保证逐位可复现。

**为什么混音要在 stretch 域**：概率域的线性组合没有"证据合并"的意义（两个 p=0.9 的独立证据不该得到 1.8），logit 域相加才近似独立证据的贝叶斯合并。

### 5.4 匹配模型

字节级匹配模型维护一个哈希表（`mht`，4 字节哈希）指向**上一次出现相同 4 字节的位置**。若匹配仍有效，就"预测下一个字节"，并把预测结果作为一路额外输入喂给混音器：

```
inputs[nctx] = ±STRETCH[msm[min(mlen,31)]]
```

符号由"预测字节的当前比特"决定；幅度由已匹配长度 `mlen` 决定（匹配越长越可信，`msm` 是 32 项的置信表）。

两个工程点：
- **断续匹配**（`gapLeft` / `lastDist`）：匹配中断时允许跨距继续容忍若干步，而不是立刻丢弃。这对付"重复块里夹了几个改动字节"的情况。
- **v15 的 `mht8`**：8 字节上下文的独立哈希表，碰撞率比 4 字节低几个数量级。理由很实际——在 33 MB 跨度上，4 字节哈希会被高频短串覆盖，记不住几 MB 外的长重复块。

### 5.5 v15 与 v20 的差别

| 特性 | v15 | v20 |
|---|---|---|
| 混合路数 | 双流（主 + 细粒度修正） | 单流 + 结构相位路 |
| APM/SSE 校准 | 有（`apmT`，v15 起） | 有，且 `apm2` 二级 |
| 匹配状态分档 | 2 档（短/长） | 4 档（<6 / <16 / 更长 / 无） |
| 变换族 | 无 | `V20_FLAG_TRANSFORMS` |
| 结构相位上下文 | 无 | 有（相位由 `s`/`r` 决定） |
| 组上下文（v21） | 不支持 | 支持 mode 1..7 |

`APM`（adaptive probability map）是一张 `(context, 33 个插值节点)` 的校准表，把混合后的概率再映射一次——本质是"按上下文对概率做分段单调校准"，对已经混合得很好的预测再挤出零点几个百分点。

`dualPass`：高端配置下同一条流跑两遍（第一遍热表），代价是一倍时间。

### 5.6 位级 CM（`bitcm.ts`，id33 r=2 专用）

这是与字节 CM **不同**的一个模型，因为输入是单条二值序列：

- **阶数 16 与 20**（`BITPLANE_BIT_ORDERS`），历史是纯粹的比特串；
- **两张 `Uint16Array`**（`zeros` / `ones`）而不是一张打包 `Uint32Array`：无移位、无掩码，且 `1<<o` 的索引天然对齐，计数溢出时的 halving 是精确的 `>>1`；
- `MAX_COUNT = 1000`；
- 混音器与字节 CM 同构，但**状态表是 Laplace 计数**（`(2n1+1)/(2(n0+n1)+2)`），这是 P16.2 修掉的一个 bug：早期用 `counts` 直接归一，在稀疏状态下严重高估置信度；
- **`squashTable` 的索引必须是整数**。`mixed` 是浮点，直接当索引会得到 `undefined` → `NaN` → 5 字节的"编码器"。这个 bug 曾经存在，且 roundtrip 是干净的（编解码同时坏），只有回执能发现。
- **算术编码器的 `prob` 语义是 P(1)**，而模型输出也是 P(1)。早期按 P(0) 用，只在均衡数据上看起来正常；偏斜数据会膨胀约 4 倍（理论 2,365 B vs 实测 15,001 B，且解码 0 错误）。

这三个 bug 有一个共同点值得记住：**能 roundtrip，不等于压缩正确**。只有"与理论值对照的回执"能抓住它们。

### 5.7 分档（memory × ratio）

`modelTuning = { maxTableBits: 24, matchTableBits: 23, largeOnly: true }` 是**上限**，实际按最终组/块的原始大小分档：

| 原始大小 | CM 位数 | mht4 | mht8 |
|---|---:|---:|---:|
| `< 512 KiB` | 21 | 20 | 20 |
| `[512 KiB, 4 MiB)` | 22 | 20 | 21 |
| `[4 MiB, 8 MiB)` | 23 | 20 | 22 |
| `≥ 8 MiB` | 24 | 20 | 23 |

`mht4` 固定在 20（P11.1）是一个**内存换比率**的取舍：24 位 CM 表体 576 MiB，mht4 从 22 降到 20 每个 live model 省 12 MiB，mht8=23 是 32 MiB，总表体 612 MiB。这是设计上限，不是实测 RSS。

分档依据是**最终组/块的原始大小**，不是文件名，也不是变换后的膨胀长度——不足 8 MiB 的组不会因为变换膨胀被误升 24 位。空流不继承父级大小。

### 5.8 成本模型与"报价=成交"

所有"采样/探针"给出的数字都是**代价估计**，不是决定。真正决定的是 `planHeader()` 序列化出来的字节数。为了让两者不漂移：

- 探针用真实序列化宽度（`selectionHeaderBytes`），不是"内容长度"；
- `realHeaderCosts` 开关只用于测试"载荷更小、容器更大"的陷阱分支；
- 最终比较一律用**完整容器长度**。

## 6. 理论盲点（诚实分析）

这一节不是"已知 bug 清单"，而是"这套设计在数学上必然看不见什么"。每条都给出可复现的观测或明确的推理。

### 6.1 长程结构化重复：AITDCC I 的 632 B

**观测**：AITDCC 的 `I` 文件，UCZ 1,630,028 B vs `zstd -18` 1,629,396 B——**差 632 B**（0.039%）。`N` 文件差 527 B。这两个文件上 UCZ 几乎打平 zstd-18，却远落后于 paq8px。

**机制一：分段把跨段匹配历史切断了。**

UCZ 的组是一份**独立**的 CM 模型加一条载荷。组内匹配模型的哈希表只看得见本组已编码的字节。地形分析一旦把文件切成 N 段，段与段之间的长重复就**永久不可见**：

- 段 A 里出现过的长块，段 B 再出现时，B 的模型从零开始；
- 唯一能吃到跨段的机制是"宏并组"（§1.5），但它的裁决基于 192 KiB 窗口的采样边际；
- 若这段重复的距离恰好大于所有窗口、或位于不同组，边际上是看不见的。

zstd/paq8px 用**持久字典 / 全局 match model**，天生没有这个问题。

**机制二：没有 repeat-offset 回退。**

LZMA 族有三个价格档：`literal` / `match` / **`rep-match`**（"距离等于最近 4 个用过的偏移之一"）。rep-match 的编码成本比一般 match 低得多，而**高度结构化、周期性重复**的数据里绝大多数匹配都是 rep-match。

UCZ 的匹配模型只有"距离 + 长度"的隐式维护（`lastDist`、`gapLeft`、`mth8`），没有把"重复偏移"作为**一等符号**建模。结果是：

- 命中一个远处重复时，它的代价没有被 amortize；
- 一段"每 4096 字节重复一次"的结构，理想编码是"距离 4096 × 一次声明 + 每周期一个字面差异"，UCZ 是每周期重新付一遍匹配代价。

这两条都指向同一个方向：**AITDCC I/N 的 632/527 B 不是"模型不够强"，而是"表示里少了一个原语"**。这不影响"通用有效"的原则——repeat-offset 是 LZMA 的通用原语，对任何周期性数据都成立。

有一条可量化的代理指标：`scripts/diag/inspect-structure.mjs` 的 `longRange` 段在 64 KiB / 1 MiB / 全文件三个窗口上给出**可匹配字节占比**与**重复偏移命中率**。这两个数之间的差，就是"持久字典能吃到、分段吃不到"的那部分。

> 未证明的部分：本沙箱**没有**编码 AITDCC I/N，上述 632/527 B 来自用户本机全量结果。这里给的是机制分析，不是"改完就能收回 632 B"的承诺。

### 6.2 lzma-9 友好的对齐数据：AITDCC H / J

**观测**：H、J 是 lzma-9 擅长的形态（高度对齐、规整记录）。

**机制**：UCZ 的转置族是"按 `s` 列切 + 逐列选编码"。但真正规整的定长记录，最优往往不是"每列独立"，而是**一部分列做差、一部分列原样、一部分列跨行预测**的组合。`TRANSPOSE_G3` 的"相邻列自适应合并"已经覆盖了一部分，但组的划分是**一次贪心**的结果，没有对"列组 × 子编码器"的组合做全局优化。

lzma 不需要显式建模列——它的 match finder 在同一列的重复上天然高效，只要记录足够规整。这就是"对齐规整数据上，一个通用 LZ 可能比一个复杂的列模型更好"的原因。

### 6.3 深度混合数据：B / C / K

**观测**：这三个文件的共同特征是"同一文件里多种地形交替"。

**机制**：UCZ 的地形分析是**一次**的（`analyze` → 合并 → 各组）。它不回溯：如果第一遍把某个边界判错，后面所有阶段都建立在错的坐标上。多轮"分-合-再分"（真的把每段当独立子问题重新跑完整流水线）会好，但代价是 O(段数 × 全流程)，当前设计明确放弃。

这与 §6.1 是同一个根：**分段的成本是"边界一旦确定就不可逆"**。

### 6.4 Silesia 的 mozilla / samba / ooffice / sao / x-ray

这五个是当前 Silesia 总账里仍有最大头寸的文件。它们的共同点是**混合地形 + 长程冗余**，因此同时受 §6.1（分段切断长程）与 §6.3（边界不可回退）影响。

一个具体的、可观测的量化线索（P16 系列，64 KiB 有界切片）：

- `mozilla-mid`：BIN3 比 TEXT3 好 **10.7%**（22,071 vs 24,705），说明"这份数据是文本"这类标签判断在这里是错的；
- `sao-mid`：`id 30 / s=28` 的转置组 36,456 B。`inspect-structure.mjs` 独立给出的最强滞后正好是 **d=28**（MI 1.77，等值率 0.21），且 28 的倍数 56/84/112… 全部上榜——这是一条 28 字节定长记录、记录内相关、跨记录弱相关的结构；
- `mr-mid`：`id 26 / s=2 / r=1024`，而 `inspect-structure.mjs` 给出 d=2 的等值率 **0.658**、对齐峰在 2/4/8/16/32/64/128 逐级衰减——典型的 16 位采样序列。

这些数字的作用不是"证明能省多少"，而是**确认流水线的选择与数据的真实结构一致**。真正剩下的头寸在 §6.1/6.3 那两条机制上。

### 6.5 位平面的边界

`refineBitplane` 是整文件粒度的，且要求 `n % 8 == 0`。这意味着：

- 一个"只有中间 200 KB 是位平面结构"的文件拿不到收益；
- 奇数长度文件完全被排除。

这是刻意的保守：位平面的价值来自"整条平面的统计"，局部切片会把 §3.9 的全平面仲裁退化成已被证伪的采样仲裁。

### 6.6 结语：这套设计**能**和**不能**做什么

**能**：在**统计结构**（上下文可预测）与**变换结构**（差分/转置/递推/位平面可显式表达）上稳定取胜，并且这条路径是可扩展的——新增一个变换只需声明它配哪些上下文，不需要新模型。

**不能**：把"长程重复"当作可复用原语（没有持久字典、没有 repeat-offset）；对已经确定的边界做回溯；对"整文件只有局部有结构"的数据做局部化。

这三点就是 P17 及以后真正该动的地方，而不是继续在 9 路上下文里调参。

## 7. 诊断工具

### 7.1 `scripts/diag/inspect-structure.mjs`

只读、不编码任何东西，用于回答"这些字节里有什么、流水线可能漏了什么"。

```bash
node scripts/diag/inspect-structure.mjs <file|dir> [--max-bytes N] [--json] [--no-ucsegs]
```

输出：JSON 到 stdout，人类可读表到 stderr。**不写盘**（除 `.diag-state/` 下一份用完即删的 esbuild 中间件，用于可选的 UCZ 段决策段）。

| 段 | 内容 | 用来回答 |
|---|---|---|
| `entropy` | 整体 H0/H1/H2(nibble)；每 4 KiB 块的 H0；相邻块 Jensen-Shannon 散度 | "一个模型够不够？" `jsOver005` 就是非平稳块数 |
| `stride` | d ∈ [1,256] 的互信息、等值率、滞后差分的一阶熵下降；2 的幂对齐峰 | 定长记录、交错平面、16/32/64 位对齐 |
| `longRange` | 64 KiB / 1 MiB / 全文件窗口上的贪心 LZ：可匹配字节占比、平均匹配长度、重复偏移命中率 | §6.1 的"跨段字典损失"有多大 |
| `subByte` | 每平面熵、高低半字节条件熵、`planeIndependenceGap = Σ_p H(plane_p) − H0` | 位平面（id33）有没有东西可吃 |
| `ucsegs` | 真实 `analyze()` 的段数、类别直方图、最大段 | 碎片化程度、拒掉的候选 |

**方法学**（写进输出，也写进这里）：

- `stride` 的 MI 在**有界前缀**（256 KiB）上估计，输出里带 `sampleBytes`，从不当成全文件结论；
- `longRange` 是**贪心** LZ + 4 字节哈希链（`chain = 16`），是"字典编码能拿到的下界"，不是最优解析；
- 任何截断输入都会在 JSON（`truncated`）与表格（`analysed first N B only`）两侧标出；
- 它**不给变换排名、不预测容器大小**。

自测（262,144 B 切片，本沙箱实测）：

| 切片 | 工具读出 | 流水线实际选择 |
|---|---|---|
| sao | d=28 的等值率 0.211，28 的整数倍全部上榜；对齐峰 d=8/16/64/128 | `id30 / s=28` |
| mr | d=2 等值率 **0.658**，对齐峰 2→4→8→16→32→64→128 单调衰减；最长匹配 703 | `id26 / s=2 / r=1024` |
| dickens | 无对齐峰；`planeIndependenceGap` 1.26 bit/字节；64 KiB 窗口可匹配 89.7% / 1 MiB 窗口 96.1% | `id23`（TEXT3 恒等） |

三者的选择与数据真实结构完全一致——这既是工具的自测，也说明**剩下的差距不在"选错规则"，而在 §6 的机制层**。

## 附录 B：本次（P16.2）修正的两处，以及一处**未**证实的怀疑

**修正 1 — 宏门窗口预算语义**（§1.5a、§2.6）

- 症状：`testP9Macro` 的 `assert.ok(partial.macroComparison?.sample)` 失败。
- 根因：窗口预算按**原始字节跨度**卡，长 FILL 游程把第二个真实片段挤出窗口，门返回 `null`。**该缺陷在 `0912a8f` 之前就存在**（`1d25fec` 可复现），`0912a8f` 只是没有修它。
- 修法：预算按非 FILL 字节计；`sample.bytes` 报信息字节、`sampleSpanBytes` 报原始跨度；步长探测改为在拼接后限 64 KiB 的缓冲上做，成本与窗口跨度脱钩。
- 边界证据（`tests/p9-macro.test.ts` 的夹具口径，沙箱实测）：跨度 1,134,592 B、信息量 86,016 B、预算 64 KiB → `sample.bytes = 57,344`（信息字节，< 86,016 且 < 跨度）、`sampleSpanBytes = 581,632`（原始窗口跨度，< 跨度）、`reusedProbePayload = false`、容器 roundtrip 通过。三个数字同时成立，才是"部分窗口未被借用为全组"的证明。

**修正 2 — 撤回 `refineWholeGroupProfile`**（§1 流水线图已无该阶段）

- 它从未在任何实测数据上赢过一次：dickens / mozilla / nci 采样筛后即放弃；`macroComparison` 侧 3 份冻结回执（`p16-macro-gate--dickens-*`、`--moz-all-sub`、`--samba-*`）里 `accepted` 全为 `false`。
- 更关键的是它的**动机不成立**：注释声称为 samba 的"单组计划"服务，但 samba 的实际产物是 `SUB_TRANSPOSE(s=38)`，而该函数在第一步就要求"所有段都是 `s=1,r=1` 的 TEXT3/BIN3"，samba 永远进不去。
- 按"零收益的时间消耗必须撤回或精确闸门"的纪律，撤回。

**未证实的怀疑 — Silesia 编码时间上升**

用户报告 `0912a8f` 相对 `1d25fec`：mozilla 653.2→765.3 s、samba 343.8→412.8 s、ooffice 100.4→117.0 s（共约 +197 s），而 12 个文件字节**完全一致**（40,038,909 B）。

沙箱**没有**复现这个时间差，因此下列是排除结果，不是结论：

1. `refineBitplane` 的两个触发门在 Silesia 上**不可能**在顶层触发：12 个文件的前 2 KiB `H0` 全部 ≤ 7.5（最高 sao 7.2499），而 STORE 主导门要求顶层 STORE 过半——12 个文件都没有。
2. 逐文件 A/B（同一 256 KiB 切片、同一进程条件）：`1d25fec` 26,916 ms / 80,390 B vs `0912a8f` 26,874 ms / 80,390 B——**没有变慢，字节完全相同**。
3. `refineWholeGroupProfile` 在 64–256 KiB 切片上实测 **0 ms（不合格早退）到 410 ms**，且从未采纳。

剩下未排除的是**分段内部的** `refineBitplane` 调用点（若某段自身以 STORE 为主，`bitplaneStoreTrigger` 可以在段级触发，代价是 8 平面 × 该段长度）。这条路径在沙箱无法用 ≤256 KiB 输入区分"段级"与"文件级"，因此**仍然开放**，需要一次针对大文件的、带 `onStage` 计时的本地测量来定位。撤回 §1 的 profile 阶段后，无论结论如何，管线都少了一条每文件必跑的后处理。
