# CM 上下文表宽的「按组实测」方案（R1 的正确形态）

> 状态：设计稿。未实施；本文记录为什么外部报告里「默认降 4 位、≤+0.07% 字节」的结论
> **不能直接照搬**，以及若要实施需要动哪些协议字段与回归项。

## 1. 现状：宽度是被"流长"决定的，不是被"内容"决定的

`src/lib/coder.ts` 的 `cmTableShape(n)` 只做两件事：

1. 按 `n` 落在哪个区间（`LARGE_CM_MIN_BYTES` / `JUMBO_CM_MIN_BYTES` / `HUGE_CM_MIN_BYTES`）给出档位；
2. `tier = min(cap, ceil(log2(8n)) + 1)`，再 `clamp(21..24)`；`probeDepth > 0` 时强制 `tier = 21`。

也就是说**同一段字节，只要长度一样，选表就看不出内容差异**。随后又有两条按 profile 的
例外把档位再抬到 23 位：

- `text-vertcol` / `text-tabcol`，`n >= 262144`（`src/lib/coder.ts` 的 `!probeDepth && v3 && …` 分支）；
- 普通 `bin` 且 `n >= 524288`。

例外存在的原因是可测的：这些族（竖排文本列、二进制车道）的混合器输入高度相关，
24 位稀疏哈希需要更宽的索引才能把碰撞压下去。

## 2. 为什么不能直接"默认降 4 位"

本仓库的实测（同一编码路径，单流、`--max`、不并行）：

| 流 | 21 位 | 23 位 | 差 |
|---|---|---|---|
| `B`（1.17 MB 文本） | 158,081 | 156,279 | **−1,802** |
| `C`（2 MB 文本） | 333,991 | 329,824 | **−4,167** |
| `K`（3 MB 文本） | 484,379 | 477,247 | **−7,132** |
| `10.G`（车道） | − | − | 22→23 位 **−35** |
| `2.O`（车道） | − | − | 22→23 位 **−120** |

外部报告的 `+0.07%` 是在**没有这两条例外**的流上测出来的（宽度从 auto 降到 auto−4，
例如 22→18）。对 `B/C/K/G/O` 这类流，降 4 位意味着把已经证明有效的 23 位拉回 19 位，
字节代价是 **+1.5% ~ +2.3%**，与报告的方向相反。

结论：可以讨论的只有"**在例外之外**是否降"，以及"**同一族内部按组实测**是否还能更省"。
两者都必须让解码端能推出同一档位，否则就是格式错误。

## 3. 协议改动（起草）

约束：容器 flag 的 16 位已全部占用（v18/v19/v20/v21/v22），组字（group word）也已用到
`0x200000`（`GROUP_CONTEXT_EXT_BIT`），解码端当前拒绝 `rRaw > 0x3fffff`。

**方案 A（推荐）：版本 v28 + 组字高位 2 bit 表示宽度档**

- `ver = 28` 表示"本容器的组宽由各组自己声明"。
- 组字新增 `GROUP_WIDTH_SHIFT = 22`，2 bit：`0 → 默认档`（同 v27 行为）、
  `1 → 默认档 −1`、`2 → 默认档 −2`、`3 → 默认档 +1`（上探一档，用于确实吃宽表的流）。
- 解码端：`v >= 28` 时不再拒绝 `rRaw >> 22`，并把宽度档传给 `encodeCM/decodeCM`
  （通过 `CMOptions.tableWidthStep`，只在 `v3 && variant === 'v20'` 生效）。
- 编码端：规划阶段对每个分组跑 2 档（默认档、默认档 −2），按实测字节数择优，
  只在 `n >= 64 KiB` 的组上做，且**只在 `--max` 档**（`fast/balanced` 保持默认档，
  避免再引入一层搜索）。

**为什么不用 flag 位**：位已满，且"同一容器里不同组可以有不同宽度"本来就是组级属性，
放在组字里语义正确；解码端所有校验都是围绕组字做的。

**风险**：这一改动会让**所有新建容器**从 v27 变 v28 且字节可增可减。必须：
1. 26 个金标文件的 `'max'` 输出允许变化，但**逐个记录差值**，且不允许任何文件 > +0.10%；
2. 历史容器（v≤27）解码路径完全不变（v28 分支是新增的），`tests/p12.test.ts` 的冻结夹具必须仍解出原字节；
3. 串行/并行必须同字节（现有 `tests/concurrency.test.ts` 已覆盖）。

## 4. 先要做的一件事：把"宽度收益"测出来

在动协议之前，先用现有的 `setModelBitsOverride()` 做**离线测量**（不改格式）：
对 `B/C/K/G/O/adult/wdbc/alice29/kennedy/ptt5` 各跑 auto、auto−2、auto−4，
记录 **(字节, 耗时, 峰值 RSS)** 三元组。只有当"auto−4 在某些族上确实省时且字节代价
< 0.10%"时才值得进协议；否则连 v28 都不该开。

`cmModelBytes(nctx, bits, mhBits)`（`src/lib/planner/budget.ts`）已经能精确算出
每档的内存：`nctx × (1 << bits) × 4 B` + 匹配表，所以候选档位的代价是可预估的。

## 5. 备选方案 B：只改"试探档"

不动格式，只把 `probeDepth > 0` 的试探宽度从固定的 21 位改成"按 `n` 再降 2 位"，
并把 `max` 档的最终宽度保持不变。这能省规划期时间（`--max` 的耗时大头在试探），
但**不改变任何字节**，因此风险接近零，收益只体现在墙钟时间上。

如果目标只是"更快"，方案 B 更划算；如果目标是"更小或更省内存"，才需要方案 A。

## 6. 与外部报告的关系

- 报告 R1 的**机理**正确：表宽是时间/内存的主开关。
- 报告 R1 的**数值**不适用于本仓库：本仓库已有"按族提档到 23 位"的例外，收益正来自这些例外。
- 报告 R6（14 位省 45% 时间、+0.59% 字节）与本仓库数据方向一致（宽度换字节），
  但绝对比例不同，应使用本仓库自己的测量表。
